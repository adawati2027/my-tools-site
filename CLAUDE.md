# أدواتي (Adawati) — adawati.space

Free multi-tool Arabic website (calculators, converters, games, daily-info tools). Owner: Ahmed Amawi. This file exists so a new Claude Code session can resume work with zero ramp-up if this session is lost.

## Deployment — READ THIS FIRST

**There is no local git repo.** Do not run `git init`, `git commit`, etc. — they will not work as expected and are not how this project deploys.

Deployment is via a custom script that talks to the GitHub REST API directly:

```
node push-to-github.js "commit message here"
```

- Reads `GITHUB_PAT` from a local `.env` file (`GITHUB_PAT=...`, gitignored/excluded from the pushed tree).
- Repo: `adawati2027/my-tools-site`, branch `main`, pushed via blobs → tree → commit → ref update (not a real git working directory).
- **Always pushes every file in the project** (no diffing) — pushing after any edit is normal and expected, don't wait to "batch" unless GitHub's rate limit forces it.
- Site is served via GitHub Pages, custom domain `adawati.space` (CNAME on GitHub Pages auto-redirects `adawati2027.github.io/my-tools-site/` → `adawati.space/` with a real 301 — already verified working, don't re-verify).
- Has retry logic built in for transient network errors (`ECONNRESET` etc.) — exponential backoff, 4 attempts.
- After pushing, changes take roughly 30–90 seconds to actually go live; poll with `curl` + `grep` for a known string rather than assuming instant.

### GitHub API rate limiting (hits this OFTEN with ~260 files/push)

Two different things can fail with a 403:
- A short secondary/abuse-detection throttle — usually clears in 1–3 minutes.
- The real hourly quota (5000 req/hr) — tied to a fixed reset epoch.

**`GET /rate_limit` is unreliable** — it has repeatedly shown "5000/5000 fresh" moments before/after real failures this project. Do not trust it.

The correct way to get the real reset time: make one direct failing call (e.g. `POST /repos/adawati2027/my-tools-site/git/blobs`) and read the `X-RateLimit-Reset` response header from that actual call. Compute wait seconds from `epoch - now`, then use `ScheduleWakeup` for exactly that delay (capped at 3600s). Do not guess, do not poll in a tight loop, do not retry more than once without getting a fresh real reset time.

## Verification policy — the load-bearing rule of this whole project

**Never publish a legal/financial/religious fact without verifying it via WebSearch/WebFetch first.** This site has real calculators (taxes, zakat, customs, social security) that Jordanians and others actually rely on. If a fact can't be verified, or sources conflict, either:
- Say so transparently in the UI (a disclaimer, not a fabricated number), or
- Don't build that feature at all.

Concrete precedent: an income-tax calculator bug was reported where "extra expense exemption" was a flat 5,000 JOD for everyone. Investigation found the real law (Article 9, Income Tax Law 34/2014, as amended 2020+) breaks it down as 1,000 self + 1,000 spouse + up to 1,000/child (max 3 kids) = up to 5,000. A different official government page ("الجديد في أحكام القانون" on istd.gov.jo) shows totally different numbers (28,000 cap, 7/14/20% brackets) — that page turned out to describe the law's *original 2014 enactment*, superseded by later amendments; it's just an outdated government page, not current law. This took 5+ rounds of WebFetch on conflicting sources to resolve. **Government pages are not automatically authoritative over other corroborated sources — cross-reference multiple sources and reason about which is actually current before trusting any single one, including official ones.**

**This got re-flagged by external QA reviewers three separate times** (each citing the same superseded 7/14/20%/28,000 numbers) before being put to rest 2026-09-07 with a dedicated fresh re-verification fork: (1) istd.gov.jo's own laws listing explicitly confirms the law *currently in force* is "رقم 34 لسنة 2014 المعدّل بالقانون رقم 38 لسنة 2018", effective 1/1/2019 — direct proof the "الجديد في أحكام القانون" page describes the superseded original text, not current law; (2) a source quoting Article 9 directly; (3) PwC's Worldwide Tax Summaries for Jordan (tax-rates and deductions pages, last reviewed July 2026 — 2 months before this check) match the site's numbers exactly on both brackets (5/10/15/20/25/30%) and exemptions (9,000 + 9,000 + up to 5,000 = 23,000 cap). Three independent angles, one of them the regulator itself. **Do not re-investigate this from scratch again** if it resurfaces — point to this note and the on-page disclaimer (`jo/calculators/income-tax/index.html`) instead, unless the user has specific knowledge of a *new* legislative change (a real amendment, not a re-read of the same old istd.gov.jo page). One genuine gap found during this re-check, not yet added to the site: a 1% "national contribution tax" applies to income over 200,000 JOD/year (very high earners only) — worth adding as a footnote sometime, not a correctness bug in the existing brackets.

When genuinely unresolvable, say so in the page's own disclaimer text rather than picking a number with false confidence.

## Firebase (quiz "friend challenge" feature)

Project: **`adawati-challenges`** (Firebase console, Spark/free plan), owned by the same Google account as Analytics/Search Console/AdSense (all already correctly configured for `adawati.space` — verified, don't redo that audit).

**Shared engine (built):** `jo/games/quiz-engine.js` holds all Firebase/challenge/leaderboard/UI logic. Each game's `index.html` just defines `const QUESTIONS = [...]` and `const QUIZ_CONFIG = {gameId, shareTitle, challengeText, resultText(score,total,pct), resultMessages:[{min,emoji,msg}]}` before loading the engine script — don't copy-paste engine logic into a page again. Firebase JS SDK loaded via compat build from `gstatic.com` CDN (not npm). Config object is inline — safe to be public (Firebase web API keys aren't secrets; access is controlled by Firestore security rules).

**Group-challenge model (current, changed from the original 1-on-1 design):** single-player mode has been removed entirely — visiting a game page with no `?challenge=` param shows only the "ابدأ تحدي" box, `#quizArea` stays `display:none` until a challenge is actually started. `MIN_PLAYERS = 2`, `MAX_PLAYERS = 20` (constants in quiz-engine.js) — the creator sees a live count of who has accepted (`acceptCountLabel`/`accepterNameSpan`/`creatorStartBtn` elements) and the "ابدأ اللعب" button stays disabled until at least 1 joiner has accepted; `joinChallenge()` and `showChallengeJoinIntro()` both block joining once `MAX_PLAYERS` is reached. Any number of joiners (not just one) can accept via the same link — the `accepts`/`players` collections already support N participants, the leaderboard renders all of them.

**Category selector (opt-in per game):** `QUIZ_CONFIG.categories` (array of `{key,label}`) turns on a category-picker UI (`#categorySelectArea`, rendered by `initCategorySelector()`) shown to the creator before they start a challenge; `pickQuestions()` filters `QUESTIONS` by `q.cat === selectedCategory` when set (special key `'mix'` = no filter). Currently only `songs-quiz` uses this (`ar` / `foreign` / `mix`, split at a hardcoded index boundary in the source questions since the original batch was written Arabic-then-foreign) — other games don't set `categories` and behave as before.

**Firestore collections** (`challenges/{challengeId}`):
- `challenges` — doc has `creatorName`, `questions` (locked array for this challenge, already category-filtered if applicable), `game`, `acceptedCount` (number, starts at 0, see atomic-join note below), `createdAt`.
- `challenges/{id}/players/{autoId}` — `name`, `score`, `total`, `timeMs`, `submittedAt`. Leaderboard sort: `orderBy('score','desc').orderBy('timeMs','asc')` — **requires a composite index**, already created (players: score desc, timeMs asc, scope Collection).
- `challenges/{id}/accepts/{autoId}` — `name`, `acceptedAt`. Written when a joiner clicks "قبول التحدي"; the creator listens on this via `onSnapshot` (shows a live count + names of everyone who's joined, not just the first).
- `challenges/{id}/starts/{autoId}` — `startedAt`. Written when the creator clicks "ابدأ اللعب"; every joiner listens on this via `onSnapshot` and starts playing at the same moment (full sync).

Security rules: public `read: true` everywhere, `create` allowed with field validation, `delete` always `false`. `update` on the `challenges` doc is allowed **only** for an atomic `acceptedCount` increment-by-exactly-1 (`request.resource.data.diff(resource.data).affectedKeys().hasOnly(['acceptedCount']) && request.resource.data.acceptedCount == resource.data.acceptedCount + 1`) — added to close a race condition where simultaneous joins past the old client-side-only `accepts.size()` check could theoretically exceed `MAX_PLAYERS`. `joinChallenge()` in quiz-engine.js now uses `db.runTransaction()` to read `acceptedCount`, abort with a `CHALLENGE_FULL` error if it would hit `MAX_PLAYERS`, and atomically increment it + create the `accepts` doc together. All other collections (`players`, `accepts`, `starts`) keep `update`/`delete: if false` (replay-prevention stays client-side via `localStorage`, see `getPlayedRecord`/`savePlayedRecord`). No server-side dedup of a single person playing twice from two browsers/devices — discussed with the user, accepted as a known limitation rather than building real auth for it. Rules edited via the Firebase console Monaco editor — see the gotcha note below; last edited 2026-09-07 to add the `acceptedCount` update rule.

### Editing Firestore Rules via the console (gotcha)
When typing into the Rules Monaco editor via browser automation, **it auto-inserts a matching closing brace for every `{` you type** — including path-param braces like `{challengeId}`, not just block braces. For a small single-block edit this usually produces exactly one extra stray `}` (fix: click Publish, read the line number from the "Unexpected '}'" error, delete that one line, Publish again). For a **full-file replace of a large multi-block ruleset** (done 2026-09-07 to add the `acceptedCount` rule), it produced 6-8 extra stray `}` at the end of the file, not just one — the "explode on Enter between an auto-closed pair" behavior duplicates against each manually-typed closing brace on its own line for every block-level `{`. What worked: select-all + delete + retype (a JS-clipboard-paste was tried first to bypass this entirely but `navigator.clipboard.writeText` hung/timed out in this environment), then compare the displayed line count against the expected line count of the source you meant to type, `Ctrl+End` + `Backspace` to trim the exact number of extra trailing lines (2 backspaces per extra line: one for the `}`, one for its newline), verify via reading the page text before publishing, then Publish and fix any single remaining stray via the line-number method as before. Don't try to fix this by eyeballing indentation in a screenshot — the visual indent can look cascading/wrong while the actual brace balance is fine (or vice versa); count `{` vs `}` instead.

### In-page English translation system (quiz-engine.js, built 2026-09-07)

The 14 game pages under `jo/games/` **do not load `i18n.js`** (confirmed via grep) — the site-wide translation system doesn't reach them. When asked to translate the game UI to English, loading `i18n.js` there was deliberately rejected: `i18n.js`'s `detectDefaultLang()` has a path-based rule that force-returns `'ar'` for anything under `/jo/`, which would override an English-preferring visitor's actual choice — architecturally wrong for this specific case. Instead `quiz-engine.js` has its own **self-contained** EN/AR system, independent of `i18n.js`:

- `quizLang` — detected once via `localStorage.getItem('lang') === 'en' ? 'en' : 'ar'`.
- `QT` object (~35 keys, ar+en, some as functions taking params) + `qt(key, ...args)` helper.
- `qGetHomeHref()` — local re-implementation of `i18n.js`'s country-hub lookup (`sessionStorage.getItem('adawati_country')` → `{OM:'om/',SA:'sa/',JO:'jo/',AE:'ae/',US:'us/',GB:'uk/'}`, default `'index.html'`) — this is what actually fixes the back-link (see the bug note above), not `data-i18n`.
- `applyQuizTranslations()` — called once at page init. Walks `[data-qt]` (textContent), `[data-qt-placeholder]` (placeholder attr), `[data-en]` (English-only override text, applied only when `quizLang==='en'`), and fixes `.page-header a`'s href/text directly.
- `qShareTitle()` / `qChallengeText()` / `qResultText(score,total,pct)` / `qResultMessages()` — read `QUIZ_CONFIG.shareTitleEn`/`challengeTextEn`/`resultTextEn`/`resultMessagesEn` when `quizLang==='en'` (added to all 14 pages' `QUIZ_CONFIG` 2026-09-07), else fall back to the original Arabic fields. Wired into `shareResult()`, `shareOrCopy()`, `showResult()`.
- Scope, deliberately: **English only**, not all 6 site languages (explicit user choice when asked). The **question text itself stays Arabic-only** — an `#quizArabicNote` element (empty div under `progressLabel` on all 14 pages) shows `qt('arabic_note')` ("(questions are in Arabic)") only in English mode, so this isn't mistaken for a bug. Page `dir` stays `rtl` always, even in English mode — text-only translation, not a bidi layout rebuild.
- Hub-card labels/descriptions for these 14 games on `ae/index.html`/`us/index.html`/`uk/index.html` (the English-language country pages) — this was the original complaint that started the whole translation project — were translated to English 2026-09-07 (13 game cards + the "🏆 تحديات" tab label → "🏆 Challenges", plus the arrow given `data-i18n="start"` matching every other card on those pages instead of hardcoded "ابدأ →"). `jordan-quiz` isn't on these pages at all (excluded from non-Jordan country hubs per explicit instruction), so it needed no hub-card translation. `om/index.html`/`sa/index.html` stay Arabic-only by design (those are Arabic-first pages, `lang="ar"`).

When adding a 15th game or editing an existing one, any new page-level string needs: an ar/en pair added to `QT` in `quiz-engine.js` (or a `*En` field on that page's `QUIZ_CONFIG` if it's per-game content like `shareTitle`), a `data-qt="key"` (or `data-qt-placeholder`) attribute on the HTML element, and — if it's the h1 — a `data-en="..."` attribute directly on the tag instead (h1 has no wrapper element to hang a generic key off cleanly, so it uses its own override mechanism).

### Logo quiz (`jo/games/logo-quiz/`) — image-based questions, built 2026-09-07

User explicitly requested real brand/car/restaurant logo images despite trademark/copyright risk (confirmed via `AskUserQuestion` — chose "شعارات حقيقية برغم المخاطرة" over a safer illustrated-icon alternative). Architecturally different from games 1-14 in two ways:

**Engine support (quiz-engine.js):** questions can now carry an optional `img` field. `pickQuestions()` copies it through into `activeQuestions`; `loadQuestion()` calls `getQuestionImageEl()` (same lazy-DOM-injection pattern as `getTimerEl()` — creates a `<img id="questionImage">` right before `#questionText` on first use, hidden by `display:none` when a question has no `img`) and sets/clears its `src`. Every other game's questions are unaffected (no `img` field → element stays hidden). Options (`opts`) are still plain brand-name strings.

**Logo sourcing (not WebSearch fact-checking — a different verification problem):** the questions aren't checkable facts, they're "does this image URL actually show this brand's real logo." The method that worked: query **Wikidata** (not raw Commons filename-guessing, which fails constantly — brand names rarely match their exact Commons file naming) for each brand's Q-id via `wbsearchentities`, then read its **P154 ("logo image") claim**, then build the image URL as `https://commons.wikimedia.org/wiki/Special:FilePath/<urlencoded filename>` (a stable redirect-to-current-file endpoint, doesn't need the actual `upload.wikimedia.org` hash path) and verify with an HTTP HEAD (following redirects) for `200` + `image/*` content-type before accepting it.

**Two real gotchas hit during sourcing, both worth knowing if this pattern is reused:**
- **Wikidata rate-limits fast** under rapid sequential requests even with a compliant `User-Agent` — a first pass with only a 150ms gap between brands and no retry logic silently returned `no_wikidata_match` for ~65 very famous brands (Toyota, BMW, Coca-Cola, Starbucks, IKEA, Walmart, etc. — all of which do exist and resolve fine individually). Fixed by adding exponential-backoff retry (4 attempts, 800ms base) on 429/403/5xx to both the Wikidata and Commons calls, plus slowing the per-brand delay to 600ms. Don't trust an empty/no-match result from a fast unthrottled batch — it's very likely rate-limiting, not missing data.
- **A Wikidata entity's P154 property can carry multiple claims (historical/alternate logos), and the array order is NOT rank order.** Naively taking `claims[0]` picked wrong images for ~30 brands including real bugs, not just stylistically-outdated ones: **Toyota** initially resolved to a trademark-registration filing scan (`Registered trademark img 06.png`) instead of the actual oval logo, because that claim happened to sit before the `rank:"preferred"` one in the array. Fixed by explicitly preferring the claim with `rank === 'preferred'`, falling back to the first claim only if none is preferred. Even after that fix, **Wikidata's own "preferred" claim was occasionally still wrong** — Peugeot's preferred P154 claim points to a photo of a parked Peugeot 308 (`2021 - Peugeot 308 III (C) - 42.jpg`), not a logo at all, a genuine Wikidata data-quality issue, not a script bug; caught by eyeballing every resolved filename for the whole batch and manually re-pointing that one entry at Peugeot's `normal`-rank claim (the real logo file) instead. **Always spot-check the final filename list by eye before trusting it** — a HEAD check only proves the URL returns *an* image, not that it's the *right* image.
- Also caught: **wrong-entity matches**, not just wrong-image-on-right-entity — "Baskin-Robbins" and "Dunkin'" both initially resolved to the Q-id for "Dunkin' Brands" (their shared former parent holding company) instead of their own separate Wikidata entities, because the keyword-filtered search fallback picked the first description-matching candidate rather than the exact-name match. Both produce a *valid* image (so the automated HEAD check passes silently) but the *wrong* one, and duplicate-QID/duplicate-image-URL detection is what actually caught it — **always dedupe the final resolved set by both Wikidata Q-id and by image URL**, not just by input brand name, since two different brand names quietly resolving to the same underlying entity/image is exactly this bug and won't show up any other way.

**Final set (first pass, 2026-09-07):** 109 questions (60 tech/global brand, 35 car brand, 14 restaurant/fast-food), 0 duplicates, 0 malformed, every image URL HEAD-verified and the full filename list manually eyeballed. Room to grow later the same way the other 14 games did (well-verified batches over padding) — the `logo_source.js`/`build_logo_questions.js` scratchpad scripts (Wikidata-search + preferred-rank-aware P154 lookup + HEAD verify + question-array serializer) are the reusable pattern if more brands are added.

**Expanded to 464 questions (2026-09-08)**, adding a 4th category (airlines) on top of tech/cars/food: tech 289 (60 original + 229 new), cars 81 (35 + 46), food 66 (14 + 52), airlines 28 (new category). ### Logo quiz — 2026-09-08 curation rewrite (464 → 139, still growing)

User reported two real problems with the 464-question set: (1) **most images had the brand's name spelled out as plain text inside the image** — trivial "read the text" rather than "recognize the logo," and (2) **images took 2-3 seconds to load** every question. Root-caused and fixed both, then kept growing the pool under a much stricter quality bar per follow-up user requests (target moved from "fix it" → 200 in 4 difficulty tiers → 200 in 2 tiers → difficulty removed entirely, flat pool, target ~400, bias toward harder/obscure logos and car brands). As of this note: **139 verified questions live** (95 tech/app, 32 cars, 8 airlines, 4 food), still short of the ~400 target — see "Realistic ceiling" below for why.

**Speed root cause:** every image URL was `https://commons.wikimedia.org/wiki/Special:FilePath/<file>`, a Wikimedia-side redirect endpoint — measured at 1.8–2.4s per image due to 3 chained redirects before reaching the real `upload.wikimedia.org` file. Fix: resolve each URL's final redirect target once at build time, strip Wikimedia's `?utm_source=...` tracking query params (they were breaking naive `.svg` extension detection — always `url.split('?')[0]` before matching an extension), download the file, and **self-host it** under `jo/games/logo-quiz/assets/<slug>.png` — cut load time to <0.1s (same-origin, served by GitHub Pages/the site's own CDN) and removed the Wikimedia dependency from the hot path entirely.

**Text-in-image root cause:** Wikidata's P154 "logo image" claim usually points at a company's *official registered* logo, which for most companies is the full wordmark/lockup (e.g. "GOOGLE" spelled out), not the standalone icon casually used as an app icon or car badge. This is systemic, not a sourcing bug — re-auditing the original 464 found only ~44 were genuinely icon-only after a full manual visual review (a ~9.5% yield). **The quality bar applied, and why it survived several rounds of user clarification:**
- **EXCLUDE**: any image where the brand's answer-option text is spelled out in plain readable typography (the vast majority of pulls). Also exclude on sight: **wrong-entity/rebrand mismatches** found this round — a "Twitter" question resolving to the new X-bird logo, "WordPress" resolving to the Yoast plugin's logo, "Etisalat" resolving to the post-rebrand "e&" mark with "etisalat and" text baked in, "GMC" resolving to a *Greater Manchester Council* logo (!) — these are real Wikidata/Commons tagging errors, not just text-count issues, and only show up by actually looking at the image.
- **KEEP**: pure pictorial symbols with zero text (Apple, Mastercard, Mercedes-Benz star, Toyota rings, Audi rings, Nike swoosh, Target bullseye, Chevrolet bowtie, Rivian/Rimac shield marks), plus short 2-4 letter **stylized monograms/app-icon tiles** that don't spell the full multi-word answer (Adobe's "Ps"/"Ai"/"Pr"/"Ae"/"Au"/"Id"/"Xd"/"Ch"/"Br"/"An" app-icon convention; Microsoft Office's "W"/"X"/"P"/"N" tiles; Rolls-Royce "RR"; Suzuki/Honda-style single-letter badges; Netflix/Facebook/Bing single-letter icons). One deliberate exception: BMW's roundel has small peripheral "BMW" letters baked into the ring design but was kept anyway since the circular badge shape/colors are the actual recognizable element, not the tiny text.
- **Script that doesn't spell the Latin answer text is not a giveaway**: Emirates' Arabic calligraphy mark and PIA's Urdu calligraphy mark were kept (cropped to remove the accompanying Latin wordmark) since they don't read as "Emirates"/"PIA" to someone reading the Latin-script answer options — genuinely harder to identify, not easier.
- **Abbreviations that don't exactly equal the answer string are allowed** even if not fully abstract: "ANA" (for "All Nippon Airways"), "AZAL" (for "Azerbaijan Airlines"), "MG" (for "MG Motor") were kept — contrast with "HP", "UPS", "KLM", "NIO", "AWS" which were excluded because those abbreviations *are* the literal expected answer, so showing them is a 100% giveaway with zero brand-recognition required.
- **Crop don't discard**: many rejects have a clean icon-on-top/text-below (or icon-left/text-right) layout — `build_assets.js`'s `cropToPng(srcFile, cropRule, aspect, outPng)` renders the source at its true aspect ratio (NOT a square contain-fit — an earlier version of this function did that and barely cropped anything, since a wide image auto-fills a square box's width, leaving the "cropped" region still showing ~97% of the original; the fixed version fixes one axis to a constant size and computes the other from the real aspect ratio, then clips a container to the wanted fraction with the image positioned flush against the crop edge) and clips a `top`/`bottom`/`left`/`right` fraction. **Always re-render and visually verify a crop before trusting it** — first-guess percentages were wrong most of the time (Baskin-Robbins/Pizza Hut/Rolex/Vodafone/7-Eleven all needed 2-3 iterations to fully exclude residual text; Target/Philips/The North Face had their icon-vs-text layout assumption backwards on the first guess — Philips turned out to be text-on-top/icon-on-bottom, inverted from what the thumbnail suggested, and The North Face's icon was bottom-right with the rest of the image blank, not cleanly croppable at all, so it was dropped entirely rather than force a bad crop). 7-Eleven was also dropped after 3 crop attempts still left the "7" digit unrecognizable or the "ELEVEN" text partly visible — not every crop-looking case is actually recoverable within reasonable effort.

**Sourcing method, changed from the original Wikidata-P154-pull approach:** blind Wikidata pulls have the ~9.5% yield described above. Direct Commons filename-guessing has a much higher yield when you already suspect an icon-only file exists — `curl -s -o /dev/null -w "%{http_code}" -L -A "<UA>" "https://commons.wikimedia.org/wiki/Special:FilePath/<guessed filename>.svg"`, trying 2-3 common patterns per brand (`<Brand>_logo.svg`, `<Brand>.svg`, `<Brand>_icon.svg`) — found the icon-only Mercedes-Benz star, BMW roundel, and Toyota oval-icon files this way after Wikidata's own P154 pull had returned their wordmark versions. Yield varies a lot by category: **tech/software app-icons are the best category by far** (Adobe's CC app suite, Google Workspace, Microsoft Office — all ~50-70% found-and-clean, since "app icon" is a real, common asset type companies actually publish separately from their wordmark); **cars are moderate** (~15-25% once you've covered the ~20 most famous marques — niche/regional/coachbuilder brands like Zagato, TVR, Lada, UAZ mostly don't have any simple-filename Commons SVG at all, found or not); **niche regional airlines are the worst yield** (found 6/40 in one batch) since most simply don't have a logo file on Commons under a guessable name.

**Practical ceiling on the ~400 target, worth knowing if this is picked up again**: this isn't a "keep grinding, it'll get there" situation. Growth per round follows a clear curve — tech app-icons stay productive far longer than any other category since there are hundreds of real software products with genuine icon-only branding; car and airline growth slows sharply after the ~30-40 most globally-recognizable marques are covered, because smaller/regional/defunct brands frequently have **no logo image on Commons at all**, not just a wordmark-only one — no amount of better guessing recovers a file that doesn't exist. Getting materially closer to 400 while holding this quality bar means either (a) grinding through many more small batches of tech app-icons (highest remaining yield, but increasingly obscure software), (b) accepting a Wikidata-search-driven (not filename-guess-driven) pass across a much larger brand candidate list the way the original 464 was built, re-applying the full visual-review+crop pipeline to the results, or (c) both. Don't reintroduce a difficulty-tier system without explicit new instruction — it was built, then explicitly reverted twice in the same session (see below) in favor of a single flat pool.

**Difficulty tiers — built, then explicitly reverted, don't rebuild without asking:** mid-session the user asked for 4 tiers (easy/medium/hard/very-hard) via a `QUIZ_CONFIG.difficulties` array mirroring the existing `categories` selector pattern (`initDifficultySelector()`/`selectedDifficulty` in `quiz-engine.js`, generalizing `pickQuestions()` to filter by both dimensions when set) — built and shipped once. Immediately revised to 2 tiers (medium/very-hard) — every question's `difficulty` field was mechanically collapsed (`easy→medium`, `hard→very-hard`) via a regex pass over the source-of-truth files rather than manually re-judging each entry. Then, before that 2-tier version even finished a push cycle, the user asked to **remove the difficulty selector entirely** — flat pool, `shuffle(pool).slice(0, 12)`, no filtering. `QUIZ_CONFIG.difficulties` and the `#difficultySelectArea` div were removed from `jo/games/logo-quiz/index.html`; the `difficulty` field was dropped from newly-built question objects (older entries may still carry a harmless unused field depending on which scratchpad build script generated them — not worth cleaning up retroactively). `initDifficultySelector()`/`selectedDifficulty`/the difficulty-filter branch in `pickQuestions()` were deliberately left in `quiz-engine.js` as dead code (same no-op-when-unset pattern already established for `categories` on games that don't use it) rather than ripped out — cheap to leave, and the pattern is already proven safe.

**Self-hosted asset pipeline, reusable for future rounds:** `jo/games/logo-quiz/assets/<slug>.png` — every file produced by rendering the (possibly cropped) source SVG through headless Chrome (`chrome.exe --headless --screenshot=...`) at a fixed intrinsic size, never relying on live Wikimedia URLs in the shipped question data. The scratchpad's round-by-round scripts (`round<N>/candidates.js` → `probe.js` → `download_batch.js` → `build_grid.js` (contact-sheet visual review, 24-per-page, 6 columns, labeled) → `final_list_r<N>.js` → `build_assets_r<N>.js` → merged into `build_merged_questions.js` → injected into the live HTML) are copy-paste-and-rename templates of each other by this point — grab the most recent round's copies rather than writing fresh ones. **Pace Commons requests at 600-700ms with retry/backoff** (established in the original 464-question pass, re-confirmed here) — one batch at 150ms silently got ~68% of downloads replaced with a "Wikimedia Error" HTML page saved under the expected filename instead of real image bytes; always sanity-check a downloaded file doesn't start with `<!DOCTYPE html` before trusting it's real.

**Verification workload & rate limits** (lessons from actually running this, useful if this pattern gets reused for another content push): background `fork` agents doing WebSearch-verified question generation, one category per fork, run well in parallel (9 were launched at once for games 6-14 in one session). Real constraints hit in practice:
- **WebSearch has a per-session budget** (200 calls) — once exhausted, forks fall back to WebFetch against specific pages (Wikipedia etc.), which still works but is slower per fact and is why later categories in a batch return fewer questions than earlier ones.
- **The account has an API rate limit that can trigger mid-fork** — first a short session-scoped one (resets within hours, a fixed daily clock time in Asia/Muscat), then (if enough forks run) a **weekly** one (resets a fixed day/time in Asia/Muscat, hit once this session) — a failed fork just needs `SendMessage` to its agentId telling it to resume; it picks up from where it left off. Don't loop retrying immediately — check the error message for the actual reset time/day and wait for it.
- A fork that returns 0 questions because WebSearch was exhausted **before any query ran** isn't a dead end — resuming it after telling it to fall back to WebFetch (like other forks in the batch did) works (this happened to the ثقافي fork, which got 138 questions on retry after initially returning empty).
- `push-to-github.js` itself hits GitHub's own separate rate limit constantly when pushing several games in sequence within a short window (each push sends the full ~270+ file tree) — this is unrelated to the Claude API limits above, see the rate-limiting section near the top of this file for how to handle it.

## Google Sign-In `auth/unauthorized-domain` — fixed 2026-09-09

After shipping the Google Sign-In UI (see above), a live click on the "Sign in with Google" button on the actual site failed with a generic "Something went wrong" toast — no code path bug, the real Firebase error (confirmed by calling `signInWithPopup` directly via a live Chrome DevTools Protocol session and reading `err.code`) was **`auth/unauthorized-domain`**: `adawati.space` was never added to Firebase Auth's **Authorized domains** list (Authentication → Settings → Authorized domains in the Firebase console) — only `localhost`, `adawati-challenges.firebaseapp.com`, and `adawati-challenges.web.app` were present by default. Firebase does not auto-add a custom domain just because GitHub Pages/DNS is configured for it; this is a separate manual step. **Fixed by adding `adawati.space` as a Custom authorized domain via the console** (confirmed live — `signInWithPopup` now opens a real `accounts.google.com` sign-in popup instead of erroring immediately). If Google Sign-In ever breaks again with a generic error, check this list first before assuming a code regression.

**CDP typing gotcha hit while fixing this**: typing into the domain-add dialog's input using `Input.dispatchKeyEvent` with both a `keyDown` (carrying `text`) and a separate `char` event for the same character double-inserts every character (Chrome processes `text` on `keyDown` *and* the `char` event as two separate insertions) — produced `"aaddaawwaattii..ssppaaccee"` from `"adawati.space"`. **Use `Input.insertText` for typing into a field, not manual `keyDown`+`char` event pairs** — a single `Input.insertText` call after a real (coordinate-based `Input.dispatchMouseEvent`, not `.click()`) click into the field worked correctly and is the simpler, correct approach; this reconfirms the same lesson noted elsewhere in this file about the Firestore Rules Monaco editor, just for a plain `<input>` this time.
