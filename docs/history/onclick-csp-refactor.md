**`file-converter.html` — refactored, and a real pre-existing bug fixed as a side effect.** This page's drag-and-drop upload zone had `ondragover="e=>{e.preventDefault();...}"` as its inline attribute value — but an HTML event-handler *attribute*'s content becomes the literal body of an implicit wrapper function, so this content was just **evaluating an arrow-function expression and discarding it**, never actually calling `preventDefault()`. Without that call, the browser's default dragover behavior applies and the `drop` event never fires — meaning **drag-and-drop file upload was silently broken** (only the "click to browse" path worked) for as long as this page has existed, invisible in any manual click-through test since clicking still worked fine. Caught and fixed as part of the normal refactor (the handler became a real `addEventListener('dragover', function(e){ e.preventDefault(); ... })`), then specifically verified via a CDP test that dispatched a synthetic `dragover` event with a spied `preventDefault` and confirmed it now gets called — this is the second real pre-existing bug this refactor project's mandatory functional-testing step has caught as a side effect (see the `kids-math.html` note above for the first), reinforcing that this testing step is worth keeping even when the diff being tested "should" be purely mechanical. **Real pre-existing bug found and fixed, third one this refactor's testing step has caught**: 5 of the 6 hubs (`jo`, `sa`, `ae`, `us`, `uk` — `om/index.html` was already a newer, already-correct variant) each define their **own local** `function toggleLangMenu(){ m.style.display = ... }` (inline-style-based) — but `i18n.js` **also** defines a global `function toggleLangMenu(){ m.classList.toggle('open') }` (class-based, since `.lang-menu.open{display:block}` in `style.css`). Because `i18n.js` loads via `<script defer>` **after** the page's own inline script, its declaration silently overwrites the page's local one at the same global name — so every actual click resolved to i18n.js's class-based version. That alone would be harmless (both mechanisms show the menu), except each of these 5 pages' own local outside-click handler was untouched and still did `langMenu.style.display='none'` directly — and an inline `style.display` **always** beats a CSS class rule for the same property. Net effect, reproduced and confirmed via CDP before fixing: **open the language menu once, click anywhere outside without picking a language, and the menu can never be reopened again for the rest of that page load** — every subsequent click on the language button silently does nothing, because the inline `display:none` set by the outside-click handler permanently overrides whatever the `open`/no-`open` class toggling does afterward. This is pre-existing and predates this refactor (the old `onclick="toggleLangMenu()"` attribute resolved to the exact same globally-overwritten function, so it was already broken in production) — not something the onclick→addEventListener conversion caused, just something its functional-testing step happened to surface by actually exercising the open→outside-click→reopen sequence, which no prior manual click-through apparently ever did. **Fixed** by deleting the 5 pages' now-fully-redundant local `toggleLangMenu()` (dead code, always overwritten anyway) and changing their outside-click handler to only manage `#ctyMenu` (which has no i18n.js equivalent and isn't affected by this collision) — `#langMenu` is now exclusively managed by i18n.js's own class-based toggle and its own matching outside-click handler, end to end. Verified via CDP: open→outside-click→reopen→outside-click→reopen again, 3 full cycles, works on all 6 hubs now (including `om`, unaffected but re-verified for regression). **If any other page is ever found defining its own local `toggleLangMenu`/`toggleCtyMenu`-style function that duplicates an i18n.js global name, check for this exact collision class before assuming it's fine — a same-named global always silently loses to whichever script declares it last.**

## CRITICAL, ACTIVE BUG — enforced CSP blocks ALL inline event-handler attributes site-wide, not just onclick — found 2026-09-16

**This is a live production regression, likely affecting a large number of calculators right now.** The 2026-09-14 onclick→addEventListener refactor project (documented at length above) was scoped to `onclick="..."` attributes only. But the CSP enforced the same day (see "CSP enforced in production" above) blocks **every** inline event-handler attribute — `oninput`, `onchange`, `onkeydown`, `onkeyup`, etc. — not just `onclick`. Per spec, `script-src` (with no separate `script-src-attr` directive) governs inline event-handler attributes too, and once a nonce is present the same graceful-degradation rule that lets nonce'd `<script>` tags ignore `'unsafe-inline'` also applies here — except **there is no way to put a nonce on an inline attribute**, so any page relying on `oninput`/`onchange`/etc. for its interactivity silently stopped working the moment CSP enforcement went live, with **zero console-visible error** in a normal check (confirmed only via a `document.addEventListener('securitypolicyviolation', ...)` listener, which reports `script-src-attr:inline` — this does not surface as a `Runtime.exceptionThrown` event, so none of this project's usual "0 JS errors" CDP checks would have caught it).

**Confirmed broken, live, via direct reproduction**: `jo/calculators/social-security/` (the existing, previously-shipped contribution calculator — `oninput="calc()"` on all 4 wage fields) and `jo/calculators/tawjihi-average/` were both directly confirmed non-functional in production via this exact test. Given `oninput`/`onchange` is a extremely common pattern across this codebase's calculators (used long before the onclick-specific refactor project existed), **this almost certainly affects many more pages than these two** — every calculator built with live-`oninput` recalculation (the pattern explicitly described as "most other live-`oninput` calculators sitewide" in the compound-interest/BMI discussion above) is a candidate. This was not caught by the original CSP-enforcement verification pass because that pass checked for `Runtime.exceptionThrown` and console-log CSP text, not `securitypolicyviolation` events specifically for `script-src-attr`.

**How to check a given page**: navigate to it, install `document.addEventListener('securitypolicyviolation', e => console.log(e.violatedDirective))`, then dispatch a real `input`/`change` event on one of its fields — `script-src-attr:inline` in the output means it's broken. A `new Function()`/console-error check alone will NOT catch this.

**Fixed so far** (2026-09-16): `jo/calculators/social-security-pension/` (built same session, caught before considering it shipped), `jo/calculators/social-security/` (user-reported live via a screenshot — see the dedicated section below), and `jo/calculators/tawjihi-average/` (fixed as an explicit follow-up request right after) — all converted from `oninput="calc()"` attributes to `element.addEventListener('input', calc)` wired in a `DOMContentLoaded` block. **The two specific pages this section originally named as confirmed-broken are now both fixed and live-verified** (`social-security/`: real screenshot values 800+100+50+100 JOD reproduced live, correct 971.250 JOD net; `tawjihi-average/`: the page's own worked example reproduced live, 85.07% — see that page's own note on a pre-existing, unrelated floating-point rounding quirk). **This does NOT mean the site-wide bug is closed** — only these 3 specific pages have been checked and fixed; the likely 50-150+ file scope described below has not been swept. Any other page using `oninput`/`onchange` for live recalculation should still be assumed broken until individually checked with the `securitypolicyviolation` method below.

**If this is picked up**: reuse the exact process already established for the onclick refactor (grep for `oninput=`/`onchange=`/`onkeydown=`/`onkeyup=` across all HTML, strip the attribute, add `element.addEventListener(eventType, handler)` in a plain script block positioned after the element in source order — no `DOMContentLoaded` wrapper needed if the script tag is already below the elements in the HTML, matching this project's own established convention, e.g. this file's own gender-toggle buttons and the fix above), then verify each fixed page with the `securitypolicyviolation`-listener method above (not just "no exception thrown"), functionally test via CDP that the calculator's result actually updates on input, push, and verify live via blob-sha diff. Given the likely scope, treat this as its own dedicated project, not something to fold into an unrelated task — flag it to the user before starting a full sweep given the size.
