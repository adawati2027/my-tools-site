## Lighthouse audit + real performance/a11y fixes — 2026-09-14

Ran Lighthouse via `npx --yes lighthouse@latest` against the live homepage (no npm dependency added to the repo — `npx` runs it ad hoc; a harmless `EPERM` temp-folder cleanup error appears at the end of every run on this Windows machine but the JSON report is still written correctly, don't treat that error as a failed run). This was the first real Core Web Vitals measurement done for this project.

**First run**: performance 45/100, LCP 6.4s, CLS 0.333, FCP 4.9s — all badly failing. Investigated rather than assuming the site itself was slow:

1. **Real CSP gap found**: `csi.gstatic.com` (an AdSense instrumentation beacon) was hitting the `connect-src` directive and getting blocked, a genuine gap in the CSP shipped earlier the same session — missing `https://*.gstatic.com` from `connect-src` (it was already in `script-src` for the Firebase SDK, but not `connect-src`). Fixed by adding it.
2. **Real render-blocking issue found and fixed**: `style.css` loaded Cairo via `@import url('https://fonts.googleapis.com/...')` — an `@import` inside a stylesheet can only be discovered *after* the browser fetches and parses that stylesheet, forcing a fully serial round-trip before text can render. **Self-hosted the font instead**: Google serves Cairo as a single variable-font file per Unicode subset (identical URL for every declared weight 300-900, confirmed by inspecting the returned `@font-face` CSS) — only 3 files needed (arabic/latin-ext/latin, ~81KB total), downloaded once into `/fonts/` and referenced from `style.css` with `font-weight: 300 900` ranges. This is a single-file change (style.css lives at repo root, so its own relative URLs resolve against its own location regardless of which nested page includes it — no per-page changes needed across any of the ~270 HTML files). Verified via headless Chrome that both subsets actually in use load correctly and `document.fonts.check(...)` resolves true before pushing.
3. **Real accessibility fixes**: `--text-muted` (`#64748b`) was 4.32:1 against its lightest background, just under the 4.5:1 WCAG AA minimum — darkened to `#5c6b83` (4.91:1, barely perceptible visually) as the single global variable rather than a scoped one-off, since it's used site-wide and darkening a muted gray can only help or maintain contrast against light surfaces (dark mode has its own separate `--text-muted` value, untouched). The `.fav-star` button (23×26px) was just under the 24×24px minimum touch-target size — fixed via `min-width`/`min-height: 24px` + flex-centering instead of relying on `padding` alone.

**Gotcha that ate significant time and is worth remembering**: after pushing the font fix, a second Lighthouse run showed almost no improvement (LCP even got slightly worse) — the network waterfall in the LHR JSON still showed `fonts.googleapis.com`/`fonts.gstatic.com` requests happening at all, meaning the fix visibly wasn't in effect. **Root cause: Cloudflare's edge cache was serving a stale `style.css` from before the fix, independently of the origin (GitHub Pages) already having the correct content** — confirmed via `curl -I` showing `cf-cache-status: HIT` with `Age: ~570s` and `Cache-Control: max-age=14400` (4 hours, longer than GitHub Pages' own native `max-age=600`). **Correction, found the same night**: an earlier version of this note claimed HTML pages are exempt (`cf-cache-status: DYNAMIC`, uncached) and only static assets (`.css`/`.js`) are at risk. **That's wrong — it was only true for the specific homepage request checked at the time.** Re-checked later the same session and found `file-converter.html` sitting at `cf-cache-status: HIT` after a real edit (the pdf.js CVE fix below), serving stale content the same way `style.css` had. **The real pattern: Cloudflare caches per-URL lazily on first request — a URL shows `MISS` until something (a visitor, a test script, Lighthouse) fetches it, then it becomes `HIT` and stays stale-able for the same ~4-hour Edge TTL as any other file, regardless of content-type.** This applies to *any* file now that Cloudflare proxies the site — HTML included — not a `.css`/`.js`-specific risk. Fixed for this incident the same way (manual Purge Everything). The **Cache Rule** ("Respect origin TTL") set up earlier the same session should shorten this window going forward for everything, not just the two files originally suspected. **Lesson, corrected: after *any* push now that Cloudflare is in front of the site — HTML pages included, not just CSS/JS — verify with `curl -I <url>` that `cf-cache-status` isn't serving something stale (check both `Age` and the actual response body) before trusting a live re-test. A bad-looking result, or a fix that "isn't taking effect," may be a caching artifact rather than a real regression or failed push.** Note: the Cache Rule only affects Cloudflare's *edge* cache duration; the `Cache-Control` value actually sent to visitors' own browsers is a separate "Browser Cache TTL" setting, not changed by this fix — lower priority, noted but not addressed this session.

**Final numbers after the fix + cache purge**: performance 45 → **96**, LCP 6.4s → **2.0s** (passes), CLS 0.333 → **0.05** (passes), FCP 4.9s → 2.0s, TBT 180ms → 110ms. Re-ran both `test-calculators.js` (20/20) and `test-e2e.js` (29/29) after the CSS changes as a regression check — both still fully pass.

**Remaining Lighthouse findings, not fixed this session** (lower priority / require a real decision, not a quick correctness fix): "Uses third-party cookies" (AdSense's own `test_cookie` on `doubleclick.net` — inherent to running AdSense at all, not fixable without removing ads); "Links are not crawlable" (the `#langMenu a[data-lang="ar"]` etc. links have no `href` at all — pre-existing from before this session's onclick-refactor work, not a regression from it, since they never had an href even with the old `onclick=` attribute; a real href isn't trivial to add without changing the JS-driven language-switch behavior); "Heading elements are not in a sequentially-descending order" (a footer `<h4>` with no preceding `<h2>`/`<h3>` on the page — pre-existing, minor); "Issues were logged in the Issues panel" (generic Chrome DevTools diagnostic, not investigated further this round).


## Dependency vulnerability scan + repo-level security review — 2026-09-14

No `package.json`/`node_modules` exists in this repo (by design), so there's no dependency tree for `npm audit` to walk — but the site does load several pinned third-party libraries via CDN `<script src>` tags, and those version pins are exactly the kind of thing a "dependency scan" should actually check. Enumerated every one site-wide and checked each against known CVEs (WebSearch, not `npm audit`):

- **Firebase JS SDK 10.13.2** — checked against CVE-2024-11023 (FIREBASE_DEFAULTS cookie hijack, fixed in 10.9.0). **Not affected** — pinned version is newer than the fix.
- **pdfjs-dist 3.11.174** (file-converter.html, PDF→text/Word/image conversion) — **CVE-2024-4367, CVSS 8.8, real and fixed.** Arbitrary JS execution from a crafted PDF when `isEvalSupported` is true (the default) — fixed upstream in 4.2.67+. Directly relevant here since this tool exists specifically to process user-supplied PDFs. Rather than a major-version CDN bump (3.x→4.x, real API-breakage risk without dedicated testing), applied the documented workaround: added `isEvalSupported: false` to all 3 `pdfjsLib.getDocument({data:ab})` call sites. **Verified the fix doesn't break real functionality** — generated a minimal valid PDF, loaded pdf.js fresh, called `getDocument` with the new option, and confirmed text extraction still returns the correct content.
- **xlsx (SheetJS) 0.18.5** (file-converter.html, Excel conversion) — **CVE-2023-30533 (Prototype Pollution) + CVE-2024-22363 (ReDoS), both real, found but NOT fixed this session.** Both require "reading a crafted file," which this tool's whole purpose is (user uploads arbitrary spreadsheets) — but this is 100% client-side with no server involved, so a malicious file at worst breaks the *uploading user's own tab*, not the site or other users; not in the same severity class as the pdf.js finding. **No safe upgrade path currently exists via the CDN this site already uses**: the `xlsx` npm package is unmaintained as of the vulnerable 0.18.5 (confirmed — `cdn.jsdelivr.net/npm/xlsx@0.19.3/...` 404s, jsDelivr mirrors npm and npm was never updated); the only fixed build (0.19.3+) is hosted on the maintainer's own `cdn.sheetjs.com`, a domain not currently in this site's CSP `script-src` allowlist and not used anywhere else on the site. Fixing this properly means adding a new CDN provider to the CSP, confirming the newer API is still compatible with how this page calls it, and testing the whole Excel-conversion flow — a real task, just not a quick one. **Left as a known, documented, low-urgency gap** rather than rushed.
- **mammoth 1.6.0** (file-converter.html, Word conversion) — CVE-2025-11849 (Directory Traversal via a docx's external image link, fixed in 1.11.0) exists for this version range, but the vulnerability's mechanism is reading arbitrary **local filesystem** paths on the machine running mammoth — not applicable in a pure browser context (no filesystem to traverse into the way the CVE describes). Assessed as **not exploitable in this site's actual deployment**, not upgraded.
- **jsPDF 2.5.1**, **html2canvas 1.4.1** — checked, no CVE found that's both current and clearly applicable to this site's browser-only, non-Node usage pattern.

**Repo-level security spot-check**: confirmed `.env` (holding `GITHUB_PAT`) is the only credential-like file in the tree, confirmed it's excluded from every push by `push-to-github.js`'s own dotfile-exclusion logic, and confirmed the PAT is never logged anywhere in that script. Combined with the earlier homepage `innerHTML`/`eval`/`document.write` review (see the CSP section above) and the fact that `test-calculators.js`/`test-e2e.js` both passed clean throughout tonight's changes, this closes out the "repository-level security review" item at a reasonable depth for this session — a full line-by-line audit of all ~270 pages was not attempted.


## Full repository security review — 2026-09-14, completes the previously-incomplete item

User said "all of them" to three previously-deferred items (CSP hardening, long-tail SEO content, full repo security audit) after the onclick refactor closed out. This is the security-audit portion — a genuinely deeper pass than the earlier spot-checks documented above, going beyond the homepage-only review.

**Dangerous JS sinks, site-wide (not just homepage)**: `eval()` — 1 file matched, `test-e2e.js`, but it's a false positive: the match is this project's own test-helper method named `.eval()` (a thin wrapper around a CDP `Runtime.evaluate` call), not JavaScript's global `eval()` — confirmed by reading every match, and irrelevant regardless since `test-e2e.js` is a local-only tool, never deployed inside any `<script>` tag on any page. `new Function()` and `document.write()` — 0 matches anywhere in the repo. `innerHTML` — 198 files use it (expected, this is the project's standard DOM-update pattern), but the two genuinely dangerous *sub-patterns* were specifically checked rather than trying to manually review 198 files: (1) URL-parameter reflection into `innerHTML` (`location.search`/`location.hash`/`URLSearchParams` feeding into `innerHTML` — the classic reflected-XSS vector) — **zero matches anywhere on the site**; (2) a text-type user input's raw `.value` flowing into `innerHTML` unescaped — found 52 candidate files (mostly lang-variant duplicates of ~15 underlying pages: the 5 leaderboard mini-games, `currency-converter.html`, the country hubs' search box, `kids-spelling`/`kids-typing`, `jo/calculators/university-gpa`), all checked and **all correctly escape user text before insertion**: the 5 leaderboard games (`car-game`/`jump-game`/`memory-game`/`number-guess`/`quick-math`/`reaction-test`) each define an identical local `esc()` helper (`&`/`<`/`>` replaced) applied to the player's saved name before it's templated into the local-only `localStorage` leaderboard's `innerHTML`; `jo/games/quiz-engine.js`'s **multiplayer** leaderboard and challenge-intro text (real player names read from shared Firestore, visible across different real users — the higher-stakes case) use a more complete `escapeHtml()` helper (`&`/`<`/`>`/`"`/`'`, i.e. also attribute-safe, not just element-safe) applied consistently to every Firestore-sourced name (`creatorName`, leaderboard `d.name`) before HTML insertion; `accepterNameSpan` uses `.textContent` instead (inherently safe, no HTML parsing, no escaping needed). No injection gap found in this whole class of risk.

**Secrets**: `.env` (holding `GITHUB_PAT`) reconfirmed excluded from every deploy (dotfile-exclusion logic in `push-to-github.js`'s `collectFiles`, allowlist is only `.well-known`+`.nojekyll`) and reconfirmed genuinely inaccessible live — `curl` both `https://adawati.space/.env` and the raw GitHub content URL for it, both 404. **Went further this round: queried GitHub's own native secret-scanning API** (`/repos/{repo}/secret-scanning/alerts`), which scans the *entire* commit history (1161 commits on `my-tools-site`), not just the current tree — a real answer to the "Git history secret scan" item this file has listed as incomplete since the first repo-security spot-check. Result: **exactly one alert, on both repos combined** — the Firebase web API key (`AIzaSyAO8Z...`), flagged in `my-tools-site` only, `adawati-app` came back with zero alerts. This is the *same* key already documented throughout this file as intentionally public (Firebase's own security model: web API keys identify the project, they don't grant access — access control lives entirely in Firestore security rules, which are the actual thing worth securing and which this file already documents in detail). GitHub's generic scanner has no way to know that semantic distinction, so it flags any Google-API-key-shaped string regardless of whether the specific key type is meant to be public. **Left the alert open rather than dismissing it myself** — dismissing a security alert is a posture decision for the account owner, not something to do unilaterally even when confident it's a false positive for this specific key type; flagged it to the user with the recommendation instead.

**Real, actionable gap found and fixed**: none of the site's external `<script src>` tags used Subresource Integrity (SRI). Checked which ones actually *can* — Google's GA (`gtag.js`) and AdSense (`adsbygoogle.js`) scripts are **not** SRI-able by design (Google explicitly serves these unversioned and updates them server-side without a version-pinned URL, so a hash would break on Google's next update, not ours — matches the "intentionally unversioned by Google design" note already in this file), but the two **version-pinned** Firebase SDK scripts (`firebase-app-compat.js`/`firebase-firestore-compat.js`, both pinned to `10.13.2`, static `<script src>` tags on all 15 `jo/games/*` pages) are exactly the case SRI is meant for — a version-pinned CDN URL's content is immutable once published. **Fixed**: computed real `sha384-` hashes (`openssl dgst -sha384 -binary <file> | openssl base64 -A` against the actual downloaded files, not guessed/copied from anywhere) and added `integrity="sha384-..." crossorigin="anonymous"` to both tags on all 15 pages (both attributes are required together — `integrity` without `crossorigin` makes the browser treat a genuinely cross-origin request as same-origin mode, which fails silently). **Verified before AND after pushing**: a local headless-Chrome test confirmed both scripts still load and `firebase`/`firebase.firestore` are defined with the hashes in place (this is exactly the kind of change that fails *silently* if the hash is wrong — no thrown JS error, the script just never executes — so existence-checking `typeof firebase` after load, not just absence of console errors, was the right verification), then re-verified the identical check against the live production URL after the push landed.

**Other checks, all clean, nothing to fix**: no open-redirect pattern (`location.href`/`location.replace` driven by a URL param) found anywhere; repo confirmed `public` (expected for a GitHub Pages site, not itself a finding); Firestore security rules already documented in detail elsewhere in this file, not re-litigated here.

**Still not done, and honestly assessed as not worth doing given the effort/value tradeoff at this site's scale**: a true line-by-line read of every one of ~306 HTML/JS files. The approach taken instead — systematic pattern-based scanning for the specific dangerous sink classes (URL-reflection, unescaped-input-to-innerHTML, eval-family, hardcoded secrets, missing SRI, open-redirects) across the *whole* repo rather than a sample — covers the realistic threat surface for a static, no-backend, no-user-auth-cookies site far more effectively than an unfocused manual read-through would, and is the same methodology this file already used successfully to close the earlier `currency-converter.html` bug and the onclick-refactor's own bug-classes. Treat this as the repo-security item being **closed at a reasonable, threat-model-appropriate depth**, not deferred.


## xlsx (SheetJS) CVE fix — self-hosted instead of a CDN-allowlist change, 2026-09-14

Closed the `xlsx` gap left open in the 2026-09-14 dependency-scan section above (CVE-2023-30533 prototype pollution + CVE-2024-22363 ReDoS, both in the pinned 0.18.5 build `file-converter.html` loaded from jsDelivr). That section's note assumed the fix just needed adding `cdn.sheetjs.com` to the CSP `script-src` allowlist — **re-verified before acting and found two things wrong with that plan**: (1) the actual fixed versions are 0.19.3 (prototype pollution) and **0.20.2** (ReDoS) — 0.19.3 alone, as the old note said, still leaves the ReDoS bug open; confirmed via WebSearch against the CVE advisories directly, not trusted from memory. (2) **Adding a new domain to the Worker's CSP wouldn't actually have worked**, given the still-open duplicate-CSP-header situation documented in the CSP-hardening section above: the old Cloudflare Transform Rule fires *in addition to* the Worker and uses an "Add" action (confirmed by the earlier finding that both a nonce'd and non-nonce'd `Content-Security-Policy` header arrive in the same response) — since CSP combines multiple headers with AND-semantics, a resource needs the domain allowed in *both* policies, and the Transform Rule's copy isn't editable (no Cloudflare Rulesets write access, same blocker documented in that section). Editing only the Worker's policy would have silently failed to unblock the new CDN.

**The actual fix sidesteps this entirely**: downloaded the real, verified 0.20.3 build (latest stable, past both CVE fixes) directly from `cdn.sheetjs.com` (sanity-checked: real SheetJS file header comment, correct embedded `version="0.20.3"` string, 952KB — not an error page), and **self-hosted it** at `vendor/xlsx-0.20.3.min.js` instead of loading from any external CDN. Since the site's own origin (`'self'`) is already allowed by both CSP policies, this needed **zero CSP changes at all** — a strictly simpler fix than the CDN-allowlist plan, and one that isn't blocked by the Transform Rule access gap. `vendor/` is a new top-level directory (this project's first self-hosted third-party JS library — `fonts/` was the only prior precedent for a self-hosted external asset). Only `loadXlsx()` in `file-converter.html` changed, from the jsDelivr URL to the relative `vendor/xlsx-0.20.3.min.js` path (resolves correctly via the page's `<base href>` regardless of nesting depth, same as every other relative link on the site).

**Verified real API compatibility, not just "it loads"**: this page uses exactly 4 SheetJS calls (`XLSX.read`, `XLSX.write`, `XLSX.utils.sheet_to_csv`, `XLSX.utils.sheet_to_json`) — all long-stable Community Edition APIs unchanged across the 0.18→0.20 range. Confirmed via a live CDP test against production: built a real workbook in-memory (`book_new`/`aoa_to_sheet`/`book_append_sheet`/`write`), read it back (`XLSX.read`), and converted to both CSV and JSON — data round-tripped exactly (`{Name:'Ahmed',Score:95}` survived the full write→read→sheet_to_json cycle unchanged), confirming `XLSX.version === '0.20.3'` was actually the code running, not a cached/stale reference. `test-calculators.js` re-run clean afterward as a broader regression check.

**Push note**: the new `vendor/` directory hit the same "GitHub Pages build lag for brand-new paths" pattern already documented elsewhere in this file (git tree confirmed correct via blob-sha diff immediately, but the live URL 404'd for ~20-30s before the Pages build caught up) — don't assume a failed push if a *new path* 404s right after pushing, same as the daily-info-modules and gold-price sections above already found.

**mammoth (Word conversion)** and **pdf.js** remain as documented in the earlier dependency-scan section (mammoth's CVE not applicable in a browser context; pdf.js already patched via the `isEvalSupported:false` workaround) — this fix only touched xlsx. If jsPDF/html2canvas or any other pinned CDN library is ever found to have a real CVE with no fixed build on its existing CDN, check for a maintainer-run CDN with the patched version first (as here) before assuming a CSP-allowlist change is required — self-hosting under `vendor/` avoids the CSP/Transform-Rule complication entirely for any future case like this.


## Performance/accessibility re-check, 2026-09-15

Continuing the "enhance and fixes" general audit into performance/accessibility, per explicit user request.

**Apparent performance regression investigated and ruled out as a false alarm**: a fresh Lighthouse run on the homepage showed Performance 68-69/100 and LCP 5.8-7.1s — a big drop from the 96/2.0s recorded 2026-09-14. Confirmed reproducible across 2 consecutive runs (not random noise), but neither `index.html`, `style.css`, nor `i18n.js` had been touched since 9/13-9/14 (file mtimes checked directly) — ruling out any of this session's edits as the cause before investigating further. **Root-caused via a controlled comparison**: re-ran Lighthouse with `--blocked-url-patterns` excluding `*googlesyndication*`/`*googletagmanager*`/`*doubleclick*` — score jumped back to 94, LCP dropped to 2.9s, TBT from 90-140ms to 10ms. **Conclusion: 100% Google AdSense/ad-network real-time-loading variance** (which ad creative loads, real-time bidding latency — inherently different every page load) — not a site regression, not something to "fix" (removing ads isn't on the table, and this variance is a known, accepted characteristic of running AdSense, already noted elsewhere in this file re: "third-party cookies" being unavoidable while ads are running). **Lesson for future performance re-checks on this site: always run one comparison with ad/analytics domains blocked before concluding a score change is a real regression** — a live ad-supported page's Lighthouse score is expected to fluctuate significantly run-to-run for reasons entirely outside this codebase's control.

**Real accessibility bug found and fixed**: Lighthouse flagged `color-contrast` again (score 0) despite the `--text-muted` variable already being darkened to `#5c6b83` on 2026-09-14 specifically to fix this class of issue. Investigation found the **footer** (`.footer`, permanently dark background `#0f172a` in light mode / `#010409` in dark mode, independent of the site's light/dark toggle) used **6 hardcoded literal colors** (`#64748b` ×4, `#475569` ×2 — in `.footer-brand-block p`, `.footer-col a`, `.footer-copy`, `.footer-langs span`, `.footer-copy-simple`) that were never touched by the earlier fix since they don't reference the `--text-muted` variable at all. Contrast ratios: `#64748b` vs `#0f172a` = 3.75:1, `#475569` vs `#0f172a` = 2.36:1 — both fail the 4.5:1 WCAG AA minimum for normal text. **This affects the footer on every single page site-wide** (`.footer-copy-simple` is the shared simple-footer class used on essentially all ~300 tool pages, not just the homepage), so this was a much bigger-reach bug than a homepage-only issue. **Fixed**: replaced all 6 occurrences with `#8492a6` (computed via the WCAG relative-luminance formula: 5.65:1 against the light-mode footer background, 6.50:1 against the dark-mode one — comfortable margin above 4.5:1 in both cases, verified by calculation before applying, not guessed). Verified via a second Lighthouse run: accessibility 92 → 98, `color-contrast` fully resolved. **Lesson: a CSS-variable-based contrast fix only reaches the elements that actually reference that variable — always grep for hardcoded literal hex colors matching the old failing value site-wide before considering a contrast fix complete, since a component styled with a literal color (like this project's footer) silently bypasses any variable-based fix entirely.**

**Remaining accessibility finding, pre-existing and already documented, not re-investigated**: `heading-order` (a footer `<h4>` with no preceding `<h2>`/`<h3>` on the page) — same minor, low-priority item noted in the original 2026-09-14 Lighthouse section of this file.

**Verification**: CSS brace-balance checked before pushing (242/242). `style.css` itself failed to blob on the first full-tree push attempt (usual secondary rate-limit pattern) and needed the targeted single-file push script — confirmed via blob-sha diff before considering it live. Re-ran `test-calculators.js` (20/20) and `test-e2e.js` (29/29) after the fix — one `test-e2e.js` run hit a single flaky failure (`no console/runtime errors on /jo/games/logo-quiz/`), reproduced-and-cleared on an immediate re-run with a fresh direct CDP check finding zero actual console errors — confirmed as transient (likely a momentary network blip loading one of the many logo-quiz images), not a real regression from the CSS change, before moving on.


## Security deep-dive, 2026-09-15

Continuing the "enhance and fixes" audit into security, per explicit user request, after the performance/accessibility pass above. Re-ran the established dangerous-sink scan (`eval`, `document.write`, `new Function`) fresh across the whole repo — same clean result as the 2026-09-14 pass (only the known `test-e2e.js` `.eval()` method-name false positive). Checked for mixed content (hardcoded `http://` resource references) — 2 hits, both false positives (XML namespace URI strings inside `build-sitemap.js`'s sitemap-schema declaration and `vendor/xlsx-0.20.3.min.js`'s internal Office-format namespace constants, neither is a fetched network resource). Reconfirmed `.env` still returns 404 live and the goldprice.dev API key (`ga_live_...`) does not appear anywhere in the repo — it only exists as a Cloudflare Worker secret, as originally set up.

**Real, if modest, finding: the `/api/gold-fallback` Worker endpoint had zero caching or rate-limiting and was publicly reachable without auth**, calling a paid, API-key-authenticated third-party service (`api.goldprice.dev`) on every single hit — `Cache-Control: no-store` on its own response meant nothing prevented a bot or deliberate prober from spamming this endpoint and exhausting the goldprice.dev API quota, an availability/cost risk (not a data-exposure risk — the currency query parameter was already confirmed safe against injection, since it's only ever used as a plain object-key lookup into the exchange-rate response, never interpolated into a URL or command). **Fixed**: added Cloudflare's `caches.default` Worker-level cache (keyed on origin+pathname+normalized currency) with a 60-second TTL, only caching genuine 200 responses (never the 502 error path, so a transient goldprice.dev outage doesn't get needlessly cached) — this both protects the API quota and naturally rate-limits repeated hits for the same currency without needing real authentication infrastructure, which wasn't worth building for a low-traffic fallback-of-a-fallback endpoint. Deployed via `wrangler deploy` (established CLI method for this Worker, not the dashboard editor). **Verified live**: two consecutive requests for the same currency returned byte-identical prices (confirming the second was genuinely served from cache, not a fresh API call) with `CF-Cache-Status: HIT` on the second; Cloudflare's own edge cache picked up the `Cache-Control: public, max-age=60` header too and applied its own (longer, Cache-Rule-governed) TTL on top — a harmless, even more protective side effect, not a bug, since gold-price data freshness at the minute-to-minute level was never a real requirement for this already-approximate fallback source. Confirmed the Worker's primary CSP-nonce functionality is completely unaffected post-redeploy (checked fresh unique nonces + correct CSP on 4 different page types), and re-ran `test-calculators.js` (20/20) + `test-e2e.js` (29/29) clean.

**Other checks, all clean, nothing to fix**: Firestore security rules (already documented in detail elsewhere in this file, not re-litigated), SRI on the Firebase SDK scripts (already in place from 2026-09-14), the single known/accepted GitHub secret-scanning alert (the intentionally-public Firebase web API key) unchanged. This closes the security-deep-dive portion of this session's general audit at a reasonable, threat-model-appropriate depth for a static site with one small serverless endpoint — a full line-by-line Worker/Firestore-rules re-audit wasn't repeated since nothing has changed there since the 2026-09-14 review beyond this one endpoint.
