# Fixed content/UX bugs — reference so they are not reintroduced

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## Known content/UX bugs already fixed this project (don't reintroduce)

- **Oman-only tool cards (salary-calculator, end-of-service, and on us/uk also vat-calculator + hijri-converter) were visible on every country hub and the global homepage** — user-reported 2026-09-14 via a screenshot showing `end-of-service.html` (explicitly Omani-labor-law content, "سلطنة عُمان" in its own title) reachable from the Jordan hub. Root cause: `index.html`/`jo/ae/sa/us/uk/index.html` each carried leftover `data-cat="oman" style="display:none"` cards (copy-pasted from `om/index.html`'s template, which is where these tools legitimately belong un-hidden), intended to stay permanently hidden since none of these 6 pages has a selectable `"oman"` tab — but each page's own `filterTools()` has `catMatch = !!q || activeCat==='all' || card.dataset.cat===activeCat`, and `activeCat` defaults to `'all'`, so `catMatch` is `true` for every card regardless of `data-cat` the moment the page loads, and `card.style.display = show?'':'none'` overwrites the original inline `display:none` — unhiding them unconditionally, not just during search. Fixed by deleting the leftover cards entirely from all 6 pages (they can never be legitimately reached via any real tab there, so keeping them served no purpose and was just a latent bug) rather than patching the shared `filterTools()` logic — lower risk, and `om/index.html` itself was unaffected (it shows these tools normally, by design, no hidden-card hack needed there). **If a future country hub is built by copying another hub's template, strip any `data-cat="X" style="display:none"` card whose `X` isn't one of that new page's own real tabs** — this exact pattern will silently reintroduce the same bug, since `filterTools()`'s `activeCat==='all'` default always exposes every card in the DOM regardless of category on initial load.
- Country-recommendation widget (`i18n.js`) used to freeze in the wrong language after switching site language via the dropdown — fixed by making `initCountryDetect()` actually write `sessionStorage.adawati_country` on the path-based detection branch (it only did this on the IP-geolocation fallback before).
- Zakat calculator: the "your gold is above nisab by X grams" info line was worded in a way users mistook for the zakat amount owed (it's just a weight-threshold note, unrelated to the actual JOD zakat figure computed separately). Reworded to remove the misleading number entirely.
- Wordle-style daily word game (`jo/games/wordle/`): the on-screen keyboard was missing the letter **ذ**, silently making any word containing it (e.g. "نافذة") impossible to guess. Fixed by adding it to `KEY_ROWS`. If adding more words to `WORDS`, validate every letter exists in `KEY_ROWS` first (script pattern used: build a `Set` from `KEY_ROWS.flat()`, check every char of every word is in it) — the keyboard still has **no key for أ/إ/آ** (only bare `ا` and the hamza forms `ء ئ ؤ`), so words must avoid those combined glyphs.
- The word-of-the-day mechanism was already correctly implemented before I was asked to add it (`dayIndex()` — deterministic by UTC date, same word for all visitors each calendar day) — don't rebuild it, just keep `WORDS` long enough that the cycle-repeat period stays reasonable (currently 129 words ≈ 4+ months before repeating).
- Cross-country navigation bug: visiting a shared/generic tool page (e.g. `bmi-calculator.html`) from a country hub (`/jo/`, `/om/`, etc.) used to force English and make the "Back to Home" links (both the floating prompt and the static per-page link) always point to the generic `/index.html` instead of back to the country hub. Root cause: `detectDefaultLang()` in `i18n.js` discarded country context on root-level pages. Fixed by having it check `sessionStorage.getItem('adawati_country')` (already set by `initCountryDetect()`) before falling back to English, and by adding `getHomeHref()`/`fixBackLink()` helpers that make both back-link mechanisms country-aware. No changes needed to the hundreds of individual tool pages — the fix works by rewriting `href` via JS on load.
- Multiplayer challenge "قبول التحدي" button had no disabled-state guard — tapping it multiple times while the async join was still in flight created duplicate accept records (user-confirmed real bug, felt like the button was "stuck"). Also, the capacity-check read at the top of `joinChallenge()` wasn't wrapped in try/catch — a transient network error there left the button permanently disabled with no error shown and no way to retry short of a page refresh. Both fixed 2026-09-07: the button now disables immediately on click, and the whole function body is wrapped in try/catch with a "جرب تاني" alert on failure that re-enables the button. Separately, a late joiner accepting *after* the creator had already clicked "ابدأ اللعب" used to wait on a `listenForStart()` Firestore round-trip; `joinChallenge()` now checks the `starts` collection directly right after joining and jumps straight into the quiz if already started, no waiting screen.
- Sitemap `lastmod` dates were a hardcoded string in `build-sitemap.js` (`const TODAY = '2026-09-02'`) that silently went stale on every subsequent regeneration — flagged by an external QA pass 2026-09-07. Fixed by making `TODAY` compute `new Date().toISOString().slice(0,10)` at build time instead, so it's always accurate for whenever `node build-sitemap.js` actually runs.
- Multiplayer join had a client-side-only capacity race condition (`accepts.size() + 1 >= MAX_PLAYERS` checked, then written, as two separate un-atomic steps — simultaneous joins right at the cap could theoretically exceed it). Fixed 2026-09-07 by adding an `acceptedCount` counter field to the challenge doc and a Firestore security rule that only allows updating it as an atomic +1; `joinChallenge()` now uses `db.runTransaction()` to check-and-increment it together with creating the `accepts` doc. See the Firebase/Firestore section above for the exact rule and the transaction code.
- Every `jo/games/*` page's static "→ العودة لأدوات الأردن" back-link and was hardcoded to `href="jo/"` — harmless while games were only linked from `/jo/`, but became a real bug once the challenges module was added to every other country hub (`om/`, `ae/`, `sa/`, `us/`, `uk/`): a user reaching a game from `/om/` would hit "back" and land on `/jo/` instead of `/om/` (user-reported). First fix attempt (2026-09-07) gave the link `data-i18n="back"` expecting `i18n.js`'s existing `fixBackLink()`/`getHomeHref()` to handle it automatically — **this was inert**, because `jo/games/*` pages don't load `i18n.js` at all (confirmed via `grep -c "i18n.js"` = 0). Actually fixed by building a self-contained replacement inside `quiz-engine.js` itself — see "In-page English translation system" below. `data-i18n="back"` is harmless leftover markup on these pages (does nothing, not wrong) since nothing processes it there; the real fix is `qGetHomeHref()` + `applyQuizTranslations()` setting the link's `href`/text directly. Applied to all 15 `jo/games/*` pages including `wordle/`; `wordle/` needed a separate minimal fix since it uses neither `i18n.js` nor `quiz-engine.js` — a tiny standalone inline `<script>` right after the back-link (2026-09-07) reads `sessionStorage.getItem('adawati_country')` and sets the `href` directly, same country-code map as `qGetHomeHref()`/`i18n.js` but not sharing code with either (wordle is small enough that duplicating the ~5-line lookup was simpler than wiring in a dependency).
- Global homepage (`index.html`) was missing the "🏆 Challenges" tab and all 13 trivia game cards entirely (user-reported 2026-09-07: "In global page the challenge button not exist") — the module had been added to every country hub (`jo/om/ae/sa/us/uk`) but never to the generic global page. Fixed by adding the tab + the same 13 English game cards used on `ae/us/uk`.
- Mixed-language bug on `jo/index.html` (user-reported via screenshot, 2026-09-07): switching the site language to English left the hero subtitle, hero badges, and 6 of the page's category tabs (`jo-education`/`challenges`/`taxes`/`decisions`/`cars`/`daily`) still in Arabic, because those elements had no `data-i18n` attribute at all (i18n.js's `applyTranslations()` only touches elements with `[data-i18n]` — an element without one, or with a key missing from `T[lang]`, is silently left unchanged, see the `if (t[k] !== undefined)` guard). Separately, the `<h1>` had `data-i18n="hero_title"` — the *generic global* tagline key — producing an off-topic English string instead of Jordan-specific copy. Fixed by adding dedicated `jo_hero_title`/`jo_hero_sub`/`jo_hero_label`/`jo_badge_loan`/`jo_badge_free` keys plus `cat_kids`/`cat_jo_education`/`cat_challenges`/`cat_taxes`/`cat_decisions`/`cat_cars`/`cat_daily` to `i18n.js` (ar+en only, matching the "English only for now" scope already established for the trivia project — fr/es/de/ru intentionally left unset, same graceful no-op fallback as before) and wiring `data-i18n` onto every previously-bare element. Also retrofitted the "🏆 Challenges" tab on `om/sa/ae/us/uk/index.html` and the global `index.html` to use the new shared `cat_challenges` key instead of hardcoded text (om/sa were missing the key entirely; ae/us/uk/global had hardcoded English that wouldn't have reverted correctly if a user switched those pages to another language). **If a new Jordan-only (or any country-only) section/tab is added to a hub page in the future, always give it a `data-i18n` key from the start** — this bug happened because several tabs were added over time without one.
- Service worker (`sw.js`) precached a hand-maintained `STATIC` list that didn't include new `/jo/` pages as they were added, so they worked online but weren't available offline until a viewer happened to load them once first. Fixed 2026-09-07: the `install` handler now also fetches `sitemap.xml` and precaches every `/jo/` URL listed in it, so new pages get offline support automatically the next time `build-sitemap.js` + a cache-version bump ship together — no manual list maintenance needed for that part. Bump `CACHE` in `sw.js` (currently `adawati-v58`) whenever `sw.js` itself changes.
- **`quiz-engine.js` was being served stale indefinitely to returning visitors** — `sw.js`'s fetch handler treats it as a generic "static asset" (cache-first: serve from cache if present, never re-check network, cache whatever comes back the one time it does fetch), same bucket as images/fonts. Every edit made to `quiz-engine.js` this session (the translation system, `restart()` behavior, the join-button fixes, the atomic-transaction fix, the logo-quiz image support — all of it) was invisible to anyone whose browser had already cached an older copy, with no way to self-correct short of a full cache-version bump. This is how the logo-quiz "images not showing" report turned out to be a red herring at first look: the reporting device was still running a *pre-image-support* cached `quiz-engine.js`, confirmed by reproducing it live — `navigator.serviceWorker.getRegistrations()` found an active registration and `caches.keys()` found 2 caches; unregistering + clearing them and reloading immediately showed the correct current-code behavior. Fixed two ways 2026-09-07: (1) bumped `CACHE` to force every existing cache to be dropped once (`activate` deletes all caches whose key ≠ current `CACHE`, and `skipWaiting()`/`clients.claim()` are already in place so this takes effect on next load without waiting for tabs to close) — a one-time catch-up for everyone already stale; (2) moved `quiz-engine.js` into the same **network-first** `isCore` bucket as `i18n.js`/`style.css` (`url.pathname.endsWith('/quiz-engine.js')`) so this class of bug can't recur — every future edit to it reaches visitors on their very next load, no manual cache-version bump needed for *this specific file* going forward. **Lesson: any shared JS file under active iteration must be network-first in `sw.js`, not cache-first — cache-first is only safe for files that don't change, or where you will remember to bump `CACHE` on literally every edit.** If a browser-tool check of a live page ever shows behavior that contradicts the code you just read/pushed, suspect this before assuming the push failed — check `navigator.serviceWorker.getRegistrations()` / `caches.keys()` in that tab.
- Logo-quiz images ultimately also had a real (separate, smaller) bug once the stale-cache issue above was ruled out: `getQuestionImageEl()` sized the `<img>` with CSS `max-width`/`max-height` only, no explicit `width`/`height` attributes on the element itself. Some Commons SVGs render at 0×0 in that setup — the element has nothing to establish an intrinsic box from before the max-constraints apply, so it can collapse to zero and take up no visible space at all (not a broken-image icon, no layout gap, genuinely invisible). Fixed by setting explicit `el.width = 220; el.height = 140` alongside the CSS. Verified live post-fix by creating an `<img>` with the exact same attributes/CSS via `javascript_tool` and confirming `naturalWidth`/`naturalHeight`/`offsetWidth`/`offsetHeight` all resolved correctly and a screenshot showed the logo rendering. If any future `<img>`-based feature is added anywhere on the site, give it explicit `width`/`height` attributes as a matter of course, not just CSS sizing.
- **Challenge creation was broken for every game except logo-quiz** since the `img` field was added to questions (2026-09-07) — `pickQuestions()` in `quiz-engine.js` always set `img: q.img` on every question object it built, so for the 14 non-logo-quiz games (whose source questions have no `img` field at all) this became `img: undefined`. Firestore's JS SDK **rejects any field with an `undefined` value** (`db.collection('challenges').add(...)` throws), so `createChallenge()`'s catch block silently showed "صار خطأ بإنشاء التحدي" for every single challenge creation attempt on those 14 games — user-reported 2026-09-09 via a screenshot of the error on Animals & Nature Quiz. `loadQuestion()` already handled a missing `img` fine (`if (q.img) {...}`), so the fix was just making `pickQuestions()` omit the key entirely when absent instead of always setting it (`if (q.img) item.img = q.img;`) rather than adding `img: q.img || null` or similar — matches the existing no-op-when-absent pattern used elsewhere in this file.
- "🔄 جرّب مرة ثانية" (Try Again, shown on the result screen) used to replay the *same locked challenge* — same 12 questions, same `challengeId`, same shareable link — because `restart()` skipped `pickQuestions()` whenever `challengeMode` was true, which by the current group-challenge architecture is *always* true once you reach the result screen (single-player mode was removed entirely earlier this session, so there's no other path to `resultArea`). User-reported 2026-09-07 ("لما تكبس جرب مرة اخرى بلش صفحة جديدة من دون اسئلة وزي كأنو دخل من الاول ويعمل شير" — Try Again should start fresh, as if arriving for the first time, with a new share). Fixed by collapsing `restart()` to a single `location.href = location.origin + location.pathname` — a full reload of the bare game URL, landing back on the "ابدأ تحدي" creation screen (new name entry, new `createChallenge()` call, new `challengeId`, new shareable link, needs a friend to accept again before playing). This is a deliberate behavior change, not just a bug fix — replaying the identical challenge is no longer possible via this button; if that's ever wanted again, it would need a separate explicit control, not `restart()`.

1. ## Two real bugs found + fixed 2026-09-09 (don't reintroduce)

- **`detectDefaultLang()` never read back a previously-saved language choice** — a user who explicitly switched to Arabic on one page would silently revert to English/auto-detected language on the next page, because the function checked URL path and country session storage but never `localStorage.getItem('lang')` itself. Fixed by checking the saved `lang` value right after URL-path detection, before falling back to country-based defaults.
- **`_getPageSlug()` returned the literal string `'index'` for every nested `.../index.html` page** (e.g. every `/jo/...`, `/om/...` page whose URL ends in `/`) instead of a page-specific id — this collided every such page's favorite-star id onto the single string `'index'`, so favoriting one country-vertical page favorited (and showed as favorited on) all of them. Fixed to fall back to the second-to-last path segment when the last one is empty/`index`.
- **20 of the ~36 `jo/` non-game pages, plus 1 legacy page each in `om/ae/sa/us/uk`, never loaded `i18n.js` at all** (confirmed via `grep -L i18n.js` across all HTML) — these pages had zero favorites, zero dark-mode toggle, zero auth button, zero bottom-nav, zero language-switching, zero PWA/offline-banner, because the single file that provides all of that was simply never included in their `<head>`/`<body>`. User-reported via a screenshot of `jo/calculators/social-security/` showing no favorite star at all. Root cause: these pages were built from a template that predates `i18n.js` being added to the standard page template, and nothing ever caught that they'd fallen out of sync. Fixed by appending `<script src="i18n.js?v=41" defer></script>` before `</body>` on all 24 affected files (`jo/calculators/{car-cost,income-tax,package-customs,rent-vs-buy,social-security,tawjihi-average,university-cost,university-gpa,wedding-cost,zakat}`, `jo/{emergency-numbers,fuel-prices,gold-price,holidays,prayer-times,weather}`, `jo/students/scholarships-loans`, `jo/tools/{government-vs-private,jordan-vs-gulf}`, `om/salary-calculator`, `ae/vat-calculator`, `sa/vat-calculator`, `us/tip-calculator`, `uk/percentage-calculator`) — all already had `<base href>` and `.page-header`/`.card` markup matching what `i18n.js` expects, so no other template changes were needed. **The 15 `jo/games/*` + `wordle/` pages are correctly excluded from this** — they intentionally don't load `i18n.js` (see the "In-page English translation system" section above); don't add it to them. **If a new `/jo/` (or any country-vertical) page is created from an older copy-pasted template in the future, verify it includes `i18n.js` before shipping** — this class of bug is invisible in a quick visual check since the page still renders and functions as a calculator, it just silently lacks every cross-page feature.


## Mobile nav menu horizontal overflow — fixed 2026-09-14

User-reported via screenshot (site owner hit this themselves): on mobile, opening the country or language dropdown inside the collapsed hamburger menu required swiping right to actually see it — the menu content was rendering off-screen.

**Root cause, found via CDP mobile-emulation diagnostics (not guessed from CSS reading alone)**: `.nav-links` (the collapsed mobile nav panel) sets `flex-direction: column` in its mobile media query, but **inherits `flex-wrap: wrap` from the desktop base `.nav-links` rule** (`flex-wrap` was never explicitly reset in the mobile override). `flex-wrap:wrap` + `flex-direction:column` on a height-constrained flex container (`max-height: calc(100vh - 68px)`) makes overflowing items wrap into a **second column** instead of just growing/scrolling vertically — so once About/Contact/Sign-Up/dark-toggle filled the first "column" height, both `.lang-switcher` instances (country picker + language picker) got pushed into a second column positioned off to the right of the viewport, requiring horizontal scroll to reach. Confirmed precisely via a live diagnostic script reading each nav child's actual `getBoundingClientRect()` — the switcher elements sat at `left:378` inside a 390px-wide viewport, i.e. almost entirely off-screen.

**Fixed**: added `flex-wrap: nowrap;` (the actual fix) and `overflow-x: hidden;` (defense-in-depth) to `.nav-links`'s mobile media-query rule in `style.css`. Verified via a fresh cache-busted fetch of the live file that the change is correctly deployed — **full CDP behavioral re-verification is still pending** a Cloudflare cache purge (see the "Cloudflare edge-cache staleness" section immediately below — `style.css` got cached with the pre-fix content in the propagation window right after this push, same as documented incidents elsewhere in this file, and this session doesn't have cache-purge API access).


## QR generator — real bug found and fixed, 2026-09-21 (user-reported: failed even on a single character)

User reported via screenshot: generating a QR code for `https://adawati.space` (and separately confirmed even a single character) failed with "❌ تعذّر توليد الرمز — النص طويل جداً، جرّب نصاً أقصر" (text too long). **This message was always a lie** — investigation found the `catch` block in `generateQR()` unconditionally showed the "too long" message for *any* thrown error, regardless of actual cause, ever since the page was built.

**Root cause investigation**: could not reproduce via headless Chrome CDP (character-by-character typing simulation and direct `new QRCode(...)` calls both succeeded cleanly against the live production page) — this is the same "reproduces fine in automation, fails on a real device" pattern already documented elsewhere in this file for the mobile Safari popup-timing bug, and the lesson from that section applies again: don't conclude the code must be fine just because CDP-driven Chrome can't trigger it. Downloaded and inspected the actual `qrcodejs@1.0.0` library source (from cdnjs, confirmed reachable and CSP-allowed) — it uses `typeNumber:4` and, critically, its `Canvas`-based drawer calls `canvas.getContext('2d')` **synchronously during construction**, with no null-check on the returned context. **This is the classic failure signature of a privacy/fingerprinting-protection browser feature** (common in privacy-focused mobile browsers and some ad-blocker "Canvas Blocker" features) that poisons or nulls `getContext('2d')` to prevent canvas-fingerprinting — `new QRCode(...)` would then throw a `TypeError` reading a property off `null` immediately, regardless of input text length, exactly matching "fails even on a single character" and being invisible to any headless-Chrome-based test (which has no such privacy extension).

**Fixed**: (1) added an explicit Canvas-availability pre-check (`document.createElement('canvas').getContext('2d')`, verifying it returns a real object with a `fillRect` method) *before* attempting `new QRCode(...)` — if it fails, shows an honest, actionable message ("your browser is blocking QR image generation, likely due to a privacy/fingerprint-protection setting — try disabling it for this site or use a different browser") instead of the misleading length claim; (2) the remaining generic `catch` block now only shows the "too long" message when `text.length > 300` (a real, generous threshold) and otherwise shows a neutral retry message — no longer lies about the cause; (3) added a 180ms debounce (`generateQRDebounced`) on the input-typing listener (previously fired `generateQR()` on *every* keystroke, tearing down and rebuilding the QRCode instance in rapid succession) as a secondary defensive measure, since rapid re-invocation of a Canvas-based drawer is also a plausible (if unconfirmed) trigger for a decade-old library not designed for that usage pattern — the explicit click button and paste handler still fire promptly.

**Verified via CDP**: normal generation still works correctly (confirmed a real `<canvas>` element renders); a simulated Canvas-blocked browser (`HTMLCanvasElement.prototype.getContext` overridden to return `null`, replicating the hypothesized real cause) now correctly shows the new accurate message instead of silently failing or lying about text length. **Could not verify the fix resolves the user's exact real-device failure** (same limitation as always with this class of bug) — ask the user to retest on the same device/browser that showed the original error.
