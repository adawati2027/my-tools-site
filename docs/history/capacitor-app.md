# Android/iOS Capacitor native app (adawati-app)

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## Android/iOS app conversion (Capacitor) — started 2026-09-07

User wants Adawati wrapped as a native Android + iOS app via Capacitor, on top of the existing web/PWA, without duplicating content or rebuilding the site. Full 20-phase plan supplied by the user (audit → PWA → offline → mobile UX → Capacitor → Android → iOS → QA → stores → Jordan integration → multi-country config → analytics → monetization → push notifications), sequenced across ~6 weeks (flexible — "not literally 6 weeks", can move faster).

**Week 1 (Phase 0 — audit, executed as a scheduled overnight job):** Full architecture/dependency/mobile audit, scored **89/100** initially, **~90/100** after this week's fixes (a judgment-call estimate against the original report's category weights, not a re-run automated audit — the user explicitly said not to bother re-running it). Full report published as an Artifact + PDF. Key findings:
- Dependency footprint is unusually clean: only 4 unique external `<script src>` references site-wide (GA + AdSense, both intentionally unversioned by Google design; Firebase SDK pinned to `10.13.2`). Heavier libs (`mammoth`, `xlsx`, `pdf.js`, `html2canvas`, `jsPDF`) are version-pinned and lazy-loaded only on `ar/file-converter`. No jQuery, no cookies, no fixed-width CSS causing horizontal-scroll risk anywhere (every flagged `width:` was actually `max-width:`).
- **`<base href="https://adawati.space/">` is not a Capacitor blocker to "fix" — it's a signal for the right architecture.** Recommendation locked in with the user: **don't bundle web assets locally into the native app** — configure Capacitor's `server: { url: 'https://adawati.space' }` instead, so the app is a native shell around the live site. This reuses the existing (already solid) service worker for all offline/caching behavior as-is, keeps one single source of truth, and avoids re-verifying CORS for the 5 third-party APIs the site calls live (`api.open-meteo.com` weather, `open.er-api.com` currency, `xaus.com` gold price, `api.country.is` geo-detect, `api.aladhan.com` prayer times) under a different bundled origin. **Do not silently switch to asset-bundling later without revisiting this decision** — it would break relative-URL resolution site-wide given how consistently `<base href>` is used.
- **Recommended against the plan's proposed `tools/oman/`, `tools/jordan/` folder reorganization** — user agreed. The current per-country top-level layout (`om/ ae/ sa/ us/ uk/ jo/`) is already deployed, indexed, and linked; reorganizing would mean a full 301-redirect + sitemap + re-indexing effort for no concrete unblocked benefit (Capacitor doesn't need it, adding a country doesn't need it). Revisit only if a future concrete requirement actually strains the current shape.
- Fixed same night (safe, additive, all validated + pushed): favicon (`<link rel="icon">`) was missing on **every single page** — added site-wide (260 pages) using existing `icon-192.svg`. Game pages (`jo/games/*`) never registered the service worker or linked the manifest themselves (relied entirely on the visitor having loaded some other page first — a real gap since shared challenge links are this feature's main entry point) — fixed by adding the same registration directly in `quiz-engine.js`. Game pages also never respected the site's dark-mode preference (same root cause: no `i18n.js`) — fixed by reading the stored `dark` key on load (no toggle button there yet, just honoring the preference).
- **Generated the missing native-app icon assets** (flagged as a P0 blocker for Phase 6/7 — `icon-192.svg`/`icon-512.svg` are SVG-only, but Capacitor/Android Studio/Xcode icon-generation tooling needs a PNG master): used **headless Chrome** (`chrome.exe --headless --screenshot=...`, already installed on this machine at the standard Program Files path — no new dependency) to rasterize a full-bleed square (no pre-baked corner rounding — native platforms apply their own mask shape, so a source icon with rounded corners already baked in double-rounds/gaps under the OS's own mask) version of the existing lightning-bolt SVG design at **1024×1024** (`icon-1024-master.png`, project root — hand this to `@capacitor/assets` or Android Studio/Xcode's icon generators later) and, via .NET `System.Drawing` bicubic downscale in PowerShell (headless Chrome's own tiny-viewport screenshots were unreliable — a `--window-size=180,180` render just cropped the top-left corner of a page CSS-sized for 1024px instead of scaling; fixed by making the render page's own CSS `100vw`/`100vh`-based instead of a fixed pixel size, which fixed the 1024 render, but the 180px screenshot was *still* unreliable at that tiny window size, so the working method was: render one clean 1024 master via headless Chrome, then resize *that* file with .NET), an **`apple-touch-icon.png`** (180×180). Both wired into all 260 pages via the same batch-script pattern as the favicon fix, plus a new `image/png` entry added to `manifest.json`'s `icons` array. **If regenerating these, remember the corner-radius lesson** — check the actual SVG source (`icon-512.svg` has `rx="112"` baked in) and strip it for any native/PNG-master render.
- Still open / needs the user, not mechanical: `manifest.json`'s `screenshots` array is empty (minor, richer install-UI only); no dark-mode *toggle button* on game pages yet (they now just read the preference); everything past Phase 5 (actual Capacitor install/build, real Android Studio/Xcode work, store accounts, native device QA) needs tooling this Windows environment doesn't have (no Android Studio, no Xcode — iOS builds fundamentally need a Mac) and the user's own paid accounts (Google Play ~$25 one-time, Apple Developer ~$99/yr).

**Week 2 (PWA/Manifest/Service Worker/Offline/Mobile UX) — same night, user said to finish it too:** most of this phase turned out to already be satisfied by the existing `manifest.json`/`sw.js`/Week-1 icon work; the two genuinely new pieces built:
- **Mobile bottom navigation** (`initBottomNav()` in `i18n.js`, called from the main `DOMContentLoaded` handler; a near-identical `initGameBottomNav()` duplicated into `quiz-engine.js` for the 15 game pages, same reason as every other game-page duplication this session — they don't load `i18n.js`). 3 items — **Home / Tools / Favorites** (the plan's suggested 4th "⚙️ Settings" item was deliberately dropped: a dark-mode toggle already exists in the top navbar via `injectDarkToggle()`, and there's no other settings destination yet, so a 4th button would have no real target). Reuses existing i18n keys (`nav_home`, `section_tools`, `fav_title` stripped of its emoji prefix) so it's already translated in all 6 languages on non-game pages; game pages use their own small AR/EN-only inline strings matching `quiz-engine.js`'s established scope. Links: Home → `getHomeHref()`, Tools → `getHomeHref() + '#toolsGrid'`, Favorites → `getHomeHref() + '#favSection'` (both anchors already exist on hub pages via the existing favorites/tools-grid features). CSS in `style.css` under "Bottom Navigation" — `display:none` by default, shown only under `@media (max-width:768px)`, `padding-bottom` added to `body.has-bottom-nav` in the same media query so it never overlaps page content, `env(safe-area-inset-bottom)` padding for the iOS home-indicator area. **Tested pre-push** (a first for a change this visually broad this session): since every page's `<base href="https://adawati.space/">` would've made a local-server preview silently load the *live, unedited* `style.css`/`i18n.js` instead of the local changes, defeating the point — built an isolated preview page instead that pulls the real local `style.css` via a tiny Node static server and manually injects the exact nav markup, verified in the browser tool in both RTL/Arabic and LTR/English, and in both light and dark mode, before rolling out to all 260 pages.
- **Offline status banner** (`initOfflineBanner()` in `i18n.js`) — a fixed top banner, hidden by default, shown via `navigator.onLine` check plus `online`/`offline` event listeners, telling the visitor live features may be unavailable but core calculators still work. Not duplicated to game pages (lower priority there — the challenge flow already needs a live Firestore connection to function at all, so "you're offline" is closer to self-evident there than on a pure client-side calculator).


## adawati-app (Capacitor native shell) — separate GitHub repo, 2026-09-09 findings

The actual Capacitor/Android/iOS project lives in a **separate repo**, `adawati2027/adawati-app` (not this one — `my-tools-site` is the web content only, `adawati-app` is just the native wrapper). Same account owns both; the `GITHUB_PAT` in this repo's `.env` also has full push access there, but there's no `push-to-github.js`-equivalent for it — pushes there were done ad hoc via a small one-off blob→tree→commit→ref script (same pattern, no local checkout of that repo either).

A user-relayed QA report (82/100, claiming a "real Full QA on the GitHub repo itself") was independently verified file-by-file rather than trusted outright — mostly accurate, but with one gap worse than reported and one gap the report completely missed:

- **iOS Associated Domains — confirmed missing, then fixed 2026-09-09.** No `App.entitlements` file existed anywhere in the iOS project (not misconfigured — genuinely absent). Added `ios/App/App/App.entitlements` (`com.apple.developer.associated-domains` = `applinks:adawati.space`) and wired `CODE_SIGN_ENTITLEMENTS = App/App.entitlements;` into both the Debug and Release build configs in `project.pbxproj` (hand-edited directly via the GitHub API — no local Xcode/Mac available to verify, so the only real check was watching the `ios-build.yml` GitHub Actions run go green afterward, which it did). Still **cannot be fully closed** until the user has an Apple Developer account: the actual `apple-app-site-association` file needs a real Apple Team ID and would need to be published at `adawati.space/.well-known/apple-app-site-association` (currently 404, confirmed via curl). Android's equivalent (`assetlinks.json`) already returns 200 — that half is fine.
- **P0 the original QA report missed entirely: App Links open the app but silently drop the destination URL.** Traced directly in Capacitor's Android source (`Bridge.java`/`BridgeActivity.java`, `ionic-team/capacitor` main branch): when an `https://adawati.space/...` link launches the app via the `autoVerify` intent-filter, Capacitor does **not** auto-navigate the WebView to that specific path — it just loads the configured `server.url` root and exposes the incoming URL only via `@capacitor/app`'s `appUrlOpen` event, which something has to explicitly listen for. Confirmed via grep that nothing in this repo (`my-tools-site`) referenced `Capacitor`/`appUrlOpen` at all — so a shared challenge link (`.../jo/games/animals-quiz/?challenge=abc123`) tapped from WhatsApp would open the app to the home page and silently lose the `?challenge=` param, defeating the entire feature. **Fixed 2026-09-09** by adding a guarded `window.Capacitor.Plugins.App.addListener('appUrlOpen', ...)` → `location.href = data.url` snippet to the top of both `i18n.js` and `quiz-engine.js` (needs both since no single script loads on every page — same duplication reason as everything else game-page-related in this file). No-ops completely outside the native app (`window.Capacitor` is undefined on the plain web), so zero risk to normal browser visitors. **Not end-to-end tested** — no real device/app install available here, only the JS logic itself and Capacitor's documented API were verified. If deep links still don't work after this, check that the app actually delivers `appUrlOpen` on cold start (not just warm-resume) as Capacitor's docs claim, since that's the one part not independently confirmed.
- Other things checked and found fine, no action needed: Gradle files all present (`android/build.gradle` compileSdk/targetSdk 36, minSdk 24 — current), no secrets in the repo or its commit history (`.gitignore` properly excludes the release keystore/passwords/`local.properties`), `ios-build.yml` is genuinely just an unsigned simulator compile-check as its own comments say (not App Store-ready, expected).
- **Known gap, not yet acted on:** no Android equivalent of `ios-build.yml` exists — Android compile is never verified in CI at all, only iOS is. `minifyEnabled false` in `android/app/build.gradle` means release builds ship unobfuscated (low priority for a WebView-shell app with little native logic to protect).
- The rest of the original 30-item checklist (real-device QA, performance, accessibility, crash/network-loss scenarios, store listing) is still untouched — needs actual device/store tooling this environment doesn't have.
