# Unsolicited external "QA report" pastes — verification pattern and outcomes

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## External QA report, 2026-09-10 — verified before acting, mixed accuracy

User pasted a large (18-point) unsolicited QA report claiming an "8.8/10" site review. Per this project's established practice (see the `adawati-app` QA-report section and the income-tax re-flagging incident above), verified claims against the live code file-by-file rather than trusting the report — several were stale/false:
- **"Recently Used missing" — false.** Exists (`recentSection`/`recentGrid` in `index.html`, `trackRecent()`), just labeled "✨ You Might Like" and correctly hidden until the visitor has browsing history (a fresh crawl seeing nothing is expected behavior, not a bug).
- **"Related Tools empty on age-calculator" — false.** Has 4 real working links.
- **"Duplicate Hijri-age FAQ" — true, confirmed and fixed.** Two separate visible FAQ entries asked the same question ("Why is my Hijri age different..." in the main JS-toggle FAQ set, "What is the difference between my Hijri and Gregorian age?" in a separately-added static `<details>` block) — removed the redundant `<details>` one.
- **App CTA — investigated and intentionally skipped.** No live Play Store/App Store listing exists yet (confirmed with the user) — a "Get the App" button with nowhere real to send users would be worse than no button. Revisit once `adawati-app` is actually published; see the adawati-app section above for what's still blocking that (user's own paid developer accounts).
- **Tool-naming inconsistency — real, found a worse case than the report's own example.** The report cited "Percentage Calculator" vs "Percentage & Discount" as the same tool having two names on the homepage — confirmed true (2 situational-bundle cards, lines using hardcoded English, didn't match the canonical `pct_card_title` i18n value/H1 used everywhere else) and fixed both instances, plus the JSON-LD `featureList`. Also found (not previously flagged): "Timezone Converter" (one word) vs the canonical "Time Zone Converter" (two words, matches the page's own H1 and `tz_card_title`) — fixed the one hardcoded instance without `data-i18n` protection (a bundle card) plus the JSON-LD featureList; left 2 other instances alone since they already carry `data-i18n="tz_card_title"` and get corrected by JS at runtime regardless of their raw fallback text.
- **Bigger, unresolved naming case found, deliberately NOT touched**: `loan-calculator.html` has **three different names** for the same tool: the page's own H1 says "Loan & Payment Calculator", the global `i18n.js` key `loan_card_title` (consistently translated this way across all 6 languages — not a typo) says "Monthly Payment Calculator", and most homepage card instances hardcode "Loan Calculator". Unlike the percentage/timezone cases, there's no single obviously-correct existing canonical form to converge on here — picking one means overriding either the page's own H1, a deliberately-translated i18n key, or the majority of existing links. Needs an explicit naming decision from the user before touching it, not a mechanical fix.

**Fixed as part of this pass** (2026-09-10):
- Removed the duplicate FAQ entry on `age-calculator.html`.
- Fixed the 2 "Percentage Calculator" → "Percentage & Discount" instances + 1 "Timezone Converter" → "Time Zone Converter" instance + the JSON-LD `featureList` string, all on `index.html`.
- Added a "See all tools →" link (anchors to `#toolsGrid`) under each of the 4 "Pick Your Situation" bundle grids (car/travel/job/student) on `index.html`, wired into `toggleBundle()` so it shows/hides with its matching bundle. This is a lighter version of the report's "internal-link cluster" ask (#13) — the bundles are intentionally country-agnostic on the global homepage, so a country-specific "cluster hub" like `jo/students/best-tools/` (built earlier this session) is a better fit for that ask than mixing Jordan-only tools into the global bundles.
- **Search matching improved**: `filterTools()` in `index.html` used single-substring matching (`data-search`/text `.includes(q)`), so a multi-word query like "jordan university" would never match anything unless that literal phrase existed verbatim in a card's keywords. Now also checks AND-of-words (every space-separated query word must appear somewhere in the card's searchable text, in any order) as a fallback when the full-phrase match fails. **Important caveat**: this still only searches cards already in the current page's DOM — it does NOT reach across pages (so "jordan university" still can't surface Jordan-specific tools from the global homepage, since those cards simply aren't in `index.html`'s `#toolsGrid` at all). Building a true cross-site smart search (a real search index covering all ~260 pages, fuzzy/semantic multi-result matching, the kind of experience the QA report describes with country/topic examples) is a substantially bigger feature — not attempted this pass, flagged as the actual gap if "smart search" work continues.
- **Zero-results fallback added**: when a search matches nothing, the "no tool found" message now also shows a "Search all of Adawati for '{query}' →" link to `google.com/search?q=site:adawati.space+...` — a real, if basic, escape hatch for the site's-search-can't-reach-everything gap above. New i18n key `search_try_site` added to all 6 languages.


## External QA report, 2026-09-14 — mixed accuracy, one real gap surfaced

User pasted another large unsolicited "full engineering/QA/security/SEO report" (same pattern as the 2026-09-10 ones documented above — confident tone, numbered sections, an overall score). Verified the checkable claims against the live site/code before acting, per this project's established practice:

- **False**: "Deterministic calculator tests are not yet implemented" and "Full end-to-end tests are not yet implemented" — both `test-calculators.js` (20/20) and `test-e2e.js` (29/29) already exist and were re-run against live production the same session, both fully passing. "Lighthouse and Core Web Vitals have not yet been run" — also false, run earlier this session with real before/after numbers (45→96 performance). "The currency converter still contains two `element.onclick=` property assignments" — false, none found via grep.
- **True, and independently confirmed rather than just trusted**: sitemap has exactly 301 URLs (`curl` + count), all 6 security headers present with correct values (`curl -I`), homepage has 5 `innerHTML` uses, CSP still uses `unsafe-inline`.
- **The one real, valuable finding**: the report's claim of "~250 secondary pages still need the onclick review" prompted a proper re-scan (see the scope-correction note above) that found this file's own "remaining, out of scope" note was stale/wrong — 60 files (not the previously-documented small remainder) still had real onclick attributes, including 6 high-traffic country hub pages that got fixed same-session as a result. **Lesson: even when a pasted "audit report" gets most of its specific technical claims wrong (this one did, on the demonstrably-checkable ones), a vague directional claim can still be worth a fresh independent scan rather than dismissing the whole report — the "~250 pages" number itself was almost certainly not really counted by whatever produced this report, but the underlying direction ("more pages than you think still need this") was right.**


## External "deep scan" QA report, 2026-09-15 — mostly a scanner artifact, two real minor gaps fixed

User pasted another large unsolicited "deep verified live scan report" (same pattern as the several before it) claiming a headline "internal path and asset-integrity problem": 2,929 of 3,482 internal targets failing, with specific examples like `/ae/style.css` → 404, `/om/about.html` → 404, `/om/salary-calculator/i18n.js?v=42` → 404, `/ae/ae/vat-calculator/` → 404 (locale prefix duplicated). Also claimed 701 onclick attributes across 220 pages (directly contradicting the 2026-09-14 onclick-refactor project documented at length above) and 2 leftover `.onclick=` assignments in `currency-converter.html` (also already fixed 2026-09-14).

**Verified rather than trusted, per this project's established practice — and this time the verification actually mattered, since the specific 404 URLs the report cited are individually real** (`curl` confirmed all 4 examples genuinely return 404). But the report's own methodology was flawed: **it evidently ignored the `<base href="https://adawati.space/">` tag every page carries** and resolved relative paths (`style.css`, `i18n.js?v=42`, `about.html`, `ae/vat-calculator/`) naively against each page's own directory instead of against the base — exactly the failure mode `<base href>` exists to prevent. **Confirmed via a real headless-Chrome CDP test** (not just reasoning about URL-resolution spec behavior): loaded `/ae/` and `/om/salary-calculator/` live, read back the actual resolved `href`/`src` the browser computed for the stylesheet and i18n script — both correctly resolved to `https://adawati.space/style.css` and `https://adawati.space/i18n.js?v=42` (root-level, correct), with **zero failed network requests** on either page. The malformed URLs the report flagged (`/ae/style.css` etc.) are real 404s in isolation, but no real browser ever actually requests them — they're an artifact of a link-checker that doesn't fully parse HTML semantics (a common category of bug in generic crawlers). **This was the report's single largest, most alarming finding (driving its "6.5/10 navigation integrity" sub-score) and it does not describe anything a real visitor or search engine crawler using a real browser would ever hit.**

**The onclick claims were also independently re-verified and found false**: a fresh full-repo regex scan (the same `<tag ...onclick="` pattern established during the original refactor) found **0 onclick attributes across all 306 HTML files** — matching the already-documented "PROJECT COMPLETE" state, not the report's claimed 701/220. `currency-converter.html` also has zero `.onclick=` property assignments, confirming that fix (also already documented) is still in place.

**Two claims in the report were real and worth fixing, both minor and already resolved**:
- **`favicon.ico` returned 404** — real, since some legacy tools/bots/RSS readers still probe this well-known path directly regardless of the site's `<link rel="icon">` SVG tag (which is what modern browsers actually use, already in place site-wide since the 2026-09-07 PWA audit). Fixed by generating a proper multi-size (16/32/48px) ICO from the existing `icon-1024-master.png` master via .NET `System.Drawing` in PowerShell (same established icon-generation technique as the original PWA icon work), placed at the repo root — no HTML changes needed since browsers/tools request this well-known path directly.
- **`.well-known/security.txt` was missing** — a real, legitimate, low-effort best practice (RFC 9116) for a site with real financial calculators and a genuine user base. Added a minimal valid one (Contact, Expires, Preferred-Languages, Canonical fields) using the same contact email already public on `contact.html` — no new information exposure, just making an already-public contact method discoverable via the standard convention. Confirmed `.well-known/` is already allowlisted in `push-to-github.js`'s dotfile-exclusion logic (`.well-known`, `.nojekyll`), so no script change was needed.

**Other claims in the report were either already-known/documented (duplicate security headers — real, but the same pre-existing Cloudflare Transform Rule gap already documented and blocked on dashboard access, not new) or generic recommendations already satisfied by existing work** (Lighthouse, `test-calculators.js`, `test-e2e.js` all already exist and were re-run clean multiple times this session, despite the report's checklist implying they don't exist). **`site.webmanifest`/`sitemap_index.xml` 404s were correctly self-assessed by the report itself as non-issues** (manifest.json and sitemap.xml already cover those needs) — confirmed manifest.json is dynamically linked via `i18n.js` (`injectManifestLink`-style code, not a static `<link>` tag), which is sufficient for real browsers' PWA install-prompt behavior even though a static-HTML scanner wouldn't see it.

**Lesson reinforced**: this is now several external "QA report" pastes in a row where the report's own specific technical claims — even ones with concrete-looking numbers and exact URLs — turned out to be wrong or scanner-artifact-driven on verification, while a couple of genuinely real, minor, previously-unflagged gaps (favicon.ico, security.txt this time) were mixed in. **Keep verifying every specific, checkable claim before acting** — including ones that "feel" alarming or come with precise numbers, since precision doesn't imply accuracy — but don't dismiss a whole report just because its majority is wrong; a quick scan for the few genuinely actionable items is worth the time.


## External "in-depth probe" report, 2026-09-15 — mostly false, one real fix applied

User pasted another external report, more measured than the previous ones, claiming: 8 URLs with 1-word placeholder meta descriptions ("Today"/"Adawati"), 11 sensitive paths tested clean, 3 calculator logic findings (BMI good, compound-interest silent failure, age-calculator no feedback on future dates), and 128 internal links with 0 broken.

**Verified each claim before acting**:
- **Meta description claim: FALSE.** Fetched all 8 URLs live — every one has a full, proper 60-150+ character description (e.g. "Today's gold price per gram in AED for 18K, 21K, 22K and 24K, updated live from the global gold spot price..."). The scanner almost certainly mis-parsed the possessive apostrophe (`Today's` → `Today`, `Adawati's` → `Adawati`), truncating its own extraction to the first word and misreporting it as the entire description.
- **Sensitive path exposure: TRUE, confirmed clean** (`.env`, `.git/HEAD`, `package.json`, `admin/`, `.DS_Store` all 404 live) — a real, accurate finding, just confirming existing good posture, not a gap.
- **BMI / compound-interest calculator finding: partially true, but the suggested fix was wrong.** Confirmed BMI does show a visible red error box (`bmi_invalid`) on invalid input, and compound-interest does silently hide the result on `P<=0||r<=0||t<=0`. But BMI is wired to a **Calculate button click** while compound-interest uses **live `oninput`** (fires every keystroke) — showing an error message on every keystroke while a user is still typing a number (e.g., typed "1" of "15") would be a genuine UX regression, and is inconsistent with the same silent-hide-while-typing pattern used deliberately across most other live-`oninput` calculators sitewide (percentage-calculator, vat-calculator, etc.). **Not changed** — the report's observation was accurate but its recommended fix would have made the UX worse for this specific interaction model.
- **Age-calculator future-date finding: TRUE, and genuinely worth fixing** — unlike compound-interest, the birthdate field uses `onchange` (fires only after a complete, deliberate date-picker selection, never mid-input), so silently returning with zero feedback really is a UX gap here. **Fixed**: added a `future_date_error` translation key (ar/en/fr/es/de/ru, Arabic written in MSA since this is a root generic tool, not a `/jo/` page) and a dedicated `#ageError` box (reusing the existing `.result-box.danger` style already used by BMI) that shows "Birth date must be in the past" when triggered.
- **128 internal links, 0 broken: plausible and not re-verified at length** — this scanner's own reported number (0 broken) is consistent with the real, correct behavior already confirmed via the base-href investigation in the previous report's debunking, so no reason to doubt it.

**Real implementation bug caught and fixed before pushing, worth remembering**: the first attempt at the age-calculator fix wrote the error message directly into `#result`'s `innerHTML`, which **destroyed the pre-existing child elements** (`#ageMain`, `#ageSub`, `#stat-years`, etc.) that the success path's code expects to already exist in the DOM — this would have permanently broken the calculator after the *first* time a user hit a future date, since every subsequent valid calculation would throw `Cannot read properties of null` trying to update elements that no longer existed. **Fixed by adding a separate sibling `#ageError` element instead of ever touching `#result`'s internal structure.** Caught via a real functional CDP test (not just "no syntax error") that specifically exercised the sequence: trigger the error, then enter a valid date afterward, and confirmed the calculator still works — this is exactly the kind of two-step regression a syntax-only check would have missed.

**Second real bug caught in the test harness itself, not the site**: the first local-server test setup (a minimal `http.createServer` with no `Content-Type` header) made Chrome render the page source as plain text instead of parsing it as HTML — `getElementById()` returned `null` for *every* element, including long-pre-existing ones like `#result`, which looked exactly like a broken page until traced to the missing `Content-Type: text/html` header on the test server. **Lesson: any future ad-hoc local static server used for testing must explicitly set `Content-Type` per file extension** — Chrome does not sniff HTML from an untyped response the way it might from a real web server's defaults.

Validated (`JSON.parse`+`new Function()`+div-balance) on all 6 lang variants, `node build-lang-pages.js` re-run, pushed (first attempt failed entirely under GitHub's secondary rate limit, second succeeded), verified live via blob-sha diff + `curl`, and both `test-calculators.js` (20/20) and `test-e2e.js` (29/29) re-run clean afterward.
