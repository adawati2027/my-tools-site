# Gold-price accuracy investigation + Cloudflare Worker server-side fallback

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## Gold-price accuracy investigation, 2026-09-10 — real local premium confirmed for Oman only

User reported `om/gold-price/`'s 21K price (~47 OMR) was noticeably below real Muscat gold shop prices they'd observed for months (~51+ OMR) — **before any making charge**, not just a "spot vs retail markup" explanation.

**Investigation** (WebSearch was down the entire time — 6+ consecutive "unavailable" errors — so this was done entirely via direct `WebFetch` on specific known gold-price-tracking sites per country):
- `xaus.com` (the API this project uses) and `goldpricez.com` (a similar aggregator) **match each other almost exactly** in every country checked — both are pure global-spot-price-converted-to-currency, no local premium, confirmed by checking the underlying math (24K × 22/24 = 22K etc., always exact).
- `omangoldprice.com` showed **21K = 50.50 OMR** — a real, ~6.5% premium over our number, matching the user's own lived experience. This looks like a genuinely different, locally-run source (not a generic multi-country template site).
- Checked the same pattern for other countries and found **no equivalent gap**: Jordan (3 independent sources — `goldpricez.com`, `livepriceofgold.com`, and `xaus.com` itself — all landed within ~0.2% of each other, ~99.9-100.0 JOD for 24K), Saudi Arabia (`goldrate24.com` matched our SAR number to 2 decimal places), UAE (`livepriceofgold.com` matched within 0.2%), UK (`livepriceofgold.com` matched within 0.2%). **Conclusion: the local-premium gap is real but country-specific, not a universal Gulf/MENA phenomenon** — don't assume it applies everywhere just because it's real in Oman.

**No free API exists for genuine local-market gold prices** — every API-based service checked (`xaus.com`, `goldapi.io` by reputation) is spot-based; the sites that DO show locally-accurate numbers (`omangoldprice.com`) are plain server-rendered HTML with no API, and scraping them was explicitly discussed with the user and deliberately not built (fragile — breaks silently on any site redesign — and ToS-ambiguous). This is a real, structural limitation, not something to keep chasing without a genuinely new data source appearing.

**Fixed 2026-09-10**:
- All 6 gold-price pages (`jo/om/sa/ae/us/uk`): rewrote the disclaimer (both the visible `<p>` note and the JSON-LD FAQ answer) to honestly state the shown price is **global spot, not local market** — replacing earlier wording that undersold the gap as "might differ slightly."
- **`om/gold-price/index.html` only**: added an opt-in checkbox ("أضف تقدير هامش سوق مسقط (+6.5%)") that multiplies all 4 displayed karat prices by 1.065 and appends "(تقديري)" to each value plus a note on the updated-time label — implemented via a `rawPrices`/`renderPrices()` refactor (fetch sets `rawPrices` once, `renderPrices()` applies the multiplier and re-renders, called both after fetch and on toggle change — toggling doesn't re-fetch, instant UI response). **Verified live via CDP**: toggling on took 21K from 47.46 → 50.54 OMR, matching omangoldprice.com's 50.50 almost exactly.
- **Jordan's page**: a similar toggle was drafted first (before the per-country check was requested) then **deliberately reverted** — no evidence supports a Jordan-specific premium, so a fake toggle there would have been exactly the kind of unverified-financial-claim this project's core policy prohibits. **Don't add this toggle to Saudi/UAE/UK/US either** unless new evidence specifically supports it for that country — this is a country-by-country judgment call already made once with real data, not a "just add it everywhere for consistency" feature.

**Gotcha hit while verifying this push**: `om/gold-price/index.html`'s GitHub Pages deployment took noticeably longer than usual to go live (several minutes, not the usual 30-90s) even though the GitHub API confirmed the blob/commit succeeded immediately — checked via `GET /repos/.../pages/builds/latest` which showed `"status":"building"` for an extended period. **If a push succeeds (confirmed via the repo tree or a direct blob read) but the live site still doesn't reflect it after the usual wait, check the Pages build status endpoint before assuming something is broken** — it may just be a slow build, same lesson as the "new directory paths take longer" note above, but this time on an *existing* path with a larger diff.


## Gold-price API outage + server-side fallback via the Worker, 2026-09-14

User-reported (screenshot): `om/gold-price/` showing "تعذّر تحميل الأسعار الآن" (failed to load prices). Investigated rather than assuming a code bug — confirmed `xaus.com` (the API all 6 countries' gold-price pages depend on) was returning `503 usage_exceeded` **site-wide** (not just the API subpath), a genuine outage on their end. This affected all 6 gold-price pages simultaneously, not just Oman's — the existing error-handling was already working correctly (showing the graceful fallback message, not crashing), this was a real external dependency failure, not a bug.

**User explicitly chose to build a real fallback** (via `AskUserQuestion`) rather than just wait it out. Real constraint hit immediately: `open.er-api.com`/`api.frankfurter.app`/`api.exchangerate-api.com` (all already in the CSP `connect-src` allowlist) don't carry XAU (gold) as a currency — none of the site's existing whitelisted APIs provide gold spot prices. `goldprice.dev`'s anonymous no-key tier does, but adding its domain to the browser-side CSP `connect-src` would hit the **exact same duplicate-Transform-Rule blocker** documented in the CSP-hardening section above (both the Worker's policy and the un-editable old Transform Rule's policy would need the new domain, and this session still can't edit the latter).

**Fix: route the fallback through the existing `adawati-csp-nonce` Cloudflare Worker instead of calling third-party APIs directly from the browser.** Added a new `/api/gold-fallback?currency=X` path handled specially at the top of the Worker's `fetch()` — it fetches `api.goldprice.dev` (XAU/USD spot, troy ounce) + `open.er-api.com` (USD→target-currency rate) **server-side** (Worker-to-API fetches aren't CSP-governed at all, only browser-initiated ones are) and returns a computed 24k gram price as same-origin JSON. Since the browser only ever calls `adawati.space/api/gold-fallback` (already covered by `'self'`), **this needed zero CSP changes** — a cleaner fix than the allowlist route, and one this session could actually deploy without needing Cloudflare dashboard/Rulesets access.

**Real problem hit deploying this: `goldprice.dev`'s anonymous tier is rate-limited via Cloudflare's *shared* Worker egress IP pool** — other, unrelated Cloudflare Workers hitting the same free tier exhausted it, so calls from *this* Worker got `429` even though this project's own traffic was nowhere near any documented limit. Confirmed this wasn't a fluke with 3 consecutive retries, all `429`. **User signed up for a free goldprice.dev API key** (email only, no credit card, isolated per-key quota — this is a real credential, not a public value, so it went into a Cloudflare Worker secret via `wrangler secret put GOLDPRICE_API_KEY`, never hardcoded in `worker.js` or committed to this repo) — wired in as `Authorization: Bearer <key>` per their docs (confirmed the exact header format via their API reference before guessing). Fixed the shared-IP throttling immediately — verified all 6 currencies (JOD/OMR/SAR/AED/USD/GBP) return real `200` prices via the authenticated key.

**Wired into all 6 `{jo,om,sa,ae,us,uk}/gold-price/index.html` pages**: on `xaus.com` fetch failure (network error, non-2xx status, or malformed response — not just a `.catch()` on the raw promise, which wouldn't have caught a 503-with-valid-JSON-body response), falls through to `/api/gold-fallback?currency=<code>`, computes the same 24k/22k/21k/18k karat breakdown from the returned `price24`, and renders normally with a small "(fallback source)"/"(مصدر احتياطي)" note appended to the updated-time label so it's transparent to visitors which source they're seeing — never silently presents estimated/fallback data as if it were the primary live feed. `om`'s page (which already had the `rawPrices`/`renderPrices()`/local-market-toggle refactor from the earlier gold-price-accuracy investigation) got an `applyGoldPrice(price24, isFallback)` wrapper around that existing flow; the other 5 (simpler `karatPrices`-direct pages) got an equivalent `applyGoldPrice` extracted from their own previously-inline fetch handler, applied via one parameterized script covering all 5 at once (byte-for-byte identical structure across them, differing only in currency code/symbol/decimals/locale).

**Verified end-to-end via live CDP against production, not just the Worker endpoint in isolation**: blocked `*xaus.com*` at the network level (`Network.setBlockedURLs`, the same technique used to isolate a fallback path throughout this project) and confirmed `om`/`jo`/`us` gold-price pages all correctly render real fallback prices with the source note, `errorMsg` staying hidden — not just that the Worker endpoint itself returns valid JSON. Also confirmed the real (non-blocked) live behavior during the actual ongoing `xaus.com` outage: the page still resolves correctly, just takes longer (~8-9s total) since `xaus.com`'s own response is slow-to-fail rather than failing instantly — acceptable degraded behavior, meaningfully better than the pre-fix broken-error state.

**If `xaus.com` recovers and this is revisited**: the primary path is untouched (same `fetch('https://xaus.com/...')` call as before), so no further action needed — the fallback only ever activates on a real primary-source failure. If `goldprice.dev`'s key ever needs rotating, `wrangler secret put GOLDPRICE_API_KEY` again (from the `csp-worker` scratchpad directory) and redeploy; the key itself lives only in Cloudflare's secret store, never in this repo.
