# CSP hardening via Cloudflare Worker + nonce, enforcement, edge-cache staleness

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## CSP hardening — Cloudflare Worker + nonce, report-only mode live — 2026-09-14

Third of the "all of them" trio (repo security review, long-tail content, CSP hardening). Unlike the other two, this touches live production infrastructure in a way that's genuinely hard to fully reverse quickly, so it got the most deliberate treatment: real numbers before deciding an approach, explicit user confirmation before each production-affecting step, and a report-only rollout before ever considering enforcement — same staged-rollout discipline the original CSP setup used.

**Why full `unsafe-inline` removal isn't attempted, with real numbers**: a repo-wide scan found **342 unique inline `<script>` blocks**, **44 unique inline `<style>` blocks**, and **18,876 inline `style="..."` attribute occurrences (659 unique values)** across ~306 HTML files. Hashing all of these into the CSP header is technically possible for static content, but creates a real, recurring failure mode specific to this project: the CSP header lives in Cloudflare (a Transform Rule), completely disconnected from `push-to-github.js`'s deploy path — every future edit to any inline script/style (which happens on nearly every push this project makes) would invalidate its hash and silently break that one page until someone remembered to regenerate and redeploy the CSP header separately, with no error until a real visitor's browser enforces the stale policy. Migrating all 659 unique inline style values to CSS classes would be a refactor on the scale of the onclick project or bigger. **Decision, confirmed with the user via `AskUserQuestion` before starting**: build a Cloudflare Worker that injects a fresh per-request nonce into `script-src` and stamps it onto every inline `<script>` element at the edge — this needs zero per-edit maintenance since it doesn't care about script *content*, only tag *structure*. `style-src` keeps `unsafe-inline` as an accepted, documented tradeoff (lower severity than script injection, and the 659-unique-value problem has no maintenance-free fix). Per the standard CSP graceful-degradation mechanism, **`'unsafe-inline'` is kept in the new nonce-carrying policy too** — CSP-3-compliant browsers ignore `unsafe-inline` once a nonce is present on the same directive, so this is real hardening for modern browsers with zero regression risk for old ones, not a compromise.

**Worker**: `adawati-csp-nonce` (account `c8983313c898f7ed72bb29582ce6903e`). `fetch()`s the real origin (hardcoded to `https://adawati.space` + the incoming path/query, not the ambient `request.url`, so the same code works whether hit via its own `workers.dev` preview or via the real domain's Route), passes non-HTML responses through completely untouched (confirmed byte-identical to direct-origin `style.css`/`i18n.js` fetches), and for HTML responses: generates a random 16-byte nonce, uses `HTMLRewriter` to add `nonce="..."` to every `<script>` element **without** a `src` attribute (external `<script src>` tags are governed by the existing URL allowlist, not nonces, and are correctly left alone), and sets a **new, separate** `Content-Security-Policy-Report-Only` header carrying the full existing policy string with `'nonce-{value}'` inserted into `script-src` — the **existing enforced** `Content-Security-Policy` header (from the pre-existing Transform Rule) is read from the origin response and passed through completely unmodified, confirmed via live header inspection. A diagnostic `X-CSP-Nonce-Worker: active` header was added to make "is the Worker actually in the response path" trivially checkable via `curl -I`, useful during the propagation-delay troubleshooting below. Wrapped in try/catch with a fail-safe fallback that re-fetches the plain origin response if anything throws — a bug in this Worker degrades to "no report-only header" at worst, never a broken page, since it never touches the header that's actually enforced.

**Built via Wrangler CLI, not the dashboard's Monaco editor — a real, hard-learned lesson.** The dashboard's in-browser code editor proved too unstable for browser automation to use reliably for a ~40-line script with a large embedded string: repeated silent focus loss (typed keystrokes landed in an unrelated global-search box instead of the editor, once corrupting ~80 characters of an in-progress paste), a real Monaco auto-bracket-closing gotcha (the same class already documented for the Firestore Rules console editor — typing `export default {` auto-inserts a matching `}` that then needs manual removal once the real closing braces are typed, confirmed and fixed twice by reading the Problems panel and using `Ctrl+End` + counting stray trailing braces), and eventually genuine renderer freezes (`Page.captureScreenshot` timing out, keyboard/mouse input silently not registering, an accidental click on the browser extension's own panel-close button losing the connection entirely and discarding an already-correct, already-validated 0-error version of the code). **Lesson for any future Cloudflare Worker work in this project: write the code with the normal file tools (`Write`/`Edit`, which don't have any of these failure modes) into a scratchpad directory with a `wrangler.toml`, authenticate once via `wrangler login`(opens a real OAuth consent screen — a genuine permission grant, confirmed with the user before running it, standard Cloudflare-verified Wrangler app requesting broad-but-standard scopes), and deploy via `wrangler deploy` — this is categorically more reliable than driving the dashboard's Monaco editor through browser automation for anything beyond a trivial one-line edit.** `node --check` validated syntax locally before ever touching Cloudflare, removing any doubt about the file itself once Wrangler's own upload succeeded.

**Verification, in order, before ever binding a Route (the actual live-traffic-affecting step)**: (1) direct `curl` against the Worker's own `workers.dev` preview URL confirmed the existing enforced CSP header passes through byte-for-byte unchanged, the new report-only header carries a fresh nonce each request, and that nonce exactly matches the nonce stamped on every inline script **within the same single response** (an earlier two-separate-`curl`-calls comparison wrongly looked like a mismatch — each request gets its own random nonce, so header and body must be captured from one request, not two, to be comparable); (2) tested across 4 different page architectures (homepage, a root calculator, a country hub, a `quiz-engine.js` game page) via the preview URL — all 200, all correctly nonce-stamped; (3) a real headless-Chrome CDP run against the preview URL found 2 genuine `Content-Security-Policy-Report-Only` violations (a `base-uri 'self'` violation, and a cascading relative-URL-resolution failure on `quiz-engine.js` caused by it) — traced to a **test-environment artifact**, not a Worker bug: `'self'` in CSP means the *document's own origin*, and testing via `adawati-csp-nonce.ahmadalamawi.workers.dev` makes that origin the workers.dev subdomain, which doesn't match the page's own `<base href="https://adawati.space/">` — a false positive specific to previewing through the wrong origin, not something that would occur once actually served from `adawati.space` itself. **This reasoning was then explicitly verified, not just assumed**: after binding the Route (a second explicit user confirmation, since this is the step that actually puts every real visitor's request through the Worker) and waiting ~15s for propagation (confirmed via the `X-CSP-Nonce-Worker` header appearing), the identical CDP violation-scan was re-run against the **real** `adawati.space` domain across 8 page types (adding a kids page, file-converter, and currency-converter to the earlier 4) — **zero CSP violations, zero JS errors, exactly one `<h1>` on every page** — confirming the base-uri reasoning was correct and the Worker is safe in its actual deployed configuration, not just in theory.

**Final full-site regression, with the Worker now live in the request path for literally every visitor**: all 301 sitemap URLs re-checked via `curl`, 0 failures; `test-calculators.js` 20/20 and `test-e2e.js` 29/29 re-run against live production, both fully passing — the exact same numbers as before the Worker existed, confirming it adds zero functional regression anywhere the existing test suites reach.

**Current state — deliberately not yet the end state**: `Content-Security-Policy-Report-Only` is live and collecting real violation data from real traffic (browser-reported violations aren't visible to this project without a `report-uri`/`report-to` endpoint receiving them server-side — none is configured, so "check for violations" currently means re-running the CDP scan above periodically, not passively monitoring). **Do not flip this to the enforced `Content-Security-Policy` header** (replacing the Transform-Rule-set one, or having the Worker override it) **without**: (a) giving it real observation time under actual visitor traffic and diverse real browsers/devices this session's CDP-only testing can't reach (Safari's stricter behavior around synchronous script execution has bitten this project before, see the mobile Google Sign-In section above — the same "CDP-only testing missed a real-Safari-specific issue" risk class applies here too), (b) an explicit new user decision to actually enforce, given this crosses from "safe, additive, reversible-by-un-routing" into "can break the site for a real visitor if something's still wrong." If it's ever time to flip it: change the Worker to set `Content-Security-Policy` instead of (or in addition to, then eventually replacing) the existing Transform-Rule header, redeploy via `wrangler deploy`, and re-run this exact same 8-page CDP verification pass against production before considering it done — don't skip straight to enforcing based on report-only having looked clean for a short synthetic test window.

### CSP enforced in production — 2026-09-14, plus a real duplicate-header finding

User explicitly requested enforcement the same day, against this project's own stated recommendation to wait for more observation time (asked via `AskUserQuestion`, offering "wait" as the recommended option — user deliberately chose "enforce now" anyway, an informed decision, not a default). Worker redeployed: `newHeaders.set('Content-Security-Policy', csp)` (real enforced header, not report-only) + `newHeaders.delete('Content-Security-Policy-Report-Only')` + `X-CSP-Nonce-Worker: enforced`. Deployed via `wrangler deploy` (same CLI-based method as the original build — see above, don't use the dashboard editor).

**Real finding on first post-deploy check**: `curl -sD -` against the live homepage showed the `Content-Security-Policy` header present **twice** in one response — once with the Worker's fresh nonce, once without (byte-identical to the old Transform-Rule policy, no nonce). Confirmed via raw `curl -sD -` (not just `grep`, to rule out a display artifact) — genuinely two separate header lines. **Root cause**: the pre-existing Cloudflare Transform Rule (the original mechanism that set the enforced CSP header before this Worker existed, referenced throughout the section above) is still active and still firing in addition to the Worker — it was never disabled when the Worker took over the job. The Worker's own `Headers.set()` only ever produces one instance from its own response construction; the second header is added by Cloudflare's Transform Rule layer running after/alongside the Worker, outside the Worker's control.

**Verified safe via real CSP semantics + a real-browser test, not just eyeballing headers**: per spec, multiple same-named `Content-Security-Policy` headers are combined with **intersection (AND) semantics** — a resource must satisfy every delivered policy simultaneously. Because the nonce-bearing policy strips `'unsafe-inline'` for itself once a nonce-source is present (CSP-3 graceful degradation, the same mechanism this Worker was built around from the start), an inline script must carry the correct nonce to satisfy *that* policy even though the second (no-nonce) policy would separately allow it via `'unsafe-inline'` — so the stricter, nonce-requiring policy still governs in practice, not just in theory. **This was then confirmed empirically**, not left as pure reasoning: ran a real headless-Chrome CDP script (`verify_enforced.js`, scratchpad) across the same 8 page types used throughout this project's CSP verification (homepage, salary-calculator, om/, jo/, jo/games/jordan-quiz/, kids-math.html, file-converter.html, currency-converter.html) — **zero CSP violations, zero JS errors, exactly one `<h1>` on every page, real body content present, and every inline `<script>` (without a `src`) correctly carrying the nonce attribute** (`scriptsWithNonce` matched the count of src-less scripts on every page). Enforcement is genuinely safe in its current (duplicate-header) state.

**Not yet fixed — a real but non-urgent cleanup item**: removing the now-redundant Transform Rule (or changing its action so it no longer double-sets the header) needs either Cloudflare dashboard access or an API token with Rulesets edit permission. The OAuth token from `wrangler login` (stored in `default.toml`, scopes include `zone:read` but nothing ruleset-related) was tried directly against `GET /zones/{id}/rulesets/phases/http_response_headers_transform/entrypoint` and got a `10000 Authentication error` — Wrangler's own scope list doesn't cover zone Rulesets at all, confirmed by direct API test rather than assumed from the scope names. **If this is worth cleaning up later**: either ask the user to remove/disable the old Transform Rule via the dashboard (Rules → Transform Rules → HTTP Response Header Modification, the zone is `adawati.space`, zone ID `c19e645c4ee42690f7cb4474c97c61bb`), or mint a proper Cloudflare API Token (not an OAuth Wrangler login) scoped to `Zone > Transform Rules > Edit` if API-driven cleanup is ever wanted. Since real-browser testing already proves this is functionally harmless, this is a hygiene item, not a safety item — don't treat it as blocking.

**Full scope of the duplication, confirmed 2026-09-14 via an external QA report's claim, verified directly rather than trusted**: the same Transform Rule duplicates not just CSP but the **entire standard security-header bundle** — `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Permissions-Policy`, and `Referrer-Policy` are each present **twice, byte-identical**, confirmed via `curl -sD -` showing two literal copies of each line. Unlike the CSP pair (two *different* policy strings, safe only via AND-semantics reasoning + empirical browser testing), these 5 are exact duplicates of the same value — a duplicate identical header is a functional no-op for every browser (no divergent semantics possible when both copies say the same thing), so this adds no risk beyond being untidy. Root cause is the same pre-existing Transform Rule, not a separate issue — fixing the one Transform Rule (see above) would clean up all 6 headers at once. The same report also flagged 2 leftover `.onclick = fn` **property assignments** in `currency-converter.html` (quick-currency buttons, FAQ toggle) — converted to `addEventListener` for consistency with the rest of the onclick-refactor project, though note property-assigned handlers were never a CSP risk in the first place (unlike HTML `onclick="..."` attributes, `.onclick = fn` executes as normal JS and needs no nonce) — this was a style-consistency fix, not a security fix.


## Cloudflare edge-cache staleness — hit again 2026-09-14, still no purge access

Reconfirms the exact pattern already documented in the Lighthouse section above ("Cloudflare caches per-URL lazily on first request... applies to any file now that Cloudflare proxies the site") — hit twice more this session, on `style.css` (the mobile-nav fix above) and `jo/games/quiz-engine.js` (the share-image feature below). Both times: the live git tree + a direct cache-busted `curl` confirmed the origin had the correct new content within seconds of pushing, but the bare (no query string) URL kept serving pre-fix content, `cf-cache-status: HIT`, for several minutes at minimum (`max-age=14400` = 4 hours is the theoretical worst case without a purge).

**New finding this round: tried a direct Cloudflare API cache-purge call** (`POST /zones/{id}/purge_cache`) using the same `wrangler login` OAuth token already on file — **also rejected with the same `10000 Authentication error` as the Rulesets-edit attempt documented in the CSP section**, confirming Wrangler's OAuth scope grant covers Workers/Pages/D1/etc. but not `Zone.Cache Purge` either. **This session has no way to force-refresh Cloudflare's edge cache after a push** — the same access gap as the Transform Rule cleanup, just for a different Cloudflare permission. Asked the user directly to purge (Dashboard → Caching → Configuration → Purge Everything, or a custom purge of the specific changed file) — this takes them seconds and is the only way to close the propagation gap immediately; otherwise it self-resolves within the `max-age` window.

**If this keeps recurring and is worth solving properly**: either (a) the user grants a Cloudflare API Token scoped to `Zone > Cache Purge > Purge` (much narrower and lower-risk than the Rulesets-edit access that CSP cleanup would need), or (b) a Cache Rule change lowering `style.css`/`quiz-engine.js`/other actively-edited files' edge TTL specifically (the existing "Respect origin TTL" Cache Rule mentioned in the Lighthouse section only bounds it by the origin's own `Cache-Control: max-age=14400`, which is itself the long window causing this). Until either happens, **always verify a CSS/JS fix with a cache-busted fetch (`?bust=<random>`) rather than a bare URL**, and expect that bare-URL behavioral testing (via CDP navigation, which can't easily add a cache-buster to sub-resource requests) may show stale results for a while after any push touching a frequently-fetched shared asset — this is a known, recurring, currently-unfixable-by-this-session propagation lag, not a sign the push itself failed.
