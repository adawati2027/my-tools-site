# Firebase Auth, favorites/recent sync, Google Sign-In (desktop + mobile)

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## User accounts (Firebase Auth) + cross-device favorites/recent sync — built 2026-09-09

Implemented per the approved plan (email+password + Google, staged Phase 1/2/3 — see `functional-squishing-stearns` plan if it still exists locally). All in `i18n.js`: `FIREBASE_CONFIG` const, `loadFirebaseAuth()` (lazy-loads firebase-app/auth/firestore compat SDKs v10.13.2, function-scoped only — never call at module scope, `build-lang-pages.js` evaluates the whole file in a Node `vm` sandbox with no `firebase` global), `onAuthSuccessSync()`/`syncFavsToCloud()`/`syncRecentToCloud()`/`mergeArraysUnion()` (union-merge on login, localStorage stays primary/synchronous, Firestore writes are non-blocking `.catch(()=>{})`-guarded), `restoreSessionIfAny()` (background silent restore via `localStorage.adawati_uid` flag), `injectAuthBtn()`/`updateAuthBtn()`/`openAuthModal()`/`submitAuthForm()`/`signInGoogle()`/`logoutUser()`. Firestore rule added: `users/{uid}` owner-only read/write, array-size-capped (favorites ≤200, recent ≤6).

**`signInGoogle(lang)` branches on `window.Capacitor.Plugins.FirebaseAuthentication`** — inside the native app it calls the native plugin's `signInWithGoogle()` (bypasses the WebView `disallowed_useragent` block that kills the standard `signInWithPopup()` there), gets an `idToken`, builds a `firebase.auth.GoogleAuthProvider.credential(idToken)`, and signs into the JS SDK via `signInWithCredential()` so the rest of the auth code (`onAuthSuccessSync` etc.) stays uniform regardless of platform. On the plain website it falls back to `signInWithPopup()`. `@capacitor-firebase/authentication` is installed in `adawati-app`'s `package.json`; Android's `google-services.json` is in place with the release keystore's SHA-1 registered in Firebase console (`1ef2f808f4df3dbce0f519ca8234e8d2dd651c7d`). **iOS native Google Sign-In not done** — same "no Mac" blocker as all other iOS native work.

`sw.js` bypasses Auth/Firestore/Google domains entirely in the fetch handler (`www.gstatic.com`, `identitytoolkit.googleapis.com`, `securetoken.googleapis.com`, `firestore.googleapis.com`, `accounts.google.com`, `apis.google.com`) — these are POSTs, `Cache.put()` throws on non-GET.

**Gradle/JDK gotcha hit while rebuilding the Android app for this**: Gradle 8.14.3 cannot run under Java 25 (`Unsupported class file major version 69`) — Android Studio's bundled JBR is Java 25. Use a real JDK 17-21 instead: `C:\Program Files\Microsoft\jdk-21.0.12.101-hotspot` is already installed on this machine and works (`JAVA_HOME` env var before `gradlew.bat assembleRelease`). Don't download a fresh JDK without checking for an existing one first.


## Google Sign-In `auth/unauthorized-domain` — fixed 2026-09-09

After shipping the Google Sign-In UI (see above), a live click on the "Sign in with Google" button on the actual site failed with a generic "Something went wrong" toast — no code path bug, the real Firebase error (confirmed by calling `signInWithPopup` directly via a live Chrome DevTools Protocol session and reading `err.code`) was **`auth/unauthorized-domain`**: `adawati.space` was never added to Firebase Auth's **Authorized domains** list (Authentication → Settings → Authorized domains in the Firebase console) — only `localhost`, `adawati-challenges.firebaseapp.com`, and `adawati-challenges.web.app` were present by default. Firebase does not auto-add a custom domain just because GitHub Pages/DNS is configured for it; this is a separate manual step. **Fixed by adding `adawati.space` as a Custom authorized domain via the console** (confirmed live — `signInWithPopup` now opens a real `accounts.google.com` sign-in popup instead of erroring immediately). If Google Sign-In ever breaks again with a generic error, check this list first before assuming a code regression.

**CDP typing gotcha hit while fixing this**: typing into the domain-add dialog's input using `Input.dispatchKeyEvent` with both a `keyDown` (carrying `text`) and a separate `char` event for the same character double-inserts every character (Chrome processes `text` on `keyDown` *and* the `char` event as two separate insertions) — produced `"aaddaawwaattii..ssppaaccee"` from `"adawati.space"`. **Use `Input.insertText` for typing into a field, not manual `keyDown`+`char` event pairs** — a single `Input.insertText` call after a real (coordinate-based `Input.dispatchMouseEvent`, not `.click()`) click into the field worked correctly and is the simpler, correct approach; this reconfirms the same lesson noted elsewhere in this file about the Firestore Rules Monaco editor, just for a plain `<input>` this time.


## Google Sign-In on mobile — signInWithRedirect doesn't work here, popup is the fix — 2026-09-10

After the `auth/unauthorized-domain` fix above, Google Sign-In worked on desktop Chrome but the user reported it still didn't work from a real phone. **First attempt (wrong): switched to `signInWithRedirect` for mobile user agents**, following Firebase's generic advice that popups are unreliable on mobile web. This made things worse, not better, and was reverted the same day — **do not reintroduce a mobile-UA → `signInWithRedirect` branch without re-reading this note.**

**How it was actually diagnosed**: emulated a real mobile browser via Chrome DevTools Protocol (`Emulation.setUserAgentOverride` with a real iPhone Safari UA string + `Emulation.setDeviceMetricsOverride` for a mobile viewport, on the *same* `76B...` CDP page target used throughout this session) rather than guessing from code review. Traced the full navigation chain (`Page.frameNavigated` events) through a real `signInWithRedirect()` call: `adawati.space` → Google's account chooser (silently auto-approved, since the test account already had an active session — `prompt=none` in the returned OAuth params) → `adawati-challenges.firebaseapp.com/__/auth/handler` (received a real OAuth `code` from Google) → back to `adawati.space`. **The OAuth exchange genuinely completes server-side** — Google issues a real authorization code — but `firebase.auth().getRedirectResult()` on the landing page resolves to `{user: null, credential: null}` with **no thrown error**, and `firebase.auth().currentUser` stays null. Tried the standard documented fix (explicit `authInst.setPersistence(firebase.auth.Auth.Persistence.LOCAL)`, awaited before any auth call, added to `loadFirebaseAuth()` in `i18n.js`) — **did not resolve it**; re-traced the identical flow afterward and got the identical null result. Root cause not fully isolated beyond "this compat SDK version's redirect-state correlation across the hard page reload doesn't survive intact in this environment" — not worth more time chasing blind once a working alternative was confirmed.

**The fix**: reverted `signInGoogle()` in `i18n.js` to use `signInWithPopup()` as the primary path on **every** platform (removed the `/Android|iPhone|iPad|iPod|Mobile/i.test(navigator.userAgent)` branch entirely) — `signInWithRedirect` is kept only as a last-resort fallback, triggered solely on an actual `auth/popup-blocked` or `auth/operation-not-supported-in-this-environment` error from the popup attempt, not proactively. **Verified working end-to-end under the same mobile CDP emulation**: triggered the real `signInGoogle()` function (not a direct SDK call) via the actual UI button, polled state every 1.5s — sign-in completed at ~t+4.5s (SDK load + popup + silent Google auth), nav button updated to `👤 Ahmed`, modal closed; reloaded the page and confirmed the session persisted (`authNavBtn` still showed the signed-in state on a fresh load). This is the second time in this project popup has been proven reliable end-to-end on the account used to test it (also verified on plain desktop Chrome earlier the same day) — trust it over Firebase's generic mobile-web guidance for this specific app/SDK-version combination.

**Also fixed while here**: `checkGoogleRedirectResult()` (the handler for the now-fallback-only redirect path) used to silently do nothing when `getRedirectResult()` came back with no user — exactly the failure mode traced above, and exactly why the user's original report was "nothing happens," not a visible error. It now shows the generic error toast in that case instead of failing silently.

**If mobile sign-in is ever reported broken again**: don't reach for `signInWithRedirect` reflexively — reproduce first via CDP mobile emulation (steps above) and get the actual `err.code`/state trace before changing anything, the same way this was actually root-caused rather than guessed at twice in a row.

**Immediately after reverting to popup, the user still hit "Something went wrong" on a real phone** — the CDP mobile-emulation tests above kept passing because desktop Chrome (even with an iPhone UA string) doesn't enforce real iOS Safari's strict popup-blocking rule: Safari requires `window.open()` to happen *synchronously within the click handler*, not after any `await`/`.then()` — even a fast one. `signInGoogle()`'s original code called `loadFirebaseAuth()` (which fetches 3 external SDK scripts over the network on a cold load) and only called `signInWithPopup()` after that promise resolved, so on a real phone's first attempt the popup call landed too late and Safari silently killed it — this is invisible to CDP-driven Chrome testing since Chrome doesn't apply the same timing strictness, which is exactly why this needed a real-device report to surface at all.

**The actual fix**: `openAuthModal()` now calls `loadFirebaseAuth().catch(function(){})` (fire-and-forget) the moment the modal opens, *before* the user has even seen the Google button, instead of the SDK load being lazily triggered only inside the Google button's own click handler. By the time the user actually taps "Sign in with Google," `loadFirebaseAuth()`'s cached promise (`_fbAuthReady`) is normally already resolved, so `signInWithPopup()` fires synchronously within that click's activation window instead of after a network round trip. **User-confirmed working on their real phone** after this change (2026-09-10) — this is the fix that actually mattered, not the popup-vs-redirect reversion above (that was a real, necessary fix too, but on its own wasn't sufficient for a cold first load on real Safari).

**Lesson for next time**: when a fix "tests clean" via CDP mobile-UA emulation but a real user still hits the bug, don't conclude the emulation must be wrong somewhere subtle in the app logic — consider whether the failure depends on a *browser engine timing/security behavior* that UA spoofing on a different engine (Chrome here) simply cannot reproduce, and reason about the underlying platform constraint (Safari's synchronous-user-activation rule for popups is a well-known one) rather than re-debugging the same code path again.
