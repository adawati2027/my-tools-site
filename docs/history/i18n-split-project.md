## i18n.js split into per-language packs, lazy-loaded — built 2026-09-21

Deferred idea from the 2026-09-16 audit (`i18n.js` was ~372KB/3,148 lines, loaded in full on every page regardless of which of the 6 languages a visitor actually needed) — picked up per explicit user request. Split the giant `const T = {ar:{...}, en:{...}, ...}` object (lines 12-1365, the bulk of the file's byte weight) into 6 standalone files — `i18n-lang-ar.js`/`en`/`fr`/`es`/`de`/`ru.js`, each doing `window.T = window.T || {}; window.T.<code> = {...};`. Core `i18n.js` dropped from ~375KB to ~131KB (all the actual logic — auth, favorites, dark mode, export-image, PWA, etc. — which every page needs regardless of language, so it stays in the shared core).

**Lazy-load mechanism, zero page-template changes required for correctness** (a key design win — this did NOT need touching all 300+ pages to work correctly, only `i18n.js` itself): `loadLangPack(lang)` dynamically injects `<script src="{I18N_BASE}i18n-lang-{lang}.js">` and returns a Promise; `I18N_BASE` is derived once at parse time from `document.currentScript.src` (stripping the trailing `i18n.js` filename) — this correctly resolves relative to however that specific page loaded `i18n.js` (bare `i18n.js`, `../i18n.js`, or an absolute base-href-resolved URL), no per-page-type special-casing needed. `setLang(lang)` — called both by the main init sequence and by every page's own dropdown-click wiring (`setLang(a.dataset.lang)`, present verbatim in ~300 pages' own inline scripts) — now self-defers: `if (!T[lang]) { loadLangPack(lang).then(() => setLang(lang)); return; }`, then re-invokes itself once loaded. Since the function name/signature is unchanged, none of those ~300 pages' own wiring code needed editing.

**A whole-init-sequence correctness fix was needed, not just `setLang()` itself**: several other `DOMContentLoaded`-time functions (`renderFAQ`, `updateAuthBtn`, `injectStarBtns`) also read `T[lang]` directly, not just `setLang()`'s own body — if only `setLang()` were made lazy-aware, these would run against an empty `T` on first page load (since no page ships a pack synchronously) and either throw or silently render nothing. Fixed by wrapping the **entire** original `DOMContentLoaded` init sequence into `_initAfterLangReady()`, and only calling it once `T[detectDefaultLang()]` is confirmed loaded (loading it first if not) — this protects every T-dependent init function uniformly rather than patching each one individually.

**Real bug found and fixed during the split, would have broken production if shipped as-is**: a *separate*, scattered block of 6 lines (`T.en.pct_seo_html = '...'; T.ar.pct_seo_html = '...'; ...`) existed **after** the main `const T = {...}` object closed — added by an earlier session for percentage-calculator's SEO content, relying on `T.en`/`T.ar`/etc. already being fully populated synchronously (true in the original file, since the whole `const T` literal ran as one atomic block). After the split, `T.en` doesn't exist yet at that point in the file — `T.en.pct_seo_html = ...` threw `TypeError: Cannot set properties of undefined`. **Caught via local CDP testing before pushing** (an `exceptionThrown` listener during a scripted page load, not a syntax check — `node --check` alone would never catch this since it's valid JS, just a runtime-order assumption). Fixed by moving each of those 6 lines into its matching `i18n-lang-<code>.js` file (appended after that file's own `window.T.<code> = {...}` assignment, so the target object already exists by the time the line runs). **Lesson if this pattern is ever extended: grep the whole file for `T\.\w+\.\w+\s*=` (bare `T.<lang>.<key> = ...` assignments, not `T[lang]` reads) before trusting a single-boundary extraction — any such assignment sitting outside the main object literal needs to move into its matching lang-pack file too.** Confirmed via the same grep that no other such assignment exists anywhere else in the file, and confirmed (via a separate grep across all ~300 HTML files' own inline scripts) that none of them use bare `T.ar.`/`T.en.` etc. either — the established, safe, already-documented pattern used by every page (`tip-calculator.html`, `currency-converter.html`, etc.) is exclusively the defensive `(typeof T!=='undefined' && T[lang]) ? T[lang] : {}` runtime read, which is safe under this lazy-load model since it only ever executes on user interaction (e.g. an export-image button click), by which point the active language's pack is guaranteed loaded by the init sequence above.

**`build-lang-pages.js` compatibility verified, not assumed**: this script evaluates the whole of `i18n.js` in a Node `vm` sandbox (with mocked `document`/`window`) to extract `PAGE_META` at build time (see the i18n Auth section elsewhere in this file for why `loadFirebaseAuth()` must stay function-scoped for the same reason). The sandbox's `document` stub has no `currentScript` property at all — confirmed this resolves to `undefined` safely (my own `I18N_BASE` IIFE already wraps the read in try/catch and falls back to `''`), so the vm-eval doesn't throw and `PAGE_META` extraction is unaffected — re-ran `build-lang-pages.js` after the split and confirmed identical output (same 30 tools list) before and after.

**`sw.js` updated**: added `/i18n-lang-(ar|en|fr|es|de|ru)\.js$/` to the same network-first `isCore` bucket as `i18n.js`/`style.css`/`quiz-engine.js`/`search-index.json` (bumped `CACHE` to `adawati-v63`) — these are exactly the "actively edited shared JS" class of file the cache-staleness lesson elsewhere in this file already warns about; cache-first would risk shipping a stale lang pack indefinitely to a returning visitor. Also added `i18n-lang-en.js` and `i18n-lang-ar.js` to the `STATIC` precache list (the homepage's default + the majority-default for Arabic-first country hubs) — a deliberate, reasonable baseline for the offline-PWA scenario, not exhaustive: an offline-first-ever-visit in a language other than en/ar (e.g. a French visitor who's never been online on this site before) won't have a pack cached yet, same class of limitation any non-precached asset already has.

**Verified live against production** (not just locally) — 4 page types (global homepage, salary-calculator, om hub, jo hub) all correctly loaded only their own needed language pack (`loadedLangs` in each case was a single-element array matching the page's actual language), zero JS exceptions. `test-calculators.js` (20/20) and `test-e2e.js` (29/29, after one test fix — see below) both re-run clean against live production.

**One real, expected test-suite update needed, not a site bug**: `test-e2e.js`'s "switching to Arabic" check clicked the language-menu Arabic option and read `document.documentElement.lang` in the *same synchronous eval*, with zero wait — valid when `setLang()` was always fully synchronous, but a switch to a non-default language now genuinely triggers a network fetch (`loadLangPack`) before applying. Fixed by splitting that test into two evals with a `s.wait(1500)` between the click and the read, matching how a real user's browser actually behaves (sees the correct language within one fetch round-trip, not instantly) — this is the test catching up to an intentional behavior change, not evidence of a regression.

**Current state — a real, live, verified win already, but not yet the fully-optimized end state**: every page now downloads only ONE language pack instead of all 6 (e.g., an English visitor gets ~131KB core + ~52KB en pack ≈ 183KB vs the old 375KB single file; a French/German/Russian/Spanish visitor gets an even bigger cut, ~131KB + ~25-35KB ≈ 156-166KB). **But since no page yet ships its own default-language pack as a static `<script>` tag, every single page load currently takes the "cold" lazy-fetch path** (`i18n.js` loads → `detectDefaultLang()` runs → `T[lang]` missing → dynamically fetch the pack → apply) — this adds one extra *sequential* network round-trip to the translation-rendering path on every page, which a same-directory static `<script src="i18n-lang-{default}.js" defer>` tag (loaded in parallel with `i18n.js` itself, before it in document order) would eliminate for the common case (visitor viewing a page in its own natural default language, which is the large majority of traffic). **This is the natural next phase, deliberately not attempted in this same session**: it requires editing all ~300 HTML files (root tool pages + `build-lang-pages.js`-generated lang variants + country hubs + country-module pages + nationality-landing pages — each needs the correct per-page-type default language determined and a correctly-relative-pathed tag inserted before its existing `i18n.js` tag), which is exactly the kind of large, many-file, rate-limit-prone batch rollout this project always stages carefully (matching the onclick-refactor and OG-image projects' own multi-batch discipline) rather than attempting in one shot. **If picked up**: default language per page-type is already fully known (lang-variant folders `/ar//fr//es//de//ru/` = that language; `jo/om/sa` + the 5 nationality-landing pages = ar; `ae/us/uk` = en; bare root pages = en — matches the already-established `localStorage.setItem` default-language convention documented in the cross-hub mixed-language-bug sections above), so the only real engineering work is a batch script inserting the correctly-relative-pathed static tag per file family, then the usual validate → functionally test → push-in-batches → blob-sha-verify cycle.


## i18n.js split, Phase 2 — static per-page pack tags rolled out site-wide, 2026-09-21

Completed the same day as the Phase 1 core split above, per explicit user follow-up ("كمل"). This closes the gap Phase 1 deliberately left open: every page now ships its own default-language pack as a static `<script defer>` tag placed immediately before `i18n.js`, so the common case (a visitor viewing a page in its own natural default language — the large majority of traffic) loads translations **synchronously in parallel** with `i18n.js` itself, with **zero dynamic fetch** — the lazy-load mechanism built in Phase 1 now only actually engages when a visitor's stored language choice differs from a given page's own default (e.g. an Arabic-preferring visitor on an English-default root tool page).

**30 `build-lang-pages.js` `TOOLS` root files**: all confirmed `<html lang="en">` (verified via a direct grep sweep, not assumed), so all 30 got a hardcoded `<script src="i18n-lang-en.js?v=1" defer></script>` inserted before their existing `i18n.js` tag via a small batch script.

**`build-lang-pages.js` itself updated** with a new substitution step (`g.`) that rewrites `i18n-lang-en.js` → `i18n-lang-{code}.js` per generated variant — since the root file's body (now carrying the hardcoded 'en' pack tag) gets copied verbatim into each of the 5 lang-variant files, without this substitution every `/ar//fr//es//de//ru/` variant would have silently shipped the wrong (English) static pack. Re-ran `build-lang-pages.js` and confirmed via spot-check that `ar/age-calculator/index.html` correctly got `i18n-lang-ar.js`, `fr/age-calculator/index.html` got `i18n-lang-fr.js`, etc. — all 150 variants regenerated correctly in one pass.

**114 hand-maintained pages** (country hubs, country-module pages under `{om,sa,ae,us,uk,jo}/calculators/`+daily-info folders, the 5 nationality-landing pages, 9 `kids-*.html` pages, `oman-*-guide.html`, `omr-to-*.html`, `about/contact/privacy/terms.html`, `index.html`) — a generic batch script determined each file's target language by reading its own `<html lang="XX">` attribute directly (ground truth, not inferred from path — this correctly handled a case that would have been wrong by path-guessing alone: `eg/index.html` turned out to be `lang="en"` by default, not `ar` as a naive "nationality pages are Arabic" assumption would have guessed) and inserted the pack tag using the **exact same relative path prefix** as that file's own existing `i18n.js` reference (bare `i18n.js`, `../i18n.js`, etc., regardless of nesting depth or `<base href>` presence) — this correctly handles every path convention already in use across the site without needing per-directory-depth special-casing, since `I18N_BASE` (added in Phase 1) is itself already derived from wherever `i18n.js` actually loaded from.

**Explicitly excluded, unchanged**: the 15 `jo/games/*` + `wordle/` pages, which don't load `i18n.js` at all (by design, see the "In-page English translation system" section above) — confirmed 16 files (not 15) correctly fell into the "no i18n.js" bucket during the initial site-wide scan (the 16th being `wordle/index.html`).

**Verification, in order**: (1) syntax/div-balance/JSON-LD validation across all 114 hand-maintained files (0 errors) plus the earlier 30+150 TOOLS-family files (0 errors); (2) local CDP test confirming the fast path actually engages — network-request logging showed exactly 2 i18n-related requests per page load (the static pack + `i18n.js` itself, both declared statically, zero runtime-injected `<script>` elements) on both a root tool page and a `kids-*` page; (3) pushed all 295 files (30 modified TOOLS root files + 150 regenerated lang variants + 114 hand-maintained files + `build-lang-pages.js`) in a single batched push — the largest this project has done (previous largest was 452 files for the OG-image project) — using the established batched-blob-with-retry pattern (500ms pacing, up to 5 retries per blob, one combined tree+commit at the end); **0 blob failures across all 295 files**, no GitHub secondary-rate-limit issues hit this time; (4) verified live via the full blob-sha tree-diff script — **0 mismatches across all 295 files**; (5) re-ran the exact same network-request-logging CDP test against **live production** on 9 diverse page types (global homepage, a root tool, `om/index.html`, `jo/index.html`, a Saudi country-module page, a currency-landing page, a kids page, an Oman guide page, and `eg/index.html`) — every single one showed exactly 2 static i18n-related requests, zero dynamic fetches, zero JS exceptions, correctly matching each page's own actual default language (including confirming `eg/index.html` really is `lang="en"` by default, validating the "read `<html lang>` directly rather than guess from path" design choice); (6) all 305 live sitemap URLs re-checked via `curl`, 0 failures; (7) `test-calculators.js` (20/20) and `test-e2e.js` (29/29) both re-run clean against live production.

**This closes the i18n.js split project end-to-end** — both phases (core split + lazy-load mechanism, then site-wide static pack tags for the zero-extra-round-trip fast path) are now live, verified, and documented. Real numbers: an English visitor on a typical page now downloads ~131KB (core) + ~52KB (en pack) ≈ 183KB instead of the original single 375KB file; a French/German/Russian/Spanish visitor gets an even bigger cut, ~131KB + ~25-35KB ≈ 156-166KB — all with zero added network round-trips versus the pre-split single-file behavior, since both the core and the matching pack now load in parallel via `defer`, in document order.

**If a new page is added in the future**: give it a `<script src="{same-prefix-as-i18n.js}i18n-lang-{its-default-lang}.js?v=1" defer></script>` tag immediately before its `i18n.js` tag, matching its own `<html lang>` attribute — skip this only for pages that don't load `i18n.js` at all (the `jo/games/*` family). If it's a new `build-lang-pages.js` `TOOLS` entry, the root file's tag should hardcode `i18n-lang-en.js` (matching every other root tool's own default) and the existing substitution step in `build-lang-pages.js` will automatically retarget it correctly for each generated variant — no further changes needed there.
