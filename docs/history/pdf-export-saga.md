# Loan-calculator amortization CSV/PDF export — the full 6-round mobile bug saga

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## Loan calculator — CSV/PDF export for the amortization schedule, built 2026-09-21

User requested export buttons for the full amortization table (`#amort-body`) on `loan-calculator.html`. Added two buttons (`#amortCsvBtn`/`#amortPdfBtn`) below the table.

**CSV**: pure client-side, no library — reads the already-rendered table rows via `getAmortRows()`, builds a properly-escaped (quoted fields containing commas, e.g. `"4,870.98"`) CSV string with a UTF-8 BOM prefix (so Excel opens Arabic headers/content correctly) and triggers download via `Blob` + `<a download>`.

**PDF — a real, reproducible jsPDF bug found and worked around, not a quick copy of the existing file-converter.html pattern.** The obvious approach (matching `file-converter.html`'s existing `xlsxToPdf()`/`csvToPdf()`, which build an off-screen `<div style="position:fixed;left:-9999px">` table and call jsPDF 2.5.1's own `doc.html(el, {..., autoPaging:'text'})` convenience method) produces a **PDF with real, correctly-encoded text content that renders completely blank** — confirmed by direct inspection of the PDF's raw content stream (not just visual testing, since Chrome's own PDF.js viewer doesn't reliably paint on CDP screenshots in headless automation either, which nearly caused a false read here). **Root cause, found by reading the actual PDF byte content**: `doc.html()` internally re-invokes `html2canvas` once per internal chunk for content taller than a single capture pass (independent of `autoPaging`, and independent of chunking rows into smaller groups — even a 20-row chunk triggered it, while a hand-verified 2-row chunk didn't) — and every chunk after the first ignores the source element's actual on-page position, producing content drawn at wildly negative coordinates (~-7472 PDF points, matching `-9999px × ~0.75pt/px`) that lands thousands of points off the visible page. The `html2canvas:{scrollX:0,scrollY:0}` option (a commonly-cited community fix for a related jsPDF/html2canvas coordinate issue) only fixed the *first* chunk, not subsequent ones — confirmed not a full fix by re-inspecting coordinates after applying it.

**Actual fix**: bypass jsPDF's `.html()` wrapper entirely. Call `html2canvas()` **directly** on the off-screen table div (proven reliable at any content height — visually verified rendering a full 36-row table correctly as a single 718×1040px canvas), then **slice the resulting canvas ourselves** into page-sized chunks (`Math.floor((297-20)mm × (718/190)px-per-mm)` ≈ 1047px per A4 page) via a scratch `<canvas>` + `ctx.drawImage(source, 0, y, w, sliceH, 0, 0, w, sliceH)`, and place each slice with `doc.addImage()` (adding `doc.addPage()` between slices) — a completely different jsPDF code path from `.html()` that has no coordinate-carryover bug, since each `addImage()` call gets an explicit, correct `x`/`y` we control directly.

**Second, real, independently-found problem while testing this: PNG output was enormous** — a 36-row single-page PDF was 2.9MB (all from one losslessly-compressed PNG image of a plain bordered table), and a 360-row/10-page test (30-year loan) produced a 37MB file before this was caught — clearly impractical to generate/download. **Fixed** by switching to JPEG at quality 0.85 (`canvas.toDataURL('image/jpeg', 0.85)` + `doc.addImage(..., 'JPEG', ...)`) — cut the 36-row case to 146KB (20x smaller) and the 360-row/10-page case to 1.28MB, with no visible quality loss for this content type (solid-color borders and dark text on a white background, exactly what JPEG handles well).

**Verification, in order**: (1) syntax + div-balance validated; (2) local CDP test confirmed real CSV content (correct headers, correct escaping, correct computed values matching `test-calculators.js`'s own independently-derived 149.85/mo expected value for the same 5000/5%/3y inputs); (3) direct PDF byte-content inspection (not just visual) confirmed the buggy `.html()` coordinates, confirmed the `addImage()`-based rewrite produces sane positive on-page coordinates throughout; (4) visual verification via three extracted canvas slices from a real 30-year/360-row/10-page run (first page, a page-boundary-straddling middle page, and the last page) — page breaks land cleanly with no row split/duplicated across the boundary, Arabic RTL column order and text render correctly, final row 360 correctly shows a 0.00 remaining balance; (5) pushed as 6 files (root + 5 lang variants), verified live via blob-sha diff (0 mismatches); (6) **a real GitHub Pages build-lag + Cloudflare edge-propagation false alarm hit and resolved during production verification** — a fresh-profile CDP navigation to the bare live URL showed the new button missing (`hasBtn:false`) even though the git tree diff was clean; traced via `GET /repos/.../pages/builds/latest` showing `"status":"building"` for the exact pushed commit SHA, waited ~55s polling until `"status":"built"`, then a cache-busted (`?bust=<timestamp>`) navigation confirmed the button present and the full CSV+PDF flow (including a real `.click()` on `#amortPdfBtn`) working end-to-end with 0 JS exceptions — matches the already-documented "verify a fix with a cache-busted fetch, not a bare URL, immediately after a push" lesson elsewhere in this file, this time triggered by Pages build lag rather than Cloudflare's edge cache specifically. `test-calculators.js` (20/20) re-run clean afterward.

**If this canvas-slicing + addImage pattern is useful elsewhere**: it's a more robust general-purpose "long HTML table → paginated PDF" building block than jsPDF's own `.html()`/`autoPaging` for any table that might exceed roughly one page's worth of content — worth reaching for directly next time rather than re-discovering this same `.html()` bug. `file-converter.html`'s own `xlsxToPdf()`/`csvToPdf()` use the exact same `.html()`+`autoPaging:'text'` pattern that was just shown to be broken for tall content — **not fixed as part of this task** (out of scope, a different feature, would need its own dedicated verification pass), but flagged here since it's now a known, real, likely-still-present bug there too if a user ever converts a sufficiently long spreadsheet/CSV to PDF.


## Amortization export — fixed for mobile (real device report), 2026-09-21

User-reported: PDF export "not working" on a real iPhone, right after the CSV/PDF feature above shipped — invisible in every round of this session's own automated testing (headless Chrome). Root cause, diagnosed from this project's own established playbook for this exact failure class (see the Google Sign-In mobile sections above) rather than guessing blind:

1. **Both exports only used `<a download>`** — Mobile Safari doesn't reliably honor the `download` attribute for blob URLs (a long-standing WebKit limitation); some versions just navigate to/preview the blob instead of saving a file. The site already has a proven fix for exactly this, already shipped and working on 6+ calculators: `exportResultImage()` in `i18n.js` tries `navigator.share({files:[...]})` first (opens the real native share sheet, where "Save to Files"/"Save Image" actually works) and only falls back to `<a download>` when file-sharing isn't supported. Neither `exportAmortCSV()` nor `exportAmortPDF()` used this pattern — added a shared `downloadOrShare(blob, filename, mime)` helper doing exactly that, and switched both exports to call it.

2. **PDF export specifically had a second, independent risk**: its async chain before reaching the share/download step is much longer than `exportResultImage()`'s (2 CDN script loads for html2canvas+jsPDF on first use, then the html2canvas capture itself) — and `navigator.share()`, like `window.open()`, must be called within a live user-activation window on Safari, which a slow network-dependent async chain can outlive. This is the *exact* root cause already diagnosed and fixed for Google Sign-in on this site (see "Google Sign-In on mobile" above) — same fix applied here: `html2canvas`/`jsPDF` now start preloading (fire-and-forget) as soon as `buildAmortTable()` runs (i.e. the moment a schedule exists), not lazily inside the export click handler, so by the time a user actually taps "Export PDF" the libraries are normally already cached and the remaining work before `share()` is much shorter.

**Verified, both paths, not just one**: real headless Chrome supports `navigator.share`/`canShare` too (confirmed `canShareFiles: true`), so a plain test would only ever exercise the share branch — explicitly stubbed `navigator.canShare` to return `false` in a separate test pass to force and confirm the `<a download>` fallback branch still works correctly (both locally and, after the push, against live production with a cache-busted navigation). Confirmed the preload fires automatically right after calculation (2 network requests for the CDN scripts, before any export click). `test-calculators.js` (20/20) re-run clean afterward. **Could not verify this actually fixes the user's specific iPhone** (same standing limitation as every mobile-only bug in this project — CDP/Chrome-based testing cannot reproduce Safari's real activation-timing behavior) — ask the user to retest on the same device.


## Amortization PDF export — hardened further after user re-reported still broken, 2026-09-21

The `navigator.share`-based fix above wasn't enough — user re-tested on the same real iPhone and PDF export still didn't work. **Real gap in that fix**: it only helped devices where `navigator.canShare({files:[...]})` actually returns `true`; on any device/Safari version that doesn't support Web Share for files at all, `canShare()` correctly returns `false` and control fell straight back to the exact same `<a download>` mechanism already known to be unreliable on Mobile Safari — i.e. the fix only ever engaged its new code path some of the time, and for a device where it doesn't, nothing had actually changed.

**Investigated a specific hypothesis before treating it as confirmed**: checked whether `html2canvas` 1.4.1's internal iframe-cloning technique (confirmed present in the library source via `grep`) could be blocked by the site's CSP — `frame-src` doesn't include `'self'`, and Safari is known to enforce CSP `frame-src` for such iframes more strictly than Chrome in some cases. **Tested directly via a `securitypolicyviolation` listener installed before running the real export flow against live production** — zero violations fired, export completed successfully. This doesn't prove Safari behaves identically (CDP-based Chrome testing has already been shown elsewhere in this file to miss real Safari-only behavior), but it means this specific theory has no supporting evidence and isn't the leading explanation anymore — noted here so it isn't re-investigated from scratch if this resurfaces without new evidence.

**Real, structural fix — no longer relies on any single mechanism working**: rewrote `downloadOrShare()` into a proper 3-tier fallback chain, each tier only engaging if the one before it isn't available or fails:
1. `navigator.share({files:[...]})` when `canShare()` reports support — but now distinguishes a user-cancelled share (`AbortError`, a legitimate outcome, does nothing further) from a genuine failure (any other rejection reason, which falls through to tier 2).
2. **New tier, PDF-specific**: `window.open(blobUrl, '_blank')` — Safari has a native, fully-featured PDF viewer for content opened directly in a tab, complete with its own Share/Save-to-Files UI; this is a well-established, more reliable pattern for "let a user save a client-generated PDF on Safari" than the `download` attribute, and doesn't depend on Web Share support at all.
3. `<a download>` as the final fallback (for any browser where even `window.open` was blocked, e.g. a strict popup blocker) — unchanged from before, but now genuinely the *last* resort instead of the *only* resort.

**Also fixed a real diagnostic gap**: every failure path previously ended in an empty `.catch(function(){})` — completely silent, giving zero signal for what actually went wrong on the user's device across two rounds of "still not working" reports. Added a real `catch` block using the site's own existing `showToast(msg, 'error')` helper (already used elsewhere on the site, not a new UI pattern) plus a new `pdf_export_error` translation key (all 6 languages) — any future real failure will now show the user a visible, readable error instead of nothing happening, closing the loop for actually diagnosing this if it recurs.

**Verified all 3 tiers explicitly, not just the happy path** — local and live-production CDP tests forced each scenario in turn: (1) a thrown error inside the export (simulated `html2canvas` rejection) → confirmed the toast appears with the correct translated message; (2) `canShare` returning `false` + a successful `window.open()` → confirmed the blob URL opens directly, confirmed the `<a>` fallback path is *not* also triggered; (3) `canShare` returning `false` AND `window.open` blocked (returns `null`, simulating a strict popup blocker) → confirmed it correctly falls all the way through to `<a download>`. Pushed as 6 files (root + 5 lang variants), verified live via blob-sha diff + a GitHub Pages build-status poll (same real build-lag pattern as the previous round) + a cache-busted production CDP run reproducing all 3 scenarios with 0 exceptions. `test-calculators.js` (20/20) re-run clean.

**Still cannot fully confirm this resolves the user's exact device** — same standing limitation noted every time this class of bug comes up in this project. If reported broken a third time: the `showToast` error message (now finally visible) is the next real diagnostic lead — ask what it actually said, since that narrows down which of the 3 tiers is failing and why, rather than guessing again from scratch.


## Amortization PDF export — round 3: real error now visible, still awaiting the actual message

User retested after the 3-tier fallback shipped and got a real, visible error toast for the first time ("تعذّر إنشاء ملف PDF — جرّب مرة أخرى") — confirms `exportAmortPDF()` genuinely throws on this device, closing the "silent failure" diagnostic gap, but the message itself was still too generic to identify the cause.

**Fixed immediately**: the `catch` block now appends the real `e.message`/`e.name` to the shown toast (plus `console.error`), so the *next* report will carry the actual error text instead of the generic wrapper. **Also added a proactive, evidence-informed (not confirmed) defensive fix while waiting for that**: `html2canvas` clones the whole document internally (to compute styles reliably) — this would include any live AdSense ad iframe on a real page visit, and Safari is known to enforce canvas cross-origin tainting more strictly than Chrome; a real ad iframe (which never actually serves in this project's own automated/headless testing, since ad networks don't serve to bots) could taint the capture with a `SecurityError` that would be completely invisible to every round of testing done so far. Added `ignoreElements` to the `html2canvas()` call, skipping `<iframe>` elements and anything with an `adsbygoogle` class — harmless if this isn't the actual cause (ad content was never meant to be part of the captured table anyway), a real fix if it is. Verified the normal flow still produces a correct PDF with this filter in place (0 exceptions, no regression).

**Status**: not confirmed fixed — waiting on the user's next retry, which will now surface the real error text (or confirm success) instead of another blind round. **If reported broken again**: read the toast's exact text first — that alone should point at the real failure point (script load, html2canvas capture, jsPDF page-building, or the final `downloadOrShare` call) rather than requiring another speculative fix.


## Amortization PDF export — round 4: the real bug, found and fixed via the user's own error message

The diagnostic-message fix above paid off immediately — the user's next retry produced a genuinely useful error: `undefined is not an object (evaluating 'window.jspdf.jsPDF')`. This is a real bug in this session's own code, not a Safari quirk, and not any of the three previous (share-timing, fallback-chain, ad-taint) theories.

**Root cause**: `loadScript(src)` deduplicated by checking `document.querySelector('script[src="'+src+'"]')` — if a tag for that URL already existed, it resolved *immediately*, without waiting for that tag's own `onload`. `buildAmortTable()` preloads `html2canvas`/`jsPDF` as soon as a schedule exists (fire-and-forget, added in an earlier round of this same fix); `exportAmortPDF()` then calls `loadScript()` again for the same two URLs when the user actually taps export. On a slow connection, the *second* call sees the tag the *first* call already inserted and resolves instantly — well before that first fetch has actually finished downloading and executing — so `window.jspdf` can genuinely still be `undefined` at the point of use. This is a real race condition, invisible in this project's own low-latency test environment (where a cdnjs fetch completes near-instantly, leaving no meaningful window for the race), and exactly why it reproduced reliably on a real phone and never once in three separate rounds of automated testing.

**Fix**: cache the *load Promise* per URL (`_scriptLoadPromises[src]`), not just check for tag presence — every caller for the same URL now shares one real completion signal, resolving only when the script has actually finished loading, regardless of which call happened to insert the `<script>` tag.

**Verified by directly reproducing the exact race, not just trusting the fix**: used CDP's `Network.emulateNetworkConditions` (800ms latency, 50KB/s throughput — a genuinely slow connection, not just "a bit slower") to recreate the real-world timing gap this project's own fast connection can't produce. Two overlapping `loadScript()` calls for the same URL, 50ms apart (mirroring the real preload → click timing), both correctly resolved only once `window.jspdf` was genuinely defined. Then the *full* export flow, triggered 200ms after the table loads (deliberately inside the old race window) under the same throttle, completed cleanly with a valid PDF and zero exceptions — both locally and, after pushing, against live production with a cache-busted navigation. `test-calculators.js` (20/20) re-run clean.

**This closes the amortization-export bug thread** — unlike the three earlier rounds, this fix is backed by a direct reproduction of the failure and a direct reproduction of the fix working, not an educated guess. **Lesson for next time this class of "works in every automated test, fails on a real device" bug comes up**: getting the user to a *visible, detailed* error message (this session's own earlier fix, via `showToast` + `e.message`) was what actually broke the stalemate — three rounds of plausible-but-unconfirmed theories (share-gesture timing, fallback chain gaps, ad-iframe canvas tainting) got fixed defensively along the way and may still have had some value, but none of them were the real cause; the moment a concrete error string existed, the actual bug was identifiable and fixable within one round. **When a bug can't be reproduced locally, prioritize getting a real error message out of the user's device over guessing at more defensive fixes** — this project has hit this exact lesson before (Google Sign-In mobile) and it held again here.


## Amortization PDF export — round 5: cdnjs itself failing to load, jsdelivr fallback added

The race-condition fix (round 4) worked — the user's next retry produced a *different*, more specific error: `script failed to load: https://cdnjs.cloudflare.com/ajax/libs/html2canvas/1.4.1/html2ca...`. This confirms the race is genuinely gone (no more `undefined` property access) and surfaces a new, separate problem: `cdnjs.cloudflare.com` itself failed to load on that device/network — a real network/DNS/content-blocker-level failure for that specific host, not something reproducible or further diagnosable from this session without yet another round-trip.

**Fix**: `loadScript()` now accepts an array of fallback URLs instead of a single URL, trying each in order — cdnjs first (matching every other CDN reference already on this site, so the common case is unaffected), then `cdn.jsdelivr.net` (a different domain, already present in the site's CSP `script-src` allowlist) if the first fails. A host-specific block or outage affecting only one of the two no longer takes the whole export feature down. The cache key for `_scriptLoadPromises` is the *first* URL in the list, so the existing preload-in-`buildAmortTable()` / awaited-call-in-`exportAmortPDF()` pattern (and its race-condition fix from the round above) keeps working unchanged — both call sites reference the same shared `HTML2CANVAS_URLS`/`JSPDF_URLS` constants.

**Verified by reproducing the exact reported failure, not just adding a fallback and hoping**: used CDP's `Network.setBlockedURLs` to fully block `*cdnjs.cloudflare.com*` (a more absolute block than the user's real failure, which was presumably intermittent or host-specific rather than 100% — a stronger test than strictly necessary) — the export correctly fell through to jsdelivr and produced a valid PDF with zero exceptions, both locally and, after pushing, against live production. Re-confirmed the normal (unblocked, cdnjs-succeeds) path is completely unaffected. `test-calculators.js` (20/20) re-run clean.

**Running tally of this whole thread, for anyone picking it up if it's reported broken yet again**: round 1 (share-timing preload) and round 2 (3-tier share/window.open/download fallback + visible errors) were both defensible improvements shipped without direct confirmation of the root cause, and neither was actually it. The visible-error-message fix from round 2, however, is what let rounds 3 (ad-iframe-taint theory, unconfirmed) through 5 (the two *actual* bugs — a real `loadScript()` race condition, then a real cdnjs host failure) get diagnosed and fixed with real evidence instead of more guessing. **If this surfaces again, read the toast's exact text first** — it now carries the real `e.message`, and every fix in this thread from round 4 onward was found this way, not guessed.


## Amortization PDF export — round 6, likely the actual end of this thread: self-hosted, no external CDN dependency left

The jsdelivr-fallback fix from round 5 produced a new report: `script failed to load from all sources` — meaning **both** `cdnjs.cloudflare.com` and `cdn.jsdelivr.net` (two unrelated domains) failed to load on the same device, while the rest of the page (including other same-origin assets) rendered fine. Two independent CDN hosts both failing points at something on that device/network blocking *third-party CDN requests specifically* — a content blocker or restrictive network policy — not either CDN's own availability. A third CDN mirror would very likely hit the same wall.

**Fix, applying this project's own already-proven pattern for exactly this problem class**: downloaded genuine `html2canvas` 1.4.1 and `jsPDF` 2.5.1 (verified real — correct file headers, correct byte sizes, not error pages) and self-hosted them under `vendor/html2canvas-1.4.1.min.js` / `vendor/jspdf-2.5.1.umd.min.js`, matching the exact same reasoning and precedent as the xlsx CVE fix earlier in this file ("self-hosted instead of a CDN-allowlist change") — a same-origin static file is indistinguishable from any other site asset (`style.css`, `i18n.js`), so it sidesteps the *whole* "external CDN blocked" failure class at once, not just one specific host. `HTML2CANVAS_URLS`/`JSPDF_URLS` now list the self-hosted path first, with the two CDN URLs kept only as a last-resort fallback tier (in the unlikely case the self-hosted copy itself 404s, which would only happen if the whole site were broken anyway).

**Verified directly against the exact reported failure**: blocked *both* `cdnjs.cloudflare.com` and `jsdelivr.net` completely via CDP (`Network.setBlockedURLs`) — the self-hosted files load with zero external network dependency, confirmed via the actual network request log (`vendor/html2canvas-1.4.1.min.js` / `vendor/jspdf-2.5.1.umd.min.js`, no CDN requests at all), and export produces a valid PDF with zero exceptions — both locally and, after pushing, against live production with both CDNs still blocked. `test-calculators.js` (20/20) re-run clean.

**This is very likely the actual end of the amortization-export bug thread** — six rounds total, the last three (loadScript race → single CDN failure → both CDNs failing) each diagnosed and fixed from a real, specific error message the user's own device surfaced, not guessed. If a *seventh* report ever comes in for this specific feature, it would mean even a same-origin static-file request is failing on that device, which would point to something much more fundamental (the whole site being unreachable, a corrupted browser cache, or the device blocking `adawati.space` itself) rather than anything left to fix in this export code specifically.
