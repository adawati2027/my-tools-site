# Branded result-image export/share feature — built, extended, and its bugs

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## Branded result-image export/share, built 2026-09-09

`exportResultImage(titleText, rows)` in `i18n.js` — a shared, reusable utility for any calculator to let visitors export/share their result as a designed, WhatsApp-ready image instead of a plain screenshot. Renders entirely via Canvas 2D (no html2canvas/screenshot library — avoids adding a dependency to every page, and Arabic RTL renders correctly via `ctx.direction`). Portrait card, gradient background matching the site's existing button gradient (`#2563eb`→`#7c3aed`), "⚡ أدواتي" branding, title, each row as label+value (a `highlight:true` row — normally the final net/total figure — renders larger and in brand blue), `adawati.space` footer.

**Canvas height is computed from row count, not fixed** — `H = clamp(260 + (rowsHeight + 140) + 170, 900, 1920)`, `cardH` derived from the same (already-clamped) `H` so the two never go out of sync. A first version used a fixed 1350px height regardless of content and looked sparse/empty for short results (e.g. a 3-row percentage calc) — don't reintroduce a fixed height.

**Output path**: `canvas.toBlob()` → `File` → `navigator.share({files:[file]})` if `navigator.canShare({files:[...]})` is supported (native OS share sheet, so picking WhatsApp there attaches the image directly — this is the actual "ready for WhatsApp" delivery mechanism, not a bespoke WhatsApp integration) → falls back to a plain PNG download (`<a download>`) on desktop browsers that don't support file-sharing.

**Not automatic** — `exportResultImage()` only builds the image from a `rows` array; it doesn't read the DOM itself, since every calculator's result markup differs. Each calculator page must build its own `rows` (`[{label, value, highlight?}]`) from its already-computed result values and call it, e.g. `salary-calculator.html`'s `exportSalaryResult()` (first implementation, the reference to copy for other calculators) reads the same values `calculate()` just computed and calls `exportResultImage(t.export_title, rows)`. Needs an `export_btn`/`export_title` pair added to the page's own translation object (ar+en, matching the page's existing local-translation pattern — `salary-calculator.html` uses its own `SAL_T` object, not `i18n.js`'s `T`) and a button wired to an `on click` handler; `updateSalaryText()` (or the equivalent per-page function that re-applies translations on language switch) must also set the button's text.

**Shipped on 6 calculators so far**: `salary-calculator.html` (the reference implementation, uses its own local `SAL_T` object for the button label + title), then `bmi-calculator.html`, `percentage-calculator.html`, `loan-calculator.html`, `age-calculator.html`, `end-of-service.html` (all 6 lang variants each, regenerated via `build-lang-pages.js`). For this second batch, the button label was added **once** as a new shared key `export_img_btn` in `i18n.js`'s global `T` (all 6 languages) instead of duplicating it into each page's own local translation object — pages that already have `data-i18n` wired site-wide (all of these do) just need `data-i18n="export_img_btn"` on the button and `i18n.js`'s existing `setLang()`/`applyTranslations()` cycle translates it automatically, no per-page update-function edit needed. The image title still reads from whatever the page already displays as its own heading (`t.main_title` from a local object, or `T[lang].xxx_card_title`/`xxx_title` from the global `T` — whichever that page already uses for its `<h1>`), never a new key. `percentage-calculator.html` needed one shared `exportPercentageResult()` (not three) — it reads whichever of its 3 tabs (`res1`/`res2`/`res3`) is currently active via the `.tab.active` element's id suffix, since only one tab's result is ever visible at a time. Verified end-to-end via live Chrome DevTools Protocol sessions on two different pages (salary + percentage) — filled real values, triggered the export, captured the canvas before `toBlob()` consumed it (temporarily wrapping `HTMLCanvasElement.prototype.toBlob` to grab `toDataURL()` first), saved and visually inspected the PNG both times.

**GitHub secondary rate-limit got unusually aggressive rolling this out** (5 pages × 6 lang variants pushed in one batch) — normal single-retry-and-it-goes-through behavior didn't hold this time; 3 consecutive full-tree pushes each still left 1-2 specific lang-variant files un-blobbed (`ru/end-of-service/index.html`, then repeatedly `ru/percentage-calculator/index.html`). Confirmed via a direct single-blob API call that the *real* hourly quota was nowhere near exhausted (885/5000 remaining) — it was purely the secondary abuse-detection throttle from firing many large pushes back-to-back. Fixed by falling back to the already-documented minimal targeted single-file push (blob → tree with one path entry + `base_tree` → commit → ref update, 5 requests instead of 443) for just that one stuck file, which succeeded immediately. **Lesson reinforced**: when a specific file keeps failing to blob across multiple full-tree push attempts, stop retrying the full push — verify live via `curl` first (don't assume a later successful-looking push actually included it, since `base_tree` inheritance silently papers over a still-missing file), then do a targeted single-file push instead of another full-tree attempt.

**Extended to 6 more calculators 2026-09-10**: `vat-calculator.html`, `compound-interest.html`, `discount-calculator.html` (2 tabs → 1 shared `exportDiscountResult()`, same pattern as percentage-calculator's active-tab detection, keyed off `.tab.active`'s `data-tab` attribute this time instead of an id suffix), `tip-calculator.html`, `date-diff.html`, `currency-converter.html` — all mechanical copies of the established pattern. `currency-converter.html` turned out to already be one of `build-lang-pages.js`'s processed tools (confirmed via its `PAGE_META` list) despite an older CLAUDE.md note describing it as "6 separate hand-maintained files" — that note was stale; only the root file needed editing, lang variants regenerated normally.

**Real bug caught during this batch's live-image verification**: a row whose label/value is pure Latin text (e.g. currency-converter's rate line, `"1 EUR = 1.1624 USD"`) rendered visually reordered under `ctx.direction='rtl'` (Arabic mode) — `"1 EUR = 1.1624 USD"` came out as `"EUR = 1.1624 USD 1"`, the same bidi-reordering bug class documented elsewhere in this file for untranslated static text, just triggered here by dynamically-generated Latin content instead. **Fixed in the shared `exportResultImage()`** (not per-calculator): a `fillRowText()` helper now sets `ctx.direction` per string based on whether it contains Arabic characters (`/[؀-ۿ]/`), independent of the card's overall `isRtl` layout — `ctx.textAlign` still anchors the position correctly regardless, only the internal character-reordering direction needed to follow the string's own script. Any future calculator whose row content is a mixed/dynamic string (units, codes, formulas) gets this fix for free since it lives in the shared function.

Extending to more calculators (GPA/tawjihi-average, income-tax, unit-converter, hijri-converter, etc.) is now even more mechanical: add the button with `data-i18n="export_img_btn"`, add a small `exportXResult()` reading the page's already-computed result-DOM values into a `rows` array, call `exportResultImage(title, rows)`. Do this incrementally per-calculator, not as one giant sweep.

**Gotcha hit while testing this**: a CDP-driven Chrome tab that had visited the site earlier in the session kept running old cached `i18n.js` even after a plain `Page.navigate` reload — `sw.js`'s `cache:'no-cache'` fetch mode should force revalidation, but this specific tab didn't pick up the change until `Network.setCacheDisabled(true)` was set before navigating. If a live Chrome-session check of a just-pushed JS change looks stale, don't assume the push failed — force-disable cache on that specific CDP session and reload before concluding anything is broken.


## Export-image original-input gap — fixed across 9 calculators, 2026-09-14

User-reported (screenshot of `bmi-calculator.html`'s shared image): the exported result image showed the BMI value and category but not the height/weight the visitor actually entered — a share is meaningless to the recipient without knowing what was calculated. Audited every calculator using `exportResultImage()` and found the same gap on **9 of 11**: `bmi-calculator`, `loan-calculator`, `age-calculator`, `end-of-service`, `vat-calculator`, `tip-calculator`, `date-diff`, and one of `percentage-calculator`'s 3 tabs + one of `discount-calculator`'s 2 tabs. `currency-converter` (fixed earlier the same session) and `compound-interest` already included their original inputs — no change needed there.

**Fixed by prepending the real original input values** (read live from each page's own input elements, not recomputed) as additional `rows` entries before the existing result rows, reusing each page's own already-translated label (`t.lbl_weight`, `t.eos_start`, `t.tip_bill`, etc.) — matching the site-wide convention of reusing existing i18n keys rather than inventing new ones (same approach used for the currency-converter fix earlier this session).

**Two calculators needed active-tab/mode-aware logic, not a flat row list**:
- `percentage-calculator.html` has 3 independent tabs (X% of Y / X is what% of Y / % change), each with its own input pair — built an `inputRows` map keyed by the active tab index, concatenated with the existing result row.
- `discount-calculator.html` has 2 tabs (discount / plain percentage) — the "discount" branch already included its inputs; only the "percentage" branch needed rows added. **First pass reused the same `percent_label1`+`percent_label2` phrase for both the new input-summary row and the existing result row, producing a visually duplicated label** ("What is % of the number" appearing twice) — caught by actually reading the test output, not just confirming no JS error. Fixed by using the distinct `pct_pct`/`pct_num` keys (already shared in `i18n.js`, originally written for `percentage-calculator.html`) for the two input rows instead.

**`vat-calculator.html`** needed care since its amount-input label text changes meaning depending on add-tax vs. extract-tax mode ("Amount before tax" vs. the VAT-inclusive total) — used the label element's own *live* `textContent` (which the page's existing mode-toggle logic already keeps correct) rather than a static translation key, so the exported row is never wrong regardless of mode.

**Verified via live CDP tests against production** (not just local validation) — for each fixed calculator, filled real input values, called the real `calculate()`/`calc1()`/etc. function, temporarily wrapped `exportResultImage` to capture its `rows` argument without actually triggering a canvas render/share, and confirmed the captured rows contain the real entered values. Caught and fixed the discount-calculator label duplication this way. `test-calculators.js` (20/20) re-run clean afterward.


## Age calculator — Hijri date + top-3 historical events added to export image, 2026-09-21

Per the original user request ("حاسبة العمر بدي نضيف التاريخ الهجري بمشارك الصورة وتعطي اهم ٣ احداث صارت في مثل هاذ اليوم وكمان تضيفه ب مشاركة الصورة"), `age-calculator.html` gained two things:

1. **Hijri birthdate + Hijri age added to `exportAgeResult()`'s rows** — these were already computed and shown on-page (`#hijriBox`) but were never included in the shareable export image; a real, previously-undiscovered gap. Fixed by storing `hBirth`/`hijriAgeStr` as module-level vars (`lastHijriBirthStr`/`lastHijriAgeStr`) inside `calcAge()` and pushing them as rows.

2. **"Top 3 historical events on your birthday" (new feature, didn't exist before)** — interpreted "مثل هاذ اليوم" as the person's birth month/day (not today's date), since that's the framing that actually fits an age calculator and pairs naturally with the Hijri-birthdate feature in the same request. Sourced live from **Wikipedia's own "on this day" REST API**, specifically the `/onthisday/selected/{MM}/{DD}` endpoint — Wikipedia's own editorially-curated "selected anniversaries" feed (the same data used on Wikipedia's own Main Page), not the noisier chronological `/onthisday/events/` endpoint, which returns much lower-signal entries. Confirmed via direct testing that `selected` is meaningfully more notable/curated than `events`. Takes the first 3 entries per language. Language follows the page's current UI language (ar/en/fr/es/de/ru all map directly to real Wikipedia language editions — confirmed all 6 have live `onthisday` data with real CORS support), falling back to `en` for any unsupported case.

**Real architectural finding while building this: the site's CSP `connect-src` does not allow `*.wikipedia.org`, and — per the already-documented duplicate-Transform-Rule situation (see CSP-hardening section above) — adding it directly to the Worker's policy would NOT have been enough, since the old un-editable Transform Rule's own connect-src would also need it and CSP directives combine with AND semantics.** Sidestepped this exactly the way the gold-price fallback did: added a new `/api/onthisday?lang=X&month=M&day=D` route to the **existing `adawati-csp-nonce` Cloudflare Worker** (server-side Worker→Wikipedia fetches aren't CSP-governed at all), which fetches the real Wikipedia endpoint, strips MediaWiki template-leak artifacts from the text (a real bug found in raw API output — some entries contain literal leaked CSS like `.mw-parser-output .m{...}` from broken wikitext-to-plaintext conversion; a `/\{[^{}]*\}/g` strip handles it), caches the result for 24h via `caches.default` (much longer than the gold-fallback's 60s, since "on this day" content for a given calendar date is stable all day), and returns clean same-origin JSON. The page's `fetchBirthdayEvents()` calls this same-origin endpoint — zero CSP changes needed on the site side.

**Recovering the live Worker source before editing it**: this session had no local copy of the currently-deployed `worker.js` (each prior Worker change in this project's history was written fresh in a since-discarded scratchpad, per the established pattern). Rather than reconstruct it from memory of CLAUDE.md's own description (risky — could silently drop the gold-fallback handler or a CSP directive), pulled the **actual live source directly from Cloudflare's API** (`GET /accounts/{id}/workers/scripts/adawati-csp-nonce` using the existing `wrangler login` OAuth token read straight from `%APPDATA%\xdg.config\.wrangler\config\default.toml`) — confirmed byte-for-byte what's actually running before adding the new route. **If this Worker needs editing again in a future session with no local source file, pull the live script this same way first** rather than rewriting from documentation.

**Deployed via `wrangler deploy`** (CLI, not the dashboard editor — same established reason as every other Worker change in this project), using a `wrangler.toml` matching the live script's own `compatibility_date` (2026-09-14) read from `GET .../workers/scripts/adawati-csp-nonce/settings` first, so the redeploy wouldn't accidentally shift it. Verified immediately after deploy that the production Route was unaffected (`X-CSP-Nonce-Worker: enforced` still present on the homepage) before testing the new endpoint — a Worker redeploy via `wrangler deploy` with no `routes` in `wrangler.toml` does NOT touch the zone Route binding, confirmed empirically, not just assumed.

**Testing**: used the established Fetch-domain CDP interception technique (serve the page from local disk while letting the browser's *own* relative-URL requests — `/api/onthisday` — hit the real live Worker) since this feature is meaningless to test purely locally. Confirmed end-to-end on the real production endpoint: English mode showed 3 real, correctly-cleaned Wikipedia events; Arabic mode (after a live language switch) re-fetched and showed different, real Arabic-Wikipedia events; the export-image capture showed all of Hijri birthdate, Hijri age, and all 3 events present as rows. `test-calculators.js` (20/20) and `test-e2e.js` (29/29) both re-run clean afterward — confirms the Worker change didn't regress anything else routed through it (which is everything on the site, given it's the CSP-nonce Worker in front of every page).

**Gotcha hit while re-running the regression suite this session, worth remembering**: `test-e2e.js` needs headless Chrome on **port 9750**, not the 9700 used by `test-calculators.js` (and by the earlier ad-hoc CDP scripts throughout this session) — confirmed via `grep CDP_PORT test-e2e.js`. Launching Chrome on the wrong port produces a generic, unhelpful `TEST RUNNER ERROR:` with no message (an `AggregateError [ECONNREFUSED]` whose `.message` happens to be empty) — don't assume this means a real regression; check `CDP_PORT` in the specific test file before concluding anything is broken, and don't reuse one test's Chrome instance/port for the other.

**Verified live via CDP** (this page has no `<base href>`, so ordinary local-server testing worked directly — no Fetch-interception workaround needed here): captured the real `rows` array for g2h mode, h2g mode (15 Ramadan 1446 → 15 March 2025, a plausible real conversion), and Arabic-mode label translation — all correct. ## exportResultImage — long row values now wrap instead of overflowing, 2026-09-21

User-reported via two real screenshots of age-calculator's export image: the historical-events rows (built earlier this session — see "Age calculator — Hijri date + top-3 historical events added to export image") rendered with the event's year and its full sentence text visibly overlapping/running off the card edge. Root cause: `exportResultImage()`'s row renderer (`fillRowText`) does a single unwrapped `ctx.fillText()` call per label/value — fine for every other calculator's genuinely short values ("70kg", "5%", "149.85"), but a full sentence (e.g. "انعقاد مؤتمر الطائف بالسعودية لحل مشكلة الحرب الأهلية اللبنانية.") rendered at the normal value font size is far wider than the card, so it overflowed past its anchor edge far enough to overlap the label positioned at the opposite edge — this was a real, pre-existing gap in the shared function (short label/value pairs were the only case anyone had ever exercised it with before), not a bug specific to the events feature's own code.

**Fixed generically in `exportResultImage()` itself**, not per-calculator, so every current and future user of the function benefits: a two-pass measurement (a throwaway canvas measures each row's value against a width threshold — matching the same "measure before creating the real canvas" pattern already established for the quiz-result-sharing feature's caption wrapping) decides per-row whether the value fits the normal two-column layout or needs to switch to a stacked layout (label as a small heading, value word-wrapped across multiple lines below it, both anchored to the same edge instead of opposing edges) — and the canvas height calculation (already row-count-driven, not fixed) now accounts for wrapped rows needing more vertical space. Short rows render through the exact same code path as before, unaffected.

**Verified**: a local test built the exact scenario from the user's screenshots (Arabic mode, 3 long event rows mixed with short date/age rows) — all 3 events now wrap cleanly with zero overlap. A regression check on `loan-calculator.html` (all short values, plus one moderately-long "Interest Type: Compound (Reducing Balance)" value that also now correctly stacks/wraps instead of whatever overflow risk it may have silently had before) confirmed the normal short-row layout is visually unaffected. Re-verified live against production `age-calculator.html` with a real fetched set of events (different text than the local test, since events are live-fetched from Wikipedia) — same clean result, 0 JS exceptions. `test-calculators.js` (20/20) and `test-e2e.js` (29/29) re-run clean afterward.


## age-calculator export — final summary row label/value swapped, fixed 2026-09-21

Follow-up to the wrap fix above — user pointed at the bottom of the exported card looking "not organized." Root cause was a separate, real bug in `age-calculator.html`'s own `exportAgeResult()`, not the shared function: the final highlighted row was built as `{label: document.getElementById('ageSub').textContent, value: main, highlight:true}` — but `#ageSub` holds the small continuation phrase ("و 0 شهر و 0 يوم") and `main` holds the big number ("14 سنة"), so the export literally put the continuation half first (as the "label") and the number half second (as the "value"), reading backwards instead of as the single coherent on-page phrase "14 سنة و 0 شهر و 0 يوم".

**Fixed**: combined both pieces into one `value` string (`main + ' ' + ageSubText`) and added a proper new short label key `lbl_your_age` ("عمرك"/"Your Age"/etc., all 6 languages) instead of reusing `#ageSub`'s text as the label. Verified live on production (real fetched values, real events) — the row now renders as a clean heading ("عمرك") above the full wrapped phrase ("24 سنة و 0 شهر و 0 يوم"), matching the same stacked layout already used for the Hijri-age row right above it. Pushed as 6 files (root + 5 lang variants), verified live via blob-sha diff, `test-calculators.js` (20/20) re-run clean.
