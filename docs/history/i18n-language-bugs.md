# Mixed-language / untranslated-element bugs across country hubs and pages

Part of أدواتي (adawati.space) project history — split out of the main CLAUDE.md on 2026-09-21 to keep that file lean. See CLAUDE.md's "Documentation index" section for how this fits in.

## Nationality-landing pages (eg/in/pk/bd/ph) translated to Arabic — fixed 2026-09-09

`eg/index.html`, `in/index.html`, `pk/index.html`, `bd/index.html`, `ph/index.html` (Oman-based expat landing pages targeting Egyptian/Indian/Pakistani/Bangladeshi/Filipino workers) each had only ~14 `data-i18n` attributes (the shared country-switcher menu labels) — the rest of the page (hero, badges, stats, featured tools, key facts, full tools grid, FAQ, footer) was hardcoded English with **no** translation wiring, unlike the properly-built `ae/us/uk` hub pages (~109 `data-i18n` attributes each). Switching these 5 pages to Arabic left almost the entire page in English while the root `<html dir>` flipped to `rtl` — which also visibly **garbled short two-word English fragments via RTL bidi reordering** (e.g. the stat value "1 mo" rendered as "mo 1"), a second symptom of the same root cause, not a separate bug. User reported this via `eg/` specifically; scoped down (via `AskUserQuestion`) to translate `eg/` first as the model, then all 4 remaining pages in one pass.

**Fixed for all 5 pages**, ~450 new `T.ar`/`T.en` key entries added to `i18n.js` (`eg_*`/`in_*`/`pk_*`/`bd_*`/`ph_*` prefixes for nationality-specific hero/stats/facts/FAQ/footer content, plus shared cross-page keys `hero_badge_tools`/`hero_badge_nosignup`/`hero_badge_nospf`/`hero_badge_browser`/`stat_spf_lbl`/`stat_gratuity_val`/`stat_gratuity_lbl`/`footer_privacy`/`footer_terms` reused verbatim across all 5). The main `#toolsGrid` tool cards on every page reuse the **existing** site-wide `TOOL_META`-linked keys (`currency_card_title`/`sal_card_title`/`eos_card_title`/`bmi_card_title`/etc.) instead of new page-specific ones — those tools are generic enough that the existing translations fit, and it avoided writing ~150 near-duplicate key pairs. FAQ answers containing an inline `<a href="...">` link (2 per page, e.g. linking to `end-of-service.html`/`currency-converter.html`) use `data-i18n-html="{key}_html"` (innerHTML-based, see `setLang()`'s `[data-i18n-html]` branch) instead of plain `data-i18n`, so the link survives translation — plain `data-i18n` uses `textContent` and would silently strip any nested tag.

Written in Modern Standard Arabic (not Jordanian dialect — these are generic expat-facing pages, not `/jo/` pages), matching the register already established in the `eg_*` keys. Only `ar`+`en` were written (matching this project's established minimum-viable-translation scope for this feature area, same as the `jo_hero_*`-style keys) — `fr`/`es`/`de`/`ru` visitors keep seeing the original English text via the `T[lang][k] !== undefined` no-op guard in `setLang()`, not a regression, same as before this fix.

**If a 6th nationality page is ever added**, copy one of these 5 as the template (they're now the properly-i18n'd reference, not the old bare English ones) and follow the same key-prefix + shared-key-reuse pattern rather than starting from a pre-translation-era page.


## om/index.html mixed-language bug — fixed 2026-09-15

User-reported via two real mobile screenshots (not an external scanner report): with the site set to English and country set to Oman, `om/index.html`'s hero privacy badge, its OMR-to-INR tool card, and the entire "📅 يوميات" (Daily Info) section (holidays/fuel-prices/gold-price/weather/prayer-times/emergency-numbers cards) still rendered in Arabic. Investigation found the same root cause already documented elsewhere in this file for `jo/index.html`'s mixed-language bug: `i18n.js`'s `applyTranslations()` only touches elements carrying a `data-i18n` attribute — these specific elements were built (by the earlier "5-module country expansion" and "daily-info modules" forks) with hardcoded Arabic text and **no `data-i18n` attribute at all**, so the language switch never reached them.

**Scope, once actually read in full**: beyond the two elements the screenshots showed, the same bare-Arabic pattern also covered the `#decisionsSection` (car-cost/wedding-cost/university-cost cards + its own header) and — found while fixing the featured OMR card — **4 more currency-conversion cards** (`omr-to-pkr`/`bdt`/`egp`/`php`) in the page's separate, larger searchable `#toolsGrid` grid, which have their own independent (undocumented-in-the-screenshots) instances of the identical bug.

**Fixed**: added 30 new i18n keys (`om_omr_title`/`om_omr_desc`, `om_pkr_title`/`om_pkr_desc`, `om_bdt_title`/`om_bdt_desc`, `om_egp_title`/`om_egp_desc`, `om_php_title`/`om_php_desc`, `om_daily_label`, `om_holidays_title`/`desc`, `om_fuel_title`/`desc`, `om_gold_title`/`desc`, `om_weather_title`/`desc`, `om_prayer_title`/`desc`, `om_emergency_title`/`desc`, `om_decisions_label`, `om_carcost_title`/`desc`, `om_wedding_title`/`desc`, `om_unicost_title`/`desc`) across all 6 languages (ar/en/fr/es/de/ru) in `i18n.js`, matching the exact wording already used on `ae/index.html`'s equivalent English cards where a direct AE↔OM equivalent existed (adapted for Oman's own already-verified single-unified-9999 emergency framing and "Omani" degree wording, not copied verbatim — AE uses a 999/998/997 three-number scheme, a different fact). Wired `data-i18n` onto every corresponding `om/index.html` element; arrow elements reuse the existing shared `start` key like every other card on the page.

**Real mistake made and self-caught mid-edit**: a Node script inserting the initial privacy-badge key across all 6 language blocks in one pass, driven by pre-computed (and therefore stale-after-each-insertion) line numbers, wrote Arabic text into the Russian block instead of a Russian translation — caught via `grep -n "om_badge_privacy" i18n.js` showing the same Arabic string appearing twice, fixed via a targeted `Edit`. The subsequent, larger batch of 22+8 new keys used a safer `indexOf`-with-advancing-cursor insertion script instead of precomputed line numbers, specifically to avoid repeating this class of bug — verified afterward via `grep` that each language block shows only its own language's text, not a duplicate.

**Real testing gotcha hit, worth remembering for any future local-server test of a page carrying `<base href="https://adawati.space/">`**: an ad-hoc local static server (`http://localhost:8900`) initially made all i18n testing look broken — `T.en.om_omr_title` (and every other new key) came back `undefined` in a CDP check, even though the file on disk was correct. Root cause: the page's own `<base href="https://adawati.space/">` makes the `<script src="../i18n.js?v=42">` tag resolve against the *live production domain*, not the local server, so the browser was silently loading the **old, unedited, live** `i18n.js` instead of the local one being tested — the exact same class of gotcha already documented in this file for the mobile-nav-collapse and quiz-result-sharing features, just newly hit here too. **Fixed by testing via CDP's `Fetch` domain instead of a bare local server**: enabled `Fetch.enable` with `urlPattern: "https://adawati.space/*"`, navigated directly to the real `https://adawati.space/om/index.html` URL, and fulfilled every intercepted request from local disk instead of the network — this is a more general, reusable version of the "isolated preview page" workaround used in past sessions, since it works for a full un-modified page (not just an isolated snippet) and needs no page rewriting. **Worth adopting as the standard technique for any future local test of a page using `<base href>`** — simpler and more faithful than manually building an isolated preview page each time.

Validated (`JSON.parse` — n/a, `i18n.js` isn't JSON but `node --check` passed; `new Function()`/div-balance on `om/index.html`, 0 errors), functionally tested via the Fetch-interception CDP technique above confirming every previously-Arabic element now correctly shows English in EN mode and confirming Arabic mode is unaffected (regression-free) with zero JS errors. Pushed via a targeted 2-file push (i18n.js + om/index.html) after a full-tree push attempt failed outright under GitHub's secondary rate limit; verified live via blob-sha diff (both files byte-identical to local) and `curl` (the only diff between local and live `om/index.html` is the CSP nonce the Cloudflare Worker injects into inline `<script>` tags — expected, not a discrepancy). `test-calculators.js` (20/20) and `test-e2e.js` (29/29) re-run clean afterward, including a zero-console-errors check specifically on `/om/index.html`.

**The 5 `oman-*-guide.html` link cards further down `om/index.html`'s searchable grid** (`data-cat="oman"`, linking to `oman-tax-guide.html` etc.) have the same bare-Arabic-hardcoded-text pattern but were **deliberately left unfixed this round** — they're a different card family (guide-page links, not calculator tools) and lower-signal than what was actually reported; flagged here in case a future pass wants to close this out too.


## Cross-hub mixed-language bug, widened scope — fixed 2026-09-15

After the om/index.html fix above, the user kept finding the same bug class live in the browser on other hubs ("لسا هون في اشي" — "there's still something here"), first on `sa/index.html`'s popularSection VAT card, then on `jo/index.html`'s hero stats row. Rather than keep whack-a-moling from screenshots, ran a full audit of all 6 country hubs' `.tool-card-title`/`.tool-card-desc`/`.stat-item-lbl` elements for missing `data-i18n`, in both directions (Arabic hardcoded on ar-default hubs, English hardcoded on en-default hubs).

**Real, separate, more serious root cause found on `jo/index.html` and `sa/index.html`**: both had an **unconditional** `localStorage.setItem('lang', 'ar');` in their own inline `<script>` (running synchronously, before the deferred `i18n.js` tag) — this silently overwrote any language the visitor had already chosen (on this page or any other) back to Arabic **on every single page load**, before `i18n.js`'s own `detectDefaultLang()` even ran. `om`/`ae`/`us`/`uk`/the global `index.html` all correctly use the guarded form (`if (!localStorage.getItem('lang')) localStorage.setItem('lang', 'ar');`/`'en'`) — only default if nothing was chosen yet. This fully explains the user's repeated reports: navigating to jo or sa (even mid-session, even right after explicitly picking English elsewhere) silently reset the page to Arabic, and any of the missing-`data-i18n` elements below would then never have gotten a chance to show English at all regardless of the other fixes. **Fixed** by changing both to the guarded form, matching the already-correct pattern on the other 4 hubs.

**Missing `data-i18n` found and fixed, by hub**:
- **`jo`**: hero stats-row "أداة ودليل"/"🔒 خصوصية تامة" (wired to `stat_tools` / new `stat_privacy_short`), plus all 14 `jo/games/*` challenge cards in **both** of jo's card sections (the legacy un-tabbed list and the tabbed `data-cat="challenges"` grid, 28 elements total) — reused the new shared `g_*` keys (see below). **Jo's own ~35 Jordan-specific tool cards** (tawjihi-average, university-gpa, income-tax, package-customs, decisions bundle, daily-info cards, etc.) were **deliberately left untouched** — this is the established site convention that Jordan-vertical content is Jordanian-dialect Arabic by design, not a bug of the same class; translating ~35 cards to English is a real, separate, much larger scope decision that needs an explicit ask, not a mechanical fix.
- **`om`**: one remaining stats-row item ("🔒 معظم الأدوات محلية" → `stat_privacy_short`, cosmetic text now reads "خصوصية تامة" to match the shared key) and all 13 `jo/games/*` challenge cards (om doesn't have logo-quiz).
- **`sa`**: stats-row ("أداة ودليل" → `stat_tools`; "VAT السعودية" → new `sa_stat_vat_lbl`), the popularSection VAT card (title+desc → new `sa_vat_card_title`/`sa_vat_card_desc`), **7 more popularSection card descs** that had a translated title but a hardcoded Arabic desc (currency/loan/hijri/compound-interest/bmi/percentage/date-diff — new `sa_*_card_desc` keys preserving the exact existing sa-specific wording), one more stray `data-cat="oman"`-tagged card pair (Gulf VAT + Hijri, unreachable via any of sa's real tabs but still shown under the `activeCat==='all'` default — same latent-card pattern documented elsewhere in this file; only the VAT one's desc needed a data-i18n fix here since Hijri's was already wired) all 6 dailySection/decisionsSection cards (reusing `om_*` keys, since the Arabic text was byte-identical to om's), and all 13 `jo/games/*` challenge cards.
- **`ae`/`us`/`uk`** (English-default — same bug, mirrored: hardcoded English with no Arabic translation, so switching to Arabic left these stuck in English): stats-row country-specific labels (`ae_stat_vat_lbl`, `us_stat_tip_lbl`/`us_stat_units_lbl`, `uk_stat_vat_lbl`/`uk_stat_rates_lbl`), the ae VAT popularSection card (`ae_vat_card_title`/`desc`), us's Mortgage Calculator + Unit Converter popularSection cards (`us_mortgage_card_title`/`desc`, reused `unit_card_title` + new `us_unit_card_desc`), uk's Percentage/Mortgage/Unit Converter popularSection cards (reused `pct_card_title`/`unit_card_title` + new `uk_percentage_card_desc`/`uk_mortgage_card_title`/`desc`/`uk_unit_card_desc`), all 6 dailySection/decisionsSection cards each (reusing `om_*` keys for the identical parts — holidays/fuel/gold/weather/prayer/car-cost/wedding-cost text was byte-identical to om's own English translations — plus new per-country keys only where the underlying fact differs: `{ae,us,uk}_emergency_desc`, `{ae,sa}_unicost_desc`, `us_unicost_title`/`desc` since US's card is literally named "College Cost Calculator" not "University Cost Calculator", `uk_unicost_desc`), and all 14 `jo/games/*` challenge cards each (13 shared + logo-quiz, new `g_logoquiz_title`/`desc`).

**Reuse strategy, to avoid key sprawl**: rather than give every hub its own prefixed key for genuinely identical content, reused the existing `om_*` daily/decisions keys (created for the original om fix) as the de-facto shared keys wherever the Arabic text (om/sa) or English text (ae/us/uk) was byte-identical — confirmed this by direct diff before reusing, not assumed. Only added new per-country keys where the underlying fact/wording genuinely differs (emergency numbers, degree-cost descriptions, VAT-specific popularSection cards). Also reused already-existing generic keys (`stat_tools`, `unit_card_title`, `pct_card_title`) where a hub's wording was an exact or near-exact match, accepting a cosmetic text change on the 1-2 instances where wording differed slightly (e.g. uk's "Percentage Calculator" now reads "Percentage & Discount" to match the sitewide canonical name already established in the 2026-09-10 naming-consistency fix — this was already the intended canonical name, this hub instance had just been missed). Game-card keys (`g_*`) are **ar+en only**, matching the established "English only for trivia content" scope convention — `g_logoquiz_desc`'s Arabic value was set to match jo's own pre-existing wording exactly (not a fresh translation) specifically so wiring `data-i18n` wouldn't change jo's default Arabic display text.

**Real script bug hit and caught mid-session, worth remembering**: an early version of the game-card-wiring script built its replacement string as a template literal containing literal `$1`/`$3`/`$5`/`$7` placeholders concatenated with the real captured group text, then called `.replace(literalSubstring, ...)` on that string (looking for the wrapper divs, which weren't there) before ever passing it to `src.replace(re, replacementString)` — but passing a string containing `$1` etc. as the *replacement* argument to `String.prototype.replace(regex, string)` makes JS treat those as **backreferences to the original regex's capture groups**, which silently reconstructed the exact original matched text with **zero net change** — the script printed "wired 13 of 13" while actually being a complete no-op. Caught immediately by grepping the output file for the expected `data-i18n` attribute and finding it absent. Fixed by building the replacement via plain string concatenation (`m[1] + newAttr + m[2] + ...`) using `slice`+insert instead of `.replace(regex, string)` at all. **Lesson: never build a `.replace(regex, replacementString)` replacement string that happens to contain literal `$N` sequences — JS will reinterpret them as backreferences regardless of your intent; always verify a batch-replace script's actual file output, not just its own success log, especially when the "count changed" logic can't distinuish a real edit from a no-op reconstruction.**

**Verification**: all 6 hub files + `i18n.js` validated (`new Function()` on every inline script, 0 errors). Functionally tested via the CDP `Fetch`-domain interception technique (documented in the earlier om fix section) against `https://adawati.space/*` URLs pointing at local files — confirmed, for every hub, that switching to English translates every previously-broken element with zero remaining untranslated Arabic-with-no-`data-i18n` elements except the two deliberately-scoped exceptions (jo's own ~35 tool cards, om's 5 `oman-*-guide.html` cards, both already documented). Also specifically re-tested the `localStorage.lang` persistence fix (set 'en' on a previous page, reload jo/sa, confirm `document.documentElement.lang` stays 'en' instead of reverting to 'ar') and a genuine fresh-visit-with-no-stored-language regression check (confirming jo/om/sa still correctly default to Arabic and ae/us/uk to English for new visitors, unaffected by the guard-condition fix). Pushed via a targeted 7-file push (i18n.js + all 6 hub `index.html`), verified live via blob-sha diff (all 7 byte-identical to local) and a final CDP run against the **real live** `https://adawati.space` domain (not local files) reproducing the identical zero-untranslated-elements result. `test-calculators.js` (20/20) and `test-e2e.js` (29/29) both re-run clean.

**Deliberately left for a future, separate pass** (flagged here, not silently dropped): jo's own ~35 Jordan-specific tool cards untranslated to English (a real scope decision, not a quick fix); om's 5 `oman-*-guide.html` cards (same as before); sa's stray `data-cat="oman"` VAT/Hijri card pair being unreachable via any real sa tab (the same latent-card display bug documented earlier in this file for other hubs — worth a proper audit of whether other hubs have similar stray `data-cat` values from copy-pasted templates, not just the already-fixed Oman-only-tool-card instance).

## Full-site QA sweep (313 pages, 4 parallel agents) — 2026-09-25

User asked for a complete site-wide test-and-fix pass ("لف على السيستم واعمل تست وشو بتلاقي مشاكل حلها كل اشي"). Confirmed all 313 sitemap URLs return HTTP 200 (no dead links) via a direct concurrent curl sweep, then split deeper functional testing across 4 parallel `general-purpose` agents (testing only, no push access, to avoid concurrent-push git-tree conflicts): root-level tools (66 pages), the `/jo/` vertical (38 pages), the other 5 country verticals (58 pages, also re-verifying the prayer-times-fallback and hub-category-filter fixes shipped earlier the same day), and a translated-language spot-check (46 page loads across ar/fr/es/de/ru). All 4 agents initially stopped short after launching a background test script and yielding on their own Monitor notification rather than reaching the coordinator — had to be explicitly nudged via SendMessage to check their script's output directly and report; all 4 then completed fully.

**Result: 313/313 pages load with zero broken links and zero JS console errors.** Two real, fixable bugs found and shipped same-day:

1. **Bottom nav (Home/Tools/Favorites) never translated, on every page, every language, since it was added.** Root cause in `i18n.js`'s `_initAfterLangReady()`: `setLang(_initLang)` (which walks every `[data-i18n]` element and translates it) ran *before* `initBottomNav()` (which creates the `#bottomNav` DOM node containing the `data-i18n` spans) — so the spans didn't exist yet when the translation pass ran, and the hardcoded English fallback text (`Home`/`Tools`/`Favorites`) stuck forever. A code comment right above it claimed this was already handled ("Label spans use data-i18n so applyTranslations() ... keeps them in sync") — true in general, but defeated by the one-time call-order bug on initial load. **Fixed** by swapping the two calls' order (`initBottomNav()` now runs first). Confirmed live across ar/de/fr/es/ru + English root — every language now shows its own translated nav labels.
2. **Footer "Privacy"/"Terms" links stayed English on fr/es/de/ru.** The `footer_privacy`/`footer_terms` keys existed only in `i18n-lang-ar.js` and `i18n-lang-en.js` — never added to the other 4 packs when they were created. **Fixed** by adding both keys to `i18n-lang-fr.js` (Confidentialité/Conditions), `i18n-lang-es.js` (Privacidad/Términos), `i18n-lang-de.js` (Datenschutz/AGB), `i18n-lang-ru.js` (Конфиденциальность/Условия).

`i18n.js` bumped `?v=46` → `?v=47` across all 301 referencing HTML files per the standard cache-busting discipline (a plain grep-and-replace script, not manual).

**Also fixed the same day, found by the root-tools agent**: `compound-interest.html` rendered raw JS scientific notation (`6.219411804435816e+44`) for the Final Amount / Total Interest fields under extreme-but-reachable inputs (e.g. 100% rate over 100 years) — `Number.prototype.toFixed(2)` silently falls back to `String(number)` above magnitude 1e21, per spec. The page's own `fmt()` helper wasn't actually used anywhere in the file (dead code) and hardcoded the `ar-EG` locale (which would have introduced Arabic-Indic digits on this English page — not a safe fix to reuse as-is). Fixed by switching the 4 affected result fields to `toLocaleString('en-US', {minimumFractionDigits:2, maximumFractionDigits:2})`, which has no exponential-notation cutoff.

**Two larger translation gaps found but NOT fixed same-day — deferred as a separate content project, not a quick bug fix:**

3. **A hardcoded, never-translated English subtitle paragraph directly under the H1 on ~16 of the 30 root tool templates**, byte-identical across all 5 language copies including Arabic (e.g. `ar/age-calculator/index.html` shows a fully English 2-sentence description right under its Arabic H1).
