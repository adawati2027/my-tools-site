## Daily-info modules extended to all countries, 2026-09-10

Jordan's 3 live-data daily-info modules (`jo/gold-price/`, `jo/weather/`, `jo/prayer-times/` — confirmed earlier this session these existed ONLY under `jo/`, nowhere else) are now replicated for `om/sa/ae/us/uk`, 15 new pages total. Deliberately scoped to just these 3 (not the other 3 Jordan has — `fuel-prices/`, `holidays/`, `emergency-numbers/` — which are static reference content requiring real per-country data collection, not a template swap) after explicit scope confirmation with the user.

**Built via 3 generator scripts** (scratchpad, reusable pattern if a 6th country or the static-content modules are added later): `gen_daily_info.js` (gold), `gen_weather.js`, `gen_prayer.js`, all reading a shared `countries_data.js` (per-country flag/names/currency/Aladhan country string+method/city list with real lat-lon coordinates). Each script has an `ar` and `en` template function — output language follows each country's **already-established** hub-page convention (confirmed via `<html lang>` on each `index.html` before building): `om`/`sa` are Arabic (`lang="ar"`), `ae`/`us`/`uk` are English (`lang="en"`) — matches the "language scope: country's natural language only" decision made with the user.

**APIs, all verified working before building** (not assumed from the Jordan template alone):
- Gold: `xaus.com/api/v1/spot?currency=<CODE>&unit=gram` — confirmed supports OMR/SAR/AED/USD/GBP directly (not just JOD).
- Weather: `api.open-meteo.com` — switched to `timezone=auto` instead of Jordan's hardcoded `timezone=Asia%2FAmman`, since Open-Meteo resolves timezone from lat/lon automatically; avoids hardcoding 5 more timezone strings.
- Prayer times: `api.aladhan.com/v1/timingsByCity?city=X&country=Y&method=N` — **verified live for all 5 countries** with real city/country name pairs before building (`curl -sL`, note the `-L` flag is required — the endpoint 302-redirects to a date-specific URL, invisible to a browser's `fetch()` which follows redirects automatically, but silently returns nothing to a bare `curl` without `-L`; this looked like a dead API at first and would have been a false negative if not caught). Calculation method per country: Oman/UAE method=8 (Gulf Region), Saudi Arabia method=4 (Umm Al-Qura — the actual regional standard), US method=2 (ISNA), UK method=3 (Muslim World League) — standard regional conventions, not verified against any authoritative source beyond that (same caution level as Jordan's own method=5 Egyptian, which was never deeply verified either — this is a calculation-method convention, not a legal/financial fact requiring the heavier verification bar).

**Cross-linked both ways**: each new page links to its 2 siblings (gold↔weather↔prayer) plus `currency-converter.html` and the country hub; each country's `index.html` got 3 new cards inserted at the top of its main tools grid (`add_hub_cards.js` script, inserted right after the `<div class="tools-grid">` opening tag via a literal string match — fragile if that exact literal ever changes, re-verify the insertion point if this pattern is reused). Added all 15 URLs to `build-sitemap.js`'s `countryTools` array (sitemap grew 256→271) and re-ran `build-search-index.js` (90→105 entries) so they're both crawlable and locally searchable via the smart-search feature built earlier this session.

**Verification**: `JSON.parse`/`new Function()` validated on all 15 new pages + 5 modified hub pages (0 errors). Pushed via `node push-to-github.js` — 7 files failed to blob in the full-tree push (`sa/weather`, `sa/prayer-times`, `us/gold-price`, `us/weather`, `uk/gold-price`, `uk/prayer-times`, `build-sitemap.js` — usual secondary rate-limit pattern) and needed the targeted single-file push script. **New paths took noticeably longer to actually go live on GitHub Pages than the usual 30-90s window** for existing-file edits — confirmed the files were genuinely in the git tree (via a direct `GET .../git/trees/main?recursive=1` API call) while `curl` against the live URLs still 404'd, then they came up within another ~30-60s of polling. If a brand-new directory 404s right after a push, check the git tree directly before assuming the push failed — it may just be Pages' build lag for new paths specifically. **Real functional verification** (not just HTTP 200) done via the headless-Chrome-CDP technique documented above, on a fresh isolated profile: confirmed `om/gold-price` (54.33 OMR/g 24K), `uk/weather` (17° London), `sa/prayer-times` (Fajr 4:18 AM Riyadh, correct Arabic date string), and `us/weather` (22° New York) all render real live API data, not just valid empty markup.

**Gotcha reconfirmed while testing**: killing the test Chrome instance by PID tree (`taskkill /F /T /PID <parent>`) rather than by image name (`taskkill /F /IM chrome.exe`) is essential — the latter kills every Chrome process system-wide including the user's real browser (this happened once already this session, see the CDP section above). Find the specific parent PID via `wmic process where "name='chrome.exe'" get ProcessId,CommandLine` and grep for the unique `--remote-debugging-port`/`--user-data-dir` value used for that test instance.


## 5-module country expansion (Holidays, Fuel Price, Car Cost, Wedding Cost, University Cost) — built 2026-09-10

User asked to extend 5 modules that previously existed only under `jo/` (and `om/holidays`+`om/fuel-prices` in one case) to **all 6 countries**, each with country-specific real data, bilingual (AR default for om/sa, EN default for ae/us/uk, with an in-page toggle for the other language on every new page — same self-contained pattern as `quiz-engine.js`'s "In-page English translation system", **not** wired into `i18n.js`, per established convention for narrow-scope per-page content). Explicitly confirmed with the user beforehand: build all 5 modules together (not staged one at a time), and culturally adapt wedding-cost/university-cost per country rather than skip them for US/UK.

**Built via 5 parallel background forks**, one per module, each producing 5 country pages (25 new files total): `{om,sa,ae,us,uk}/holidays/`, `{...}/fuel-prices/`, `{...}/calculators/car-cost/`, `{...}/calculators/wedding-cost/`, `{...}/calculators/university-cost/`. Every fork's output was independently re-validated by the main session (not trusted at face value) — `JSON.parse` on all JSON-LD blocks and `new Function()` on all inline `<script>` bodies, 0 errors across all 25 files — plus targeted fact spot-checks via fresh WebSearch on a few uncertain items the forks themselves flagged (e.g. Saudi VAT rate, UK fuel prices) and a grep confirming `us/uk` wedding-cost pages contain zero mahr/مهر references (correctly adapted, not just translated).

**Integration** (done in the main session, not by the forks, to keep hub-page markup consistent): the forks' own self-reported hub-card HTML snippets used inconsistent markup (wrong icon-wrap class, inconsistent arrow text) vs. the site's established convention — cards were rebuilt from scratch using `jo/index.html`'s exact pattern (`tool-icon-wrap` div + title + desc + `tool-card-arrow` with "ابدأ ←"/"Start →"), using the forks' content (titles/descriptions/URLs) but correct structure. Holidays + Fuel Price cards were appended to each country's existing `<div id="dailySection">` (now 5 cards instead of 3); Car Cost + Wedding Cost + University Cost cards went into a new `<div id="decisionsSection">` ("💡 قرارات كبيرة" / "💡 Big Decisions") added right after `dailySection` on all 5 hub pages. `build-sitemap.js` got a new loop appending the 25 URLs to `countryTools` (sitemap grew 271→296 entries). `build-search-index.js`'s title/description regexes were tightened to tolerate extra attributes (`<title id="pageTitleTag">` — used by the holidays pages for their countdown feature — was silently failing the old exact-match regex `/<title>([^<]*)<\/title>/`, which meant those 5 pages weren't indexed at all until this was fixed).

**Push required 3 rounds** due to unusually heavy GitHub secondary rate-limiting on this batch (two full-tree pushes each dropped 30-60 files, including several of this task's own new/changed files). **Don't trust which specific files a full-tree push's error log shows failing as the complete picture** — do a direct tree-verification pass instead: fetch the live commit's recursive git tree via the API, compute each target file's local git-blob-sha1 (`blob <len>\0<content>` sha1, same algorithm git itself uses), and diff against the remote tree's sha for that path. This caught 8 files (`om/index.html`, `us/holidays/`, `us/calculators/car-cost/`, `uk/calculators/car-cost/`, `uk/calculators/wedding-cost/`, `sitemap.xml`, `search-index.json`, `build-sitemap.js`) that were stale/missing after both full-tree pushes despite not all appearing in either push's visible error log (the first push's failure log was truncated in terminal output, so some real failures were invisible without this check) — fixed via 8 individual `push_single_file.js` calls, then re-ran the same tree-verification script and got 0 mismatches before declaring done. **This verification-by-tree-diff approach is more reliable than grepping push logs when a batch has had multiple retry rounds** — reuse it (the script is a straightforward ~40-line Node script using `crypto.createHash('sha1')` on the git blob format) instead of trying to reconstruct which round actually saved which file from truncated logs.

All 34 touched/new files (25 pages + 5 hub `index.html` + `sitemap.xml` + `search-index.json` + `build-sitemap.js` + `build-search-index.js`) confirmed live via direct blob-sha comparison and spot-checked via `curl` (with a cache-busting query param — the bare URL initially showed stale CDN-cached content for `om/index.html` even though the underlying commit was already built, per the Pages build-status endpoint).


## Emergency numbers extended to all 6 countries — built 2026-09-13

Jordan's `jo/emergency-numbers/` page (static AR content, no live API — police/ambulance/fire numbers don't change) was the only one of the 6 countries with this module. Extended to `om/sa/ae/us/uk`, one new page each, following the language convention already established elsewhere (AR for om/sa, EN for ae/us/uk, no in-page toggle — this content doesn't need one since it's simple enough on one language, matching `jo/emergency-numbers/`'s own no-toggle precedent rather than the toggle pattern used on `fuel-prices`/`holidays`).

**Numbers verified via WebSearch (multiple independent sources cross-referenced per country) before writing anything** — this is safety-critical factual content, held to the same verification bar as the site's legal/financial facts even though it's not explicitly named in the verification policy:
- **Oman**: single unified number **9999** for police/ambulance/fire (confirmed via Wikipedia's Civil Defence and Ambulance Authority page + a dedicated emergency-numbers aggregator; 112 explicitly does NOT reliably work here — noted on the page).
- **Saudi Arabia**: 999 police / 997 ambulance (Red Crescent) / 998 civil defence — the historical 3-number system, still the only one that works nationwide. Also noted: a newer unified **911** exists but only in Riyadh/Makkah/Madinah/Eastern Province — worth knowing since some sources cite 911 as *the* Saudi number without that regional caveat.
- **UAE**: 999 police / 998 ambulance / 997 fire, all toll-free nationwide; 112 works as a backup reaching the same services; 996 is Coast Guard (mentioned as a footnote, not a main card).
- **US**: 911 for all physical emergencies; **988** (Suicide & Crisis Lifeline) added as a genuinely important second number, not just padding — distinguished clearly on-page (911 = physical danger, 988 = mental health crisis, no physical danger).
- **UK**: 999 and 112 are functionally identical (both reach the same services) — shown as two equal cards rather than picking one as "the" number, since sources are clear neither is more correct. 101 (non-emergency police, small per-call fee) and 111 (NHS non-emergency) added as a second row, mirroring the real UK convention of steering non-urgent calls away from 999.

**Integration**: hub card added to each of the 5 countries' `dailySection` (same `tool-icon-wrap`/`tool-card-arrow` markup as the 5-module expansion above, positioned right after the prayer-times card). Cross-links added to all 25 sibling daily-info pages (`{holidays,weather,prayer-times,gold-price,fuel-prices}` × 5 countries) via a small Node script matching each file's existing "insert before the primary-styled all-tools link" pattern — verified 100% consistent across all 25 files before running it (every sibling page ends its cross-link row with the identical `background:var(--primary)`-styled all-tools `<a>`, confirmed by grep before scripting, not assumed). `build-sitemap.js` got a new loop appending the 5 URLs (jo's was already present); sitemap grew 296→301, search-index 130→135.

**Push hit the usual GitHub secondary rate limit** (13 files dropped from a ~490-file full-tree push, including several of this task's own files: `sa/emergency-numbers/`, `us/index.html`, `sa/weather/prayer-times/fuel-prices/`, `us/weather/gold-price/fuel-prices/`, `uk/prayer-times/gold-price/fuel-prices/`, `build-sitemap.js`, `search-index.json`) — caught via the same tree-verification-by-blob-sha script documented in the 5-module expansion section above (reused as-is, not rewritten), fixed via one combined targeted-push script (single tree with `base_tree` + all 13 blobs, 700ms spacing between blob calls) rather than 13 separate single-file pushes. Re-ran the verification script afterward and got 0 mismatches before declaring done — same discipline as before, don't skip this step when a rate limit hits mid-push.


## Holidays extended to 2 years (2026-2027) + weather expanded to comprehensive city coverage — 2026-09-14

User-reported: Jordan's `jo/holidays/` already showed both 2026 and 2027 (built that way originally), but `om/sa/ae/us/uk/holidays/` only had 2026 — user asked ("العطل الرسمية في كل الدول دايما بدي سنتين") for all countries to always show 2 years like Jordan already does.

**2027 dates sourced via WebSearch, not guessed** (Islamic lunar dates especially need real sourcing, not estimation): Eid al-Fitr 2027 ≈ Mar 9-13, Eid al-Adha 2027 ≈ May 15-19, Islamic New Year 2027 ≈ Jun 5, Mawlid 2027 = Aug 14, Isra & Mi'raj 2027 ≈ Jan 6 — all Umm al-Qura-calendar estimates, inherently uncertain a year out (same caveat Jordan's page already carries). US federal holidays 2027 and UK bank holidays 2027 are **not** estimates — they're rule-based/government-confirmed (nth-weekday-of-month rules, Easter computus, weekend-observance shifts) and were also verified via WebSearch rather than hand-computed, to avoid an off-by-one error on rules like "Independence Day falls on Sunday → observed Monday."

**Implementation**: added a `lastYear`-tracking year-divider row to each country's `buildTable()` (om/sa/ae/us/uk previously lacked this entirely — only jo had it). For om/sa/ae (genuine lunar content), added a `prelimYear`/`prelimNote` bilingual disclaimer (same wording pattern as jo's own 2027 caveat) shown only on the 2027 divider. **Deliberately did NOT add the "preliminary/estimated" disclaimer to us/uk** — their 2027 dates are rule-confirmed, not moon-sighting-dependent, so labeling them "very preliminary" the same way as Islamic dates would be inaccurate and inconsistent with how confident the sourcing actually is. Also fixed a pre-existing copy-paste bug found while here: `us/holidays/` and `uk/holidays/` meta descriptions both said "Islamic dates are estimates pending moon sighting" despite neither page having a single lunar holiday — corrected to accurate US/UK-specific copy.

**Weather, same session**: user asked for full city coverage ("والطقس اعطيني كل المدن ل كل دوله ما عدا اميركا بدي 25 منطقة") — `jo/weather/` already covers all 12 governorates (no change needed), but `om/sa/ae/uk/weather/` each only had 5 cities. Expanded: **Oman** to all 11 governorates (added Khasab, Al Buraimi, Rustaq, Ibra, Ibri, Haima), **Saudi Arabia** to 14 cities covering all 13 provinces (added Abha, Tabuk, Hail, Arar, Jazan, Najran, Al-Bahah, Sakaka, Buraidah), **UAE** to all 7 emirates (added Ajman, Umm Al Quwain, Ras Al Khaimah — Al Ain, a non-emirate city already present, was kept), **UK** to 18 major cities (added Liverpool, Leeds, Bristol, Cardiff, Belfast, Newcastle, Sheffield, Nottingham, Southampton, Aberdeen, Oxford, Cambridge, Inverness), **US** to exactly 25 major metro areas per the explicit request (added Phoenix, Philadelphia, San Antonio, San Diego, Dallas, San Francisco, Seattle, Denver, Boston, Atlanta, Las Vegas, Washington DC, Detroit, Minneapolis, Orlando, Austin, Portland, New Orleans, Honolulu, Anchorage — deliberately including Hawaii and Alaska for real geographic range, not just contiguous-US metros).

City coordinates are general geographic knowledge (not subject to this project's legal/financial/religious verification policy) — used directly rather than WebSearched. Each new `<option value="X">` was cross-checked against its `CITY_COORDS` key via a Node script asserting zero missing/orphaned entries before pushing, and 5 newly-added cities (one per country) were live-verified via real headless-Chrome CDP calls to `fetchWeather()`, confirming real, plausible-for-the-location temperature/condition data came back (not just "no JS error").

**Push hit the usual GitHub secondary rate limit on both the holidays and weather batches** — 2 of 5 target files failed to blob in each full-tree push (truncated logs, not visible in the immediate error output) and needed the established targeted single-file push script; both batches re-verified via the blob-sha tree-diff script afterward with 0 mismatches before considering either done.
